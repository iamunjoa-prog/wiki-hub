> 문서가 낡지 않게 유지하는 방법. 누구나 고칠 수 있고, 관리자가 확인한 뒤 반영된다.

## 왜 제안·승인을 거치나

아무나 바로 고칠 수 있으면 문서는 빨리 낡지 않지만 **무엇이 왜 바뀌었는지** 를 잃는다.
반대로 관리자만 고칠 수 있으면 현장 지식이 반영되지 않는다.
그래서 **실무자가 제안하고 관리자가 확인해 반영** 하는 절차를 둔다.

## 절차

1. **수정 제안** — 문서 우측 상단 `✎ 수정 제안` 을 누르고 본문을 고친다. 무엇을 왜 바꾸는지 **사유** 를 함께 적는다.
2. **비교(diff) 확인** — 원문과 수정안이 나란히 비교된다. 의도한 부분만 바뀌었는지 확인하고 제출한다.
3. **관리자 검토** — 관리자의 `승인 관리` 메뉴에 대기 항목으로 올라간다.
4. **승인 또는 반려** — 승인되면 위키에 반영되고 버전이 올라간다. 반려되면 **사유가 함께 전달** 되므로 보완해 다시 제안한다.
5. **이력 확인** — 문서의 `⎇ 히스토리` 에서 버전별 변경 내용을 본다.

> 진행 상태는 **내 요청 현황** 메뉴에서 확인한다.

## Git 워크플로우와의 대응

지식 문서를 Git + 마크다운으로 관리하기 때문에, 이 절차는 Git 동작에 그대로 대응된다.
승인 절차를 따로 개발한 것이 아니라 **Git이 이미 하는 일을 화면으로 보여주는 것** 이다.

| 허브 화면 | Git |
| --- | --- |
| 수정 제안 | 브랜치 생성 + 커밋 |
| diff 비교 뷰 | Pull Request diff |
| 관리자 승인 | PR Approve |
| 반려(사유 입력) | Request changes |
| 위키 반영 | main 브랜치 머지 |
| 수정 이력 | `git log` · `git blame` |

## 편집 경로 두 가지

### ① 웹앱 UI — 일반 담당자

에디터에서 고치면 뒤에서 브랜치·커밋이 자동으로 만들어진다. Git을 몰라도 된다.
문서 한두 건을 고칠 때 쓴다.

### ② Claude Code CLI — 파워 유저

저장소를 로컬에 두고 자연어로 문서를 수정하거나 PR을 만든다.
단건 수정보다 **일괄 작업** 에서 가치가 크다.

- "모든 PPM 문서의 UI 버전 표기를 5.4.1 기준으로 갱신해줘"
- "용어 사전에 없는 약어를 본문에서 찾아 항목으로 추가해줘"

## 시트를 정식 문서로 승격하기

개인이 관리하던 편성·마케팅 시트에 쌓인 기준도 지식 자산이다.

1. **GNB별 편성표** 에 시트를 등록한다.
2. 시트 상세에서 `↑ 정식 지식 문서로 승격 요청` 을 누른다.
3. 관리자가 카테고리를 지정해 승인하면 위키 문서로 만들어진다.

담당자가 바뀌어도 노하우가 남게 하는 것이 목적이다.

## 문서를 새로 넣으려면

마크다운 파일을 폴더에 넣는 방식이 가장 빠르다. 형식은 [문서 작성 규칙](HUB-03)을 본다.
