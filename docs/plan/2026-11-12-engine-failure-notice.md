# 챗봇 엔진 실패 안내 문구

상위 지시: 배포 챗봇에서 Gemini 가 일시 과부하(503)로 실패하면 답변 하단에 원문 JSON 이 그대로 보인다. 짧은 문장으로 바꾼다.
분담: `dev-server` 가 서버 오류를 `{ error, code }` (짧은 문장 + 분류 코드)로 바꾸고, `dev-front` 가 이 문서의 문구·위치로 화면에 반영한다. 작성 `chatbot-planner`.

## 지금 보이는 것

실제로 나오는 줄:

```
답변 · 규칙 기반 (Gemini: 모델 gemini-3.8-flash 호출 실패 — {"error":{"code":503,"message":"This model is currently experiencing high demand...
```

만들어지는 경로:

- `server/gemini.ts` `callGemini` 가 SDK 오류 원문을 `모델 {model} 호출 실패 — {원문}` 으로 감싼다.
- `api/ask.ts` 가 그 문장을 502 `{ error }` 로 돌려준다.
- `src/lib/assistant.ts` `requestEngine` 이 `{error} (HTTP {status})` 로 다시 감싸고, `askAssistant` 가 `shortReason` 으로 140자에서 자른 뒤 `answeredBy` 에 `규칙 기반 (엔진: 사유 · …)` 형식으로 넣는다.
- `src/components/AssistantDock.tsx` 113행이 `답변 · {answeredBy}` 를 `.msg .by` 에 그린다. 이 줄은 11.5px 고정폭 회색 글꼴이라 로그처럼 읽힌다.

### 현재 라벨 정리

`{N}` 은 `ENGINE_TIMEOUT_MS` 값(claude 150, codex 210, gemini 90)이다. 모든 줄 앞에 `답변 · ` 이 붙는다.

## 분류 코드별 안내 문구

원칙

- 기술 원문(JSON, HTTP 상태, exit 코드, stderr, 모델명, 환경변수 이름)은 실무자 화면에 내지 않는다.
- 한 줄에 세 가지를 담는다: 무엇이 일어났는지, 지금 답이 어디서 왔는지, 실무자가 할 일.
- 말투는 화면 안내 문구에 맞춰 합니다체로 쓰고 권유는 `~세요` 로 한다. 화면은 이미 `연결되었습니다`, `실행하세요`, `규칙 기반 답변으로 동작 중입니다` 처럼 쓴다.
- 이 상황에서 "문서 기준"이라는 말이 뜻을 가진다. 규칙 기반 답도 위키 문서를 검색해 만들기 때문에, 답이 지어낸 것이 아니라 문서에서 나왔다는 점을 알린다.
- 할 일은 두 가지로만 나눈다. 시간이 지나면 풀리는 문제는 "잠시 후 다시 물어보세요", 사람이 손대야 풀리는 문제는 "관리자에게 알려 주세요".

| 코드 | 언제 (분류 기준) | 실무자 안내 (한 줄) | 할 일 유형 |
| --- | --- | --- | --- |
| `overloaded` | Gemini 503·UNAVAILABLE, "high demand"·"overloaded" | AI 엔진이 잠시 붐벼 문서 기준 규칙 기반으로 답했습니다. 잠시 후 다시 물어보세요. | 다시 묻기 |
| `timeout` | 화면 쪽 중단, CLI 시간 초과, 배포 함수 504 | AI 엔진 응답이 늦어 문서 기준 규칙 기반으로 답했습니다. 잠시 후 다시 물어보세요. | 다시 묻기 |
| `quota` | 429·RESOURCE_EXHAUSTED | AI 엔진 사용 한도에 걸려 문서 기준 규칙 기반으로 답했습니다. 계속되면 관리자에게 알려 주세요. | 관리자 |
| `auth` | 401·403, 키 미설정·만료, CLI 미로그인 | AI 엔진 연결 설정에 문제가 있어 문서 기준 규칙 기반으로 답했습니다. 관리자에게 알려 주세요. | 관리자 |
| `model` | 404·모델명 오류 | `auth` 와 같은 문장 | 관리자 |
| `unknown` | 빈 응답, 구성 누락(500), 네트워크 끊김, CLI 비정상 종료, 그 밖의 모든 경우 | AI 엔진 응답을 받지 못해 문서 기준 규칙 기반으로 답했습니다. 계속되면 관리자에게 알려 주세요. | 다시 묻기, 계속되면 관리자 |

같이 정할 두 경우

| 경우 | 안내 |
| --- | --- |
| 엔진 없음 (실패가 아니라 원래 규칙 기반) | 안내 줄 없음. 출처 줄은 `답변 · 규칙 기반 (문서 기준)` |
| 앞 엔진 실패 후 다음 엔진 성공 (로컬) | 안내 줄 없음. 답은 정상이다. 출처 줄은 `답변 · Gemini (Claude 응답 실패)` 처럼 엔진 이름과 "응답 실패"만 둔다 |

`model` 을 `auth` 와 같은 문장으로 둔 이유: 실무자가 할 일은 둘 다 "관리자에게 알리기"로 같다. 둘을 가르는 정보(모델명이냐 키냐)는 관리자에게만 쓸모가 있다.

### 관리자에게만 보일 것

- 관리자(`session.role === 'admin'`)에게만 출처 줄 끝에 `· Gemini overloaded` 처럼 엔진 이름과 분류 코드를 붙인다. 로컬에서 여러 엔진이 실패했으면 `· Claude timeout · Gemini quota` 처럼 이어 쓴다. 이것만 있어도 키·모델·할당량 가운데 어디부터 볼지 정할 수 있다.
- 원문(SDK 오류 JSON, stderr)은 관리자 화면에도 내지 않고 서버 로그(`console.error`)에만 둔다. 이유: `session.role` 은 화면 상단에서 실무자↔관리자로 바로 바꿀 수 있는 값이라 보안 경계가 아니다. 응답 본문에 실린 것은 누구나 개발자 도구로 볼 수 있다. 그래서 `dev-server` 가 응답에 원문을 싣지 않는 것이 실제 차단선이다. 키 값은 어떤 경우에도 응답에 넣지 않는다.

## 화면 위치 제안

- 출처 줄(`.msg .by`)은 지금처럼 짧은 출처 표시로만 쓴다. 실패했을 때는 `답변 · 규칙 기반 (문서 기준)`, 관리자에게는 그 뒤에 `· Gemini overloaded` 를 붙인다.
- 안내 한 줄은 출처 줄 바로 위에 따로 작은 안내로 둔다. 본문 글꼴, 작은 크기, 회색 계열로 한다. 고정폭 글꼴은 로그처럼 읽혀서 피한다. 빨간 경고색도 피한다. 답은 정상으로 나왔고, 빨간색을 쓰면 답 내용까지 의심하게 된다.
- 안내는 실패한 그 답변에만 붙인다. 대화창 상단 배너나 토스트는 쓰지 않는다. 토스트는 사라지면 어느 답이 규칙 기반이었는지 알 수 없다.
- 데이터 모양 제안(`dev-front`·`dev-server` 협의): `AssistantReply` 에 `fallback?: { code; engine }[]` 를 두고, 문구는 화면에서 코드로 고른다. `answeredBy` 에 문장을 섞지 않는다.
- 새 기능(다시 묻기 버튼, 재시도 자동화)은 넣지 않는다.

## 이 변경으로 막히는 오답 사례

- 실무자가 `{"error":{"code":503,…}}` 를 보고 답 자체가 오류라고 여겨 버리거나, 원문을 그대로 캡처해 문의하는 일이 없어진다.
- 일시 과부하인데 "관리자에게 알리세요"가 나가 불필요한 문의가 생기는 일, 반대로 키 만료인데 "다시 물어보세요"만 나가 같은 실패가 반복되는 일을 코드별 할 일로 가른다.
- 로컬에서 Gemini 가 정상으로 답했는데 앞선 CLI 실패 원문이 붙어 답이 실패한 것처럼 보이던 일이 없어진다.

## 열린 질문

1. `unknown` 에 묶은 배포 구성 누락(프롬프트·문서 폴더 500)과 키 미설정을 따로 `config` 로 뺄지. 실무자 문구는 `auth` 와 같고, 관리자 줄만 달라진다.
2. 같은 실패가 연달아 나면 답변마다 안내를 반복할지, 첫 답에만 붙일지. 이 문서는 우선 매번 붙이는 것으로 둔다.
3. `CliStatus` 의 `연결됨` 을 마지막 실패 코드(예: `quota`)에 맞춰 바꿀지. 이건 새 상태 저장이 필요해 이번 범위에서 뺐다.
4. 수정 제안 경로(`aiEdit`, `AI 수정에 실패했습니다 — {원문}`)도 같은 원문을 보인다. 같은 분류를 쓸지는 `requests-planner` 와 함께 정한다.
5. 시간 초과 문구에 기다린 시간(`90초`)을 넣을지. 이 문서는 넣지 않는 쪽이다. 실무자에게는 숫자보다 할 일이 중요하다.
