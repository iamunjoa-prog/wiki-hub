# 챗봇 대화로 지식 입력·수정하기

상위 지시: "챗봇 대화로 지식 입력하거나 수정하도록 기획해줘"
기본 방향(PM 데스크): 챗봇은 파일을 바로 쓰지 않는다. 대화로 초안을 만들고, 사용자가 diff를 확인하고, 승인을 거쳐 PR로 반영한다.

> **진행 현황 (2026-11-10)** — 이 기획서는 #47 이전 코드를 기준으로 썼다.
> - 2단계의 핵심(수정 제안 = 실제 PR, 제안 목록 API, 가짜 승인 흐름 제거, 제출 전 안전장치)은 main #47 로 먼저 들어갔다. 아래 "현재 상태"·"1단계"의 '승인 문구 바로잡기·준비 중 안내'는 그래서 필요 없어졌다.
> - 1단계 중 남은 것(프롬프트 경로 정정, 다섯 번째 발화 유형 "지식 입력·수정", 규칙 기반 답변의 같은 안내)은 반영했다. 안내 문구는 "제출 → PR → 머지 → 다음 배포" 기준이다.
> - 편성표 승격은 아직 화면 안 기록뿐이다(저장소 반영 없음).
> - 다음은 3단계(대화 초안 카드)다. 착수 전에 #47 의 createEditPR·docEdit 기준으로 3단계 설계를 다시 맞춘다.
> - (2026-11-12) 담당 이름이 바뀌었다. 아래 표의 `dev` 는 서버 쪽이면 `dev-server`, 화면 쪽이면 `dev-front` 로 읽는다. `wiki-ux` 의 "반영"은 `dev-front` 가 맡고, 승인·제안 화면 흐름은 `requests-planner` 가 설계한다. 남은 3단계 재배정은 `docs/plan/2026-11-12-agent-team-expansion.md` "11-10 기획 남은 작업 재배정".

## 문제

편성·마케팅 실무자는 대화하다가 문서가 틀렸거나 빠진 것을 발견한다. 지금은 그 자리에서 고칠 길이 없다.

| 누가 | 어떤 상황에서 | 무엇을 못 하나 |
| --- | --- | --- |
| 실무자 | 챗봇 답이 바뀐 정책과 다르다 ("결재선 바뀌었어") | 대화 중에 문서 수정을 요청할 수 없다. 챗봇은 읽기 전용이다. |
| 실무자 | 새로 정한 규칙을 남기고 싶다 | 챗봇에 말해도 남지 않는다. "+ 새 문서" 화면에 처음부터 다시 써야 한다. |
| 실무자 | 수정 제안 화면에서 제안을 낸다 | 새로고침하면 제안이 사라진다. 다른 사람이 볼 수 없다. |
| 승인자 | 제안을 승인한다 | "커밋 생성 후 위키에 반영했습니다"라는 안내가 뜬다. 실제로는 아무것도 반영되지 않는다. |

가장 급한 것은 마지막 줄이다. 사실과 다른 안내가 지금 나가고 있다.

### 결론

"기존 승인 흐름"은 저장되지 않는 메모리 상태다. 승인자 역할도 스스로 고른다. 그래서 기본안의 "기존 승인 흐름을 거쳐 PR"은 그대로 쓸 수 없다. 아래 수정안을 제안한다.

## 기본안 수정 제안 — PR을 승인 대기열로 쓴다

| 구분 | PM 데스크 기본안 | 수정안 (권장) |
| --- | --- | --- |
| 흐름 | 대화 초안 → diff 확인 → 허브 승인 → PR 생성 → 머지 | 대화 초안 → diff 확인 → **제출 = PR 생성** → **승인 = PR 머지** |
| 대기 목록 저장 | 메모리 (사라짐) | GitHub 열린 PR (영속, 공유) |
| 승인 권한 | 스스로 고른 역할 | 저장소 쓰기 권한이 있는 사람 |
| 승인 화면 | `Approvals.tsx` 가 메모리 목록을 본다 | `Approvals.tsx` 가 라벨 `wiki-edit` 이 붙은 열린 PR 목록을 본다 |
| 새로 지어야 할 것 | 제안 저장소, 승인자 인증 | 없음. GitHub이 둘 다 해 준다 |

근거.
· 제안을 저장할 곳이 없다. 배포판은 파일을 못 쓰고 DB도 없다.
· PR은 이미 저장·공유·diff·권한·이력이 있다.
· 새 문서 흐름이 이미 이 방식이다 (제출하면 PR, 머지되면 반영). 두 흐름이 같아진다.

허브 안에서 머지 버튼까지 둘지는 열린 질문 Q2 로 남긴다. 1차는 "GitHub에서 머지" 링크만 둔다.

### 의도 알아채기 — 다섯 번째 발화 유형 "지식 입력·수정"

| 신호 | 예 | 처리 |
| --- | --- | --- |
| 명시 요청 | "문서에 추가해줘", "이거 고쳐줘", "반영해줘", "새 문서로 남겨줘" | 지식 입력·수정으로 본다 |

### 흐름 A — 기존 문서 수정

1. 사용자: "판촉 쿠폰 품의 결재선 바뀌었어. 이제 팀장 전결이야."
2. 챗봇: 정정을 인정하고 "문서 수정 초안을 만들까요?"를 묻는다.
3. 사용자: "응."
4. 챗봇: 대상 문서가 하나면 바로 초안을 만든다. 여럿이면 후보를 보여준다 (되묻기 1).
5. 서버가 대상 문서 원문을 넣어 초안을 만든다 (엔진이 직접 읽지 않는다. gemini 도 같은 방식으로 동작한다).
6. 화면: 대화 아래 **초안 카드**가 뜬다.
7. 사용자: 카드에서 diff 를 확인한다. 필요하면 [편집] 으로 수정 제안 화면을 연다 (본문이 채워진 상태).
8. 사용자: [제출] 을 누른다. 서버가 마스킹·충돌 검사 후 PR 을 연다.
9. 화면: "PR을 열었습니다. 머지되면 다음 배포에서 반영됩니다." 와 PR 링크.

### 흐름 B — 새 문서 추가

1. 사용자: "빅배너 A/B 테스트 운영 기준을 새 문서로 남겨줘. 내용은 ..."
2. 챗봇: 카테고리·서브메뉴 후보를 보여준다 (되묻기 1). 비슷한 기존 문서가 있으면 "기존 문서에 추가할까요, 새 문서로 만들까요?"를 먼저 묻는다.
3. 챗봇: 제목·요약·본문 초안을 만든다. 본문은 사용자가 말한 내용만 정리한다.
4. 화면: 초안 카드 (전체 본문 미리보기). [편집] 은 "+ 새 문서" 화면을 채운 상태로 연다.
5. 사용자: [제출]. 기존 `createDocPR` 로 PR 을 연다. 마스킹 검사를 거친다.

## 데이터와 API

### 응답 스키마 확장

`server/knowledge.ts` 의 `REPLY_SCHEMA` · `CliReply` · `checkAskReply` 를 함께 바꾼다. 세 엔진이 이 하나를 공유한다.

| 필드 | 형식 | 설명 |
| --- | --- | --- |
| `text` | string | 기존 그대로 |
| `sourcePaths` | string[] | 기존 그대로 |
| `action` | object, 선택 | 없으면 기존 답변과 같다 |
| `action.type` | `'none' \| 'propose_edit' \| 'propose_new'` | |
| `action.path` | string | 수정 대상 경로. `지식/` 아래여야 한다. 서버가 실제 존재를 확인한다 |
| `action.category`, `action.subcategory`, `action.title`, `action.summary` | string | 새 문서일 때 |
| `action.changes` | `{ before: string, after: string, basis: string }[]` | 수정일 때. `before` 는 원문에 그대로 있어야 한다 |
| `action.body` | string | 새 문서 본문 |
| `action.reason` | string | 사용자가 밝힌 근거. 없으면 빈 문자열 |

설계 원칙.
· 엔진은 **전체 본문을 다시 쓰지 않고** 바뀌는 줄만 낸다. 서버가 원문에 `before → after` 를 적용한다. 엔진이 다른 줄을 몰래 바꾸는 것을 막는다.
· `before` 가 원문에 없거나 두 번 이상 나오면 서버가 `action` 을 버리고 `text` 만 돌려준다. 화면에는 "초안을 만들지 못했습니다. 바꿀 줄을 다시 알려 주세요"를 띄운다.
· `action` 은 **제안일 뿐이다.** `/api/ask` 는 어떤 경우에도 GitHub 을 호출하지 않는다.

### 새 API — 기존 문서 수정 PR

| 항목 | 내용 |
| --- | --- |
| 함수 | `server/github.ts` `updateDocPR(input, opts)` · `parseUpdateDocInput(raw)` |
| 입력 | `path`, `baseSha` (초안을 만들 때의 파일 sha), `newBody`, `reason`, `requestedBy`, `origin` (`chat` / `form`) |
| 처리 | main 의 현재 파일 sha 조회 → `baseSha` 와 다르면 409 → 마스킹 검사 → 머리말 `version +1`, `updatedBy`, `updatedAt` 갱신 → 브랜치 `edit/<문서코드>-<시각>` → 파일 PUT (sha 포함) → PR 생성, 라벨 `wiki-edit` |
| PR 본문 | 요청자(자칭 표시), 출처(챗봇/수정 제안 화면), 근거, 바뀐 줄 요약, "머지되면 다음 배포에서 반영됩니다" |
| 로컬 | `server/cliBridge.ts` 에 `/api/proposeEdit` 미들웨어 |
| 배포 | `api/proposeEdit.ts` |
| 공유 원칙 | 입력 검사·마스킹 검사·본문 조립은 `server/github.ts` 와 `server/knowledge.ts` 에만 둔다. `cliBridge.ts` 와 `api/proposeEdit.ts` 는 호출만 한다. 두 쪽이 같은 함수를 부른다 |

`baseSha` 를 얻는 법: 문서는 빌드에 묶여 있어 sha 가 없다. 초안 카드를 띄울 때 `/api/docSha?path=` (또는 `/api/proposeEdit` 의 사전 조회 모드)로 main 의 현재 sha 를 받아 둔다. 같은 원칙으로 server/ 와 api/ 를 함께 만든다.

### 승인 흐름을 실제 PR 과 연결

| 단계 | 지금 | 2단계 | 3단계 |
| --- | --- | --- | --- |
| 제출 | 메모리에 저장 | `/api/proposeEdit` 호출. PR 링크를 받는다. "내 요청" 에 PR 링크를 남긴다 (브라우저 저장) | 대화 초안 카드도 같은 API |
| 승인 | 화면 데이터만 바꿈 | 승인 화면은 "GitHub에서 검토·머지" 링크로 바꾼다. 허브 안 승인 버튼은 끈다 | 승인 화면이 `wiki-edit` 라벨 열린 PR 목록을 읽는다 (`/api/proposals`) |
| 반영 | 없음 | 머지 → 재배포 | 같음 |
| 안내 문구 | "커밋 생성 후 위키에 반영했습니다" | "PR을 열었습니다 · 머지되면 다음 배포에서 반영됩니다" | 같음 |

1단계에서는 API 를 만들기 전이므로 승인 문구만 바로잡는다 (아래 단계 참고).

## 안전

### 마스킹 서버 검사

| 항목 | 기준 |
| --- | --- |
| 적용 대상 | `createDocPR`, `updateDocPR` 에 들어가는 모든 본문·제목·요약·PR 본문 |
| 위치 | `server/knowledge.ts` `checkMasking(text): { blocked: Hit[], warned: Hit[] }`. server/ 와 api/ 가 같이 쓴다 |
| 막는 것 (제출 불가) | 금액 + 매출 표현 (예: `억 원`, `매출 N원`, `UV당 매출`) · 제휴사 실명 목록 · 사내 URL·IP 패턴 · 사람 실명 패턴(머리말 `updatedBy` 의 마스킹 형식 `구*화` 외) |
| 경고만 하는 것 | 금액처럼 보이는 숫자 (`N만 원`). 쿠폰 할인 금액은 남겨도 되는 값이라 막지 않는다 |
| 남기는 것 | 반응률(%), 가입자 수, 모수, 쿠폰 할인 금액, 배너 규격, UI 버전 |
| **제휴사 실명 목록의 위치** | **코드에 두지 않는다.** 실명 목록을 공개 저장소에 올리면 그 자체가 누출이다. 시스템 목록처럼 공유 드라이브 파일을 환경 변수 `HUB_MASK_FILE` 로 가리킨다. 배포판은 Vercel 환경 변수에 둔다 |
| 목록이 없을 때 | 제출을 막는다 (닫힌 쪽 기본값). "마스킹 기준을 불러오지 못했습니다" |
| 응답 | 막히면 422 와 걸린 위치·종류. 걸린 원문은 응답에 다시 싣지 않고 줄 번호만 준다 |

### 인증·requestedBy

| 문제 | 영향 | 대응 |
| --- | --- | --- |
| 배포판에 인증이 없다 | 누구나 PR 을 열 수 있다. 공개 URL 이라 스팸 PR 이 가능하다 | Q3 에서 고른다. 고르기 전까지 배포판의 쓰기 API(`createDoc`, `proposeEdit`)는 끈다 |
| `requestedBy` 를 위조할 수 있다 | PR 에 남은 이름을 믿을 수 없다 | PR 본문에 "요청자(자칭)"로 표시한다. 책임 확인은 머지하는 사람이 한다 |
| 승인자 역할을 스스로 고른다 | 허브 안 승인은 의미가 없다 | 승인 = GitHub 머지로 옮긴다 (수정안) |
| 토큰 권한 | 토큰이 main 에 직접 쓸 수 있으면 사고가 크다 | 토큰은 contents·pull requests 쓰기만. main 은 브랜치 보호로 직접 푸시 금지 (ops) |
| 남용 | 반복 제출 | 서버에서 같은 요청자·같은 문서 1분 1건 제한. 하루 상한은 ops 가 정한다 |

### 근거 없는 내용 지어내기 방지

| 장치 | 내용 |
| --- | --- |
| 프롬프트 규칙 | 초안에는 사용자 발화와 기존 문서에 있는 것만 넣는다. 없는 값은 비워 두고 묻는다 |
| 줄별 `basis` | `changes[].basis` 가 비어 있으면 서버가 그 변경을 버린다 |
| 숫자 대조 | `after` 에 새로 나온 숫자·날짜·버전이 사용자 발화와 원문 어디에도 없으면 카드에 "근거 확인 필요" 경고를 띄운다. 제출은 막지 않는다 |
| 줄 단위 적용 | 엔진은 바뀌는 줄만 낸다. 서버가 적용한다. 다른 줄은 원문 그대로 남는다 |
| 변경 크기 | 한 번에 바꾸는 줄이 원문의 절반을 넘으면 "새로 쓰기에 가깝습니다. 편집 화면에서 확인해 주세요" 경고 |
| 사람 확인 | diff 확인과 [제출] 버튼, 그리고 GitHub 머지. 두 번 사람 눈을 거친다 |

### 충돌

| 경우 | 처리 |
| --- | --- |
| 초안을 만든 뒤 main 의 문서가 바뀌었다 | `baseSha` 가 다르면 409. 카드에 "문서가 그사이 바뀌었습니다. 초안을 다시 만들까요?" |
| 같은 문서에 열린 `wiki-edit` PR 이 이미 있다 | 새 PR 을 열기 전에 확인한다. 카드에 기존 PR 링크와 함께 "이미 검토 중인 수정이 있습니다" 를 보여준다. 계속 열지는 Q5 |
| 두 PR 이 모두 머지된다 | 두 번째 머지는 GitHub 이 충돌로 막는다. 머지하는 사람이 해결한다. 허브는 관여하지 않는다 |
| 머지 후 재배포 전 | 허브 문서는 옛 내용이다. 승인 화면과 문서 화면에 "반영 대기 중인 수정이 있습니다" 표시 (3단계) |

| 항목 | 현재 | 제안 | 영향 | PM 의견 |

| Q1 승인 흐름 | 허브 안 승인 (메모리, 스스로 고른 역할) | 제출 = PR 생성, 승인 = GitHub 머지 | 기본안과 다르다. 허브 승인 화면 역할이 "PR 목록 보기"로 바뀐다 | 수정안 권장. 저장소·권한을 새로 만들 필요가 없다 |
| Q2 허브 안 머지 버튼 | 없음 | 1차는 GitHub 링크만. 머지 버튼은 인증이 생긴 뒤 | 승인자가 GitHub 에 들어가야 한다 | 링크만 권장. 인증 없이 머지 버튼을 두면 누구나 머지할 수 있다 |
