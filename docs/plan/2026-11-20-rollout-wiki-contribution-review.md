## 0-1. 2026-11-20 계정 조건 확정 — 팀 계정 4개 + 관리자 1개

상위 지시자가 계정을 **4개 팀에 팀 계정 1개씩(member) + 관리자 전용 계정 1개(admin), 모두 5개**로 정했다. 팀 계정 하나를 관리자로 쓰면 그 팀원 모두가 전체 대화 기록·삭제·계정 발급 권한을 갖게 되므로 관리자는 따로 둔다. 아래 내용이 이 문서의 다른 절보다 우선한다.

## 1. 문제

**누가:** 편성·마케팅 실무자 전체(수십~수백 명)와 이들을 관리할 허브 관리자 몇 명.

**어떤 상황에서:** 지금 허브는 소수가 쓰고 있다. 실무자 전체에게 열어 "각자 아는 것을 위키 문서로 모아 가는" 단계로 넘어가려 한다.

**무엇을 못 하거나, 무엇이 위험한가:**

1. **관리자**는 수백 명의 계정을 발급하고, 비밀번호를 잊은 사람·퇴사자를 정리해야 한다. 지금 도구로는 발급은 되지만, 사무실 전체가 로그인 잠금에 걸리면 풀 방법이 없고, 누가 안 쓰는지 알 수 없다.
2. **실무자**는 새 문서·수정 제안은 낼 수 있지만, 새 분류를 만들거나 문서를 지우거나 옮기는 일은 할 수 없다. 그런 요청을 어디에 내야 하는지도 안내가 없다.
3. **승인자**는 GitHub에서 머지한다. 허브 관리자가 GitHub 권한이 없으면 승인할 수 없고, 제안이 많아지면 허브 목록(최근 50건)에서 대기 중인 제안이 사라진다.
4. **회사 전체**의 위험: 이 저장소는 공개다. 실무자가 올린 문서에 제휴사 실명·매출 금액·직원 실명이 들어가면 **PR이 열리는 순간 공개**되고 반려해도 지워지지 않는다. 지금 검사는 새 문서 일부만 막고, 수정 제안과 작성자 이름은 막지 않는다.

**안 되는 것**

- 계정 **삭제** 없음 (중지만). 아이디 변경 없음.
- **마지막 로그인 시각**을 남기지 않음 → 안 쓰는 계정·퇴사자를 골라낼 근거가 없음.
- 팀 단위·여러 명 **일괄 중지** 없음.
- 본인 비밀번호 찾기(메일 등) 없음 — 반드시 관리자가 초기화.
- 관리자가 **로그인 잠금을 풀 수 없음** — 10분 기다려야 함.
- 권한은 `member`·`admin` 둘뿐. 관리자 한 명이 계정 관리와 승인 관리 화면을 함께 가짐.

**흐름 (지금)**

```
새 문서:   /wiki/new → (화면) 공개 검사 → POST /api/createDoc
           → 서버 공개 검사 → 코드 자동 채번 → 새 브랜치 docs/{코드}-… → 파일 1개 → PR

승인:      GitHub PR 화면에서 머지 → main 반영 → 다음 배포 때 위키에 보임
```

**지금 되는 것**

- 새 문서: 카테고리·서브메뉴는 **이미 있는 목록에서만** 고른다(서버가 `isKnownPlace` 로 다시 본다). 시스템 매뉴얼(코드가 숫자로 안 끝남)은 자동 채번이 안 돼 목록에서 뺐다. 파일은 `지식/{카테고리}/{코드}.md` 로 생긴다.
- 수정 제안: 본문만 보낸다. 서버가 main의 프론트매터를 줄 단위로 복사하고 `version`·`updatedBy`·`updatedAt` 세 줄만 바꾼다. 수정 사유 필수.
- 충돌(409): 제출할 때 main 버전이 화면 버전과 다르면 PR을 열지 않고 최신 본문을 함께 돌려준다. 화면은 "재배포 전이면 옛 버전일 수 있다, 편집 내용은 남아 있다"를 보인다.
- 한도(429): 새 문서·수정 제안을 합쳐 **계정당 하루 30건**. 넘으면 "내일 다시"로 안내. 챗봇·AI 수정은 분당 10회.
- 제안 목록: 허브가 따로 저장하지 않고 GitHub PR을 읽는다. 상태는 대기 중·머지됨·닫힘.
- "AI로 수정"(`api/edit.ts`): 지시문을 받아 Gemini가 고친 본문을 **돌려줄 뿐 저장하지 않는다.** 사용자는 이 결과를 다시 수정 제안으로 낸다. 즉 **main에 바로 쓰는 "직접 수정" 경로는 없다.**

**챗봇 삭제를 되게 하려면** (상용화 후, 순서대로)

1. 먼저 **사람이 화면에서 삭제 제안**을 할 수 있어야 한다 (삭제 PR 서버 함수 + 승인 목록이 "삭제"를 구분). 챗봇은 그 위에 얹는다.
2. 삭제 전 확인: 다른 문서가 이 코드로 링크하는지(`[…](PPC-R-02)`) 찾아 보여 주기. 링크가 깨져도 오류가 나지 않는 구조라(`writing.md`) 꼭 필요하다.
3. `REPLY_SCHEMA` 의 `action.type` 에 `delete`(필요하면 `move`) 추가 — `server/knowledge.ts` 는 로컬·배포 공유라 한 번에 바꾼다.
4. 프롬프트 5절의 "삭제는 none" 문장을 대상·사유 되묻기 규칙으로 바꾼다.
5. 카드: 삭제는 미리보기 대신 "이 문서를 가리키는 문서 n개"를 보이고, 제출은 여전히 사람이 누른다.

정리하면, **배포 허브에서 실무자가 제휴사 실명이나 금액을 넣으면** 새 문서든 수정 제안이든 경고만 뜨고 제출할 수 있다. 그리고 PR이 열리는 순간 공개된다. 반려해도 PR 화면의 diff는 공개 저장소에 계속 남는다.

참고로 금액을 일괄 차단하기 어려운 이유도 있다. 챗봇 규약(`assistant-prompt.md` 6절)은 "쿠폰 할인 금액과 할인율은 그대로 둔다"로 정해 두었다. 그래서 금액 차단을 넓히면 정당한 쿠폰 문서까지 막힌다.

**비공개 이름 목록(`HUB_PRIVATE_TERMS_FILE`) 운영**

- 지금: 공유 드라이브 파일을 가리킨다. 한 줄에 하나, `#` 주석, JSON 배열도 된다. 2글자 미만은 버린다. 1분 캐시를 둔다. 로그에는 건수만 남긴다.
- 빈틈 ① 배포 함수는 공유 드라이브를 못 읽는다 (`requests-report.md` 13절 R-B, 미결).
- 빈틈 ② 목록을 누가 언제 갱신하는지 정해 두지 않았다. 새 제휴사가 생겨도 목록에 없으면 통과한다.
- 빈틈 ③ 실무자 PC마다 `.env.local` 에 경로를 넣어야 로컬에서도 검사가 돈다. 설치 스크립트가 넣어 주는지는 **확인하지 못했다**.
- 보완안: 배포본은 Vercel 환경변수에 **목록 내용**을 넣는다(예: `HUB_PRIVATE_TERMS`, 코드·저장소에는 두지 않음). ops가 월 1회와 새 제휴 때 공유 드라이브 파일과 환경변수를 함께 갱신한다.

| 하는 일 | 수정 제안 서버 검사, 배포본 이름 목록, 작성자 가림, 승인자 점검표 | GitHub 설정에서 비공개로 전환 | `지식/` 을 별도 비공개 저장소로. 앱 저장소는 공개 유지 |
| 유출 막는 정도 | 목록·패턴에 걸리는 것만. **목록에 없는 새 이름, 문맥상 금액은 새어 나감.** 새면 되돌릴 수 없음 | 외부 공개는 막음. 사내 열람자만 봄 | 문서는 외부 공개 안 됨 |
| 실무자 설치·업데이트 | 그대로 | **깨진다.** 한 줄 설치(`install-hub.sh`)와 업데이트(`update-hub.ps1`)가 토큰 없이 공개 저장소의 압축을 받는 구조 | 앱은 그대로 받는다. 로컬 허브에 문서를 넣는 방법을 새로 만들어야 함 |
| 개발 작업량 | 작다 (서버 함수 몇 곳) | 설정은 작다. 설치·업데이트 경로를 토큰 방식으로 다시 짜야 해 초보자 설치가 어려워짐 | 크다. 빌드가 문서 저장소를 받아 오기, `api/ask.ts` 의 문서 포함, 허브 ZIP, PR 대상 저장소(`GITHUB_REPO`) 분리 |
| 이미 공개된 것 | 그대로 남음 | 비공개 전환 뒤에도 이미 받아 간 복제본·포크는 남음 | 기존 앱 저장소의 문서 이력은 남음 (이력 정리는 별도) |
| Vercel 무료 플랜 | 영향 없음 | 개인 계정 비공개 저장소 배포는 가능한 것으로 알고 있으나 **확인 필요** | 빌드 때 다른 비공개 저장소 접근 토큰이 필요 |

PM 의견은 결정 필요 표 D1에 적었다.

**GitHub 토큰 한 개 구조의 한계**

| 한계 | 설명 |
| --- | --- |
| 작성자 표시 | GitHub에서 PR·커밋 작성자는 늘 **토큰 주인 한 사람**이다. 실제 요청자는 PR 본문 첫 줄 글자뿐이라, 이 글자는 꾸밀 수 있는 값(로컬 허브는 화면이 보낸 값)이다 |
| 권한 | 토큰이 저장소 쓰기 권한을 가진다. 유출되면 저장소 전체가 위험하다. 토큰 주인이 퇴사하면 모든 제출이 멈춘다 |
| API 한도 | 개인 토큰은 시간당 5,000회, 그리고 "만드는 요청"에 분·시간 단위 보조 한도가 따로 있다. 새 문서 1건은 GitHub 호출 4번(그중 쓰기 3번), 목록 1번은 1회, 허브 내려받기도 같은 토큰을 쓴다. 지금 규모에서는 여유가 있지만 **전체 상한이 없어** 몰리면 모두가 함께 실패한다 |
| 보완 (상용화 후) | GitHub App으로 바꾸면 봇 이름으로 올라가고, 권한을 저장소 하나·필요한 범위로 줄일 수 있다. 토큰 주인 퇴사 문제도 사라진다 |

**Vercel·Upstash 무료 한도**

| 항목 | 지금 | 위험 | 확인 필요 |
| --- | --- | --- | --- |
| 배포 함수 수 | `api/` 에 12개 (`ask`·`auth`·`chatlog`·`createDoc`·`download-hub`·`edit`·`engines`·`proposals`·`proposeEdit`·`publicCheck`·`schedule`·`users`) | 무료(Hobby) 플랜은 배포당 함수 수 상한이 12개로 알려져 있다. 그렇다면 **이미 꽉 찼고 새 API 파일 하나로 배포가 실패한다** | ops: 현재 플랜과 상한 (대화 기록 기획 담당 분배 3(a)와 같은 항목) |
| 업무용 사용 | 무료 플랜 | Vercel 무료 플랜은 개인·비상업 용도 조건이 있는 것으로 알고 있다. 사내 실무자 전체 서비스가 해당되는지 | ops: 약관 확인, 상위 지시자 결정 D6 |
| Upstash Redis | 무료 1개 DB (256MB, 월 50만 명령) | 계정·잠금·호출 횟수·대화 기록이 같은 DB. 넘으면 로그인이 함께 멈춤 | 계산·점검은 **대화 기록 기획 2절**을 따른다. 상용화로 사용자가 늘면 그 표의 B·C 경우를 다시 계산 |
| Gemini (배포 챗봇·AI 수정) | 환경변수 키 하나 | 사용자가 늘면 분·일 한도에 걸리고, 무료 등급이면 입력 내용 취급 조건 확인이 필요 | ops: 키의 요금 등급·한도 |

## 3. 이번 범위 / 범위 밖

이 기획서의 "이번 범위"는 **상용화(전체 공개) 전에 끝낼 것**이다.

**이번 범위 (상용화 전)**

1. 수정 제안 PR 앞에 서버 공개 검사 추가 (차단 수준은 D2).
2. 배포본 이름 목록 검사 — Vercel 환경변수로 목록 내용 읽기 (D3).
3. 작성자 이름 가림 — PR 본문 첫 줄과 `updatedBy` 에 가린 표기 (D4).
4. 저장소 전략 결정 (D1). A가 아니면 해당 작업을 별도 기획으로.
5. 로그인 잠금 — IP 기준 상향, 관리자 "잠금 풀기" (기존 `api/users.ts` 에 붙임, 새 함수 파일 없음).
6. 제안 목록 — 허브 PR만 골라 대기 중은 빠짐없이 읽기 (승인 관리·내 요청 공통).
7. 전체 하루 PR 상한 (모든 계정 합계).
8. 운영 확인 — Vercel 플랜·함수 수·약관, Gemini 키 등급, Upstash 사용량 재계산.
9. 운영 안내 — 승인자 명단·머지 전 점검표, 임시 비밀번호 전달·CSV 폐기, 이름 목록 갱신 주기, "섹션 추가·삭제·이동은 요청으로" 안내, `writing.md`·`docs/accounts.md` 정정.
10. 시범 운영 — 한 팀 정도로 먼저 열기 (D9).

**범위 밖 (이유)**

| 항목 | 이유 |
| --- | --- |
| 문서 삭제·이름 바꾸기·이동 화면·API | 새 PR 종류와 승인 화면 구분, 링크 깨짐 검사가 함께 필요해 크다. 상용화 직후 2단계로 |
| 서브메뉴를 화면에서 추가 | 메뉴 정의가 코드 5곳에 있어 먼저 한 파일로 모으는 구조 작업이 필요하다. 그전에는 요청 → 개발자 PR로 충분하다 |
| 챗봇 삭제·이동 초안 | 위 삭제·이동이 먼저다 |
| 편집자·승인자 role, 허브 안 승인 버튼 | 승인은 지금 GitHub 권한이 맡는다. role만 늘리면 허브와 GitHub 권한이 갈라진다. 운영으로 먼저 맞춘다 |
| GitHub App 전환 | 토큰 구조를 바꾸는 일이라 환경·배포 전반이 바뀐다. 한도 문제가 실제로 보이면 그때 |
| 마지막 로그인·퇴사자 일괄 정리·계정 삭제 | 수백 명이 된 뒤에 필요하다. 시범 운영 중엔 중지로 충분하다 |
| 새 문서 코드 중복 방지 | 동시에 같은 서브메뉴에 두 건이 드물다. 승인자 점검표로 먼저 막는다 |
| 대화 기록(저장·조회·한도) | `docs/plan/2026-11-20-chat-history-log.md` 에서 다룬다 |
| 시스템 요청·시트 승격 기록의 공유 저장 | 브라우저 메모리에만 있는 문제는 문서 기여와 별개라 따로 기획 |

## 4. 수용 기준

각 문장은 배포 허브(Production 또는 같은 설정의 Preview)에서 확인한다.

**공개 위험**

1. 배포 허브에서 화면을 거치지 않고 `/api/proposeEdit` 에 비공개 이름 목록에 있는 이름을 넣어 보내면, PR이 열리지 않고 400 `code:'public-leak'` 가 온다. 새 브랜치도 생기지 않는다.
2. 배포 허브에서 `/api/publicCheck` 응답의 `namesChecked` 가 `true` 다 (D3에서 환경변수 안으로 정한 경우).
3. 비공개 이름 목록의 내용이 저장소의 어떤 파일에도, 함수 로그에도 나타나지 않는다 (로그에는 `name=1` 같은 건수만).
4. 이름이 "홍길동"인 계정으로 새 문서와 수정 제안을 하나씩 올리면, 두 PR의 본문 첫 줄과 파일의 `updatedBy` 가 모두 가린 표기(D4에서 정한 형식)이고 "홍길동" 세 글자는 PR 어디에도 없다.
5. 모든 계정의 하루 PR 합계가 정한 상한을 넘으면 다음 제출은 429가 되고, 화면은 "오늘 허브 전체 제출 수를 넘었다"는 뜻의 한국어 문구를 보인다.

**계정**

6. 같은 IP에서 서로 다른 아이디로 30번 틀린 직후에도, 올바른 비밀번호를 가진 다른 계정은 로그인된다 (상향한 한도 이내라면).
7. 관리자가 계정 관리에서 "잠금 풀기"를 누르면 그 아이디는 10분을 기다리지 않고 바로 로그인된다.
8. `api/` 폴더의 파일 수가 이 작업 전과 같다 (새 배포 함수 파일 없음).

**승인 흐름**

9. 허브가 만든 대기 중 PR이 51건 이상이어도 승인 관리의 "대기 중" 목록에 모두 보인다.
10. 개발 PR(허브가 만들지 않은 브랜치)은 승인 관리·내 요청 어디에도 보이지 않는다 (지금과 같음).

**운영**

11. 운영 메모에 Vercel 플랜 이름, 함수 수 상한, 업무용 사용 가능 여부, Gemini 키 등급이 확인 날짜와 함께 적혀 있다.
12. `지식/guide/writing.md` 의 서브메뉴 id 목록이 `server/knowledge.ts` `DOC_SUBCATEGORIES` 와 글자까지 같다.
13. `docs/accounts.md` 에 "수정 제안 기록은 브라우저 메모리에만"이라는 문장이 없고, 승인은 GitHub 머지로 한다는 문장이 있다.
14. 이용 안내 문서 목록에서 3클릭 안에 "새 분류 추가·문서 삭제·이동은 이렇게 요청하세요" 안내에 닿는다.
15. 승인자 점검표(머지 전 이름·금액·작성자 표기·문서 코드 중복 확인)가 운영 메모에 있고, 승인자 명단(GitHub 쓰기 권한자)이 계정 관리의 관리자 명단과 맞춰져 있다.

## 5. 담당 분배 (단계별 실행안)

### 0단계 — 상위 지시자 결정 (6절 D1~D9)

D1(저장소)·D2(수정 제안 차단 수준)·D3(배포본 이름 목록)·D4(작성자 표기)는 1단계 개발 전에 정해야 한다. 나머지는 1단계와 함께 진행해도 된다.

### 1단계 — 기획·확인 (병렬 가능)

| 담당 | 할 일 | 산출물 | 병렬 |
| --- | --- | --- | --- |
| ops | (a) Vercel 플랜·함수 수 상한·업무용 약관 확인 (b) Gemini 키 등급·한도 (c) Upstash 사용량을 상용화 인원으로 다시 계산 — 방식은 대화 기록 기획 2절 (d) 비공개 이름 목록 갱신 담당·주기 정하기 | 운영 메모 | 혼자 병렬 가능. (a)는 대화 기록 기획의 같은 항목과 한 번에 |
| requests-planner | (a) 작성자 가림 형식과 "내 요청" 구분 방법(이름 글자 대신 아이디 기준으로 고를지) (b) 수정 제안 차단 시 문구 (c) 잠금 풀기·전체 상한 안내 문구 (d) 승인자 점검표 (e) 상용화 후 삭제·이동 제안의 상태·권한·문구 초안 | `docs/sections/requests-rollout.md` | ops와 병렬 |
| wiki-ux | "섹션 추가·삭제·이동 요청" 안내가 놓일 자리(이용 안내 목록·문서 화면), 상용화 후 삭제·이동 진입점 설계 | `docs/ux/` | 위와 병렬 |
| chatbot-planner | 지금 규약(삭제·이동은 `none`) 유지 확인. 안내 문장 끝에 "요청 방법" 링크를 붙일지 정하기. 상용화 후 `delete` 초안 규약 초안 | `server/assistant-prompt.md` 변경안(반영은 2단계 뒤) | 위와 병렬 |

### 2단계 — 서버 (dev-server, 1단계 requests-planner 산출물 뒤)

| 할 일 | 파일 |
| --- | --- |
| 수정 제안 서버 공개 검사 (D2 수준), 로컬 중계에도 같은 검사 | `server/github.ts` `createEditPR`, `server/publicCheck.ts`, `server/cliBridge.ts` |
| 배포본 이름 목록 환경변수 읽기 (D3) | `server/env.ts`, `server/publicCheck.ts` |
| 작성자 가림 (D4) — PR 본문·`updatedBy` | `server/github.ts` |
| IP 잠금 한도 조정, 관리자 잠금 풀기 (PATCH 확장) | `server/accounts.ts`, `api/users.ts` |
| 전체 하루 PR 상한 | `server/guard.ts` |
| 제안 목록 — 허브 브랜치만, 대기 중은 끝까지 | `server/github.ts` `listProposalPrs` |

- **새 `api/` 파일을 만들지 않는다** (함수 수 상한).
- `server/cliBridge.ts` 는 대화 기록 작업이 함께 쓰는 파일이다. 대화 기록의 서버 쪽 남은 작업이 있으면 **그 PR 머지 뒤**에 시작한다.

### 3단계 — 화면 (dev-front, 2단계 머지 뒤)

| 할 일 | 파일 |
| --- | --- |
| 수정 제안 차단 결과 표시(걸린 줄), 전체 상한 429 문구 | `src/pages/ProposeEdit.tsx`, `src/lib/proposeEdit.ts` |
| 계정 관리 "잠금 풀기" 버튼 | `src/pages/Accounts.tsx`, `src/lib/auth.ts` |
| 내 요청 구분 방식 변경(1단계 결정 따라) | `src/pages/MyRequests.tsx` |

- 대화 기록 관리자 화면(dev-front)과 사이드바·`App.tsx` 를 함께 건드릴 수 있다. **같은 파일이면 동시에 돌리지 않는다.**

### 4단계 — 운영 반영·시범 (ops, 3단계 뒤)

- 안내 문서 정정(`지식/guide/writing.md`, `지식/guide/propose.md`, `docs/accounts.md`), 요청 안내 문서.
- Vercel 환경변수(이름 목록) 넣고 재배포 → 수용 기준 1~15 점검.
- 시범 팀 계정 일괄 발급 → 2주 운영 → 잠금·한도·제안 수 보고.

### 5단계 — 상용화 후 (차례로)

1. dev-server → dev-front: 삭제 PR·이동 PR(제목·서브메뉴·적용 상품 변경), 승인 목록에 종류 표시, 링크 깨짐 검사.
2. dev-front + dev-server: 메뉴 정의를 한 파일로 모으기(①②④⑤가 같은 원본을 읽게) → 그 뒤 "섹션 추가"는 그 파일 하나를 고치는 PR로.
3. chatbot-planner → dev-server → dev-front: 챗봇 `delete`·`move` 초안.
4. dev-server: 마지막 로그인 시각, 일괄 중지. 새 문서 코드를 열린 PR까지 보고 채번.
5. ops + dev-server: GitHub App 전환 검토.

```
0 결정 ─┬─ 1 ops ───────────────┐
        ├─ 1 requests-planner ──┼─ 2 dev-server ── 3 dev-front ── 4 ops(시범) ── 5 상용화 후
        ├─ 1 wiki-ux ───────────┤
        └─ 1 chatbot-planner ───┘
```
