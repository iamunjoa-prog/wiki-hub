# 챗봇 대화 기록 저장 — 관리자 개선용 기록과 내 대화 기록

작성 `plan-pm` · 2026-11-20
상위 지시자 확정 조건 (이 문서는 아래 다섯 가지를 바꾸지 않는다)

1. 주목적은 **관리자가 기록을 보고 챗봇을 개선하는 것**이다. 함께 쓰는 목적은 ② 위키 문서 빈틈 찾기(근거 문서 없이 답한 질문), ⑤ 엔진 비교(엔진·응답 시간·실패 여부·모드), ⑥ 사용자 본인 다시 보기, ⑦ 문의가 왔을 때 사실 확인이다.
2. ⑧ 답변 평가 버튼(좋아요/싫어요)은 2차로 미루고 이번 범위 밖에 둔다.
3. 저장소는 계정 저장에 이미 쓰는 Upstash Redis REST(`server/accounts.ts` 의 `redis()`, `KV_REST_API_URL`/`KV_REST_API_TOKEN`)를 함께 쓴다. 기준은 **무료 플랜**이다. 용량 256MB, 월 50만 명령, 데이터베이스 1개.
4. 공개 저장소다. 기록은 GitHub에 절대 올리지 않는다. Redis에만 두고, 전체 기록은 관리자만 본다.
5. 저장에 실패해도 챗봇 답변은 그대로 나가야 한다.

| 누가 | 어떤 상황에서 | 무엇을 못 하나 |
| --- | --- | --- |
| 허브 관리자 | 챗봇 답이 엉뚱하다는 말을 듣고 대화 규약(`server/assistant-prompt.md`)이나 위키 문서를 고치려 한다 | 실무자가 실제로 무엇을 물었고 챗봇이 어떻게 답했는지 볼 수 없다. 화면 메모리에만 있다가 새로고침하면 사라지고, 서버도 남기지 않는다. 고칠 대상을 감으로 고른다 |

핵심은 대화 한 턴의 **질문·답·근거·엔진·시간·결과**가 어디에도 남지 않는다는 점이다. 이번 일은 이 기록을 남기는 것이다. 단 다음 세 가지 선 안에서 한다. (1) 답 경로를 막지 않는다. (2) 무료 한도 안에 머물고, 같은 저장소를 쓰는 로그인 기능을 위협하지 않는다. (3) 관리자 화면 밖으로 원문이 나가지 않는다.

## 이번 범위 / 범위 밖

### 이번 범위

1. **턴 기록 저장** — 서버 `/api/ask` 한 번(= 엔진 한 번 시도)마다 기록 1건을 Redis에 남긴다. 배포와 로컬이 같은 공용 모듈을 쓴다.
2. **대화 묶음 ID** — 화면이 대화 세션 ID(`chatId`)와 턴 ID(`turnId`)를 요청에 실어 보낸다. 엔진을 넘겨 가며 여러 번 시도한 것도 한 턴으로 묶어 볼 수 있다.
3. **90일 자동 삭제**와 **하루 저장 상한** — 무료 한도와 계정 기능을 지킨다.
4. **조회 API** — 관리자 전체 조회(필터·사용량), 본인 조회, 저장 상태 조회.
5. **화면** — 관리자 "대화 기록" 화면, 사용자 "내 대화 기록" 화면, 챗봇 창의 고지 한 줄. 화면 상세 설계는 wiki-ux가, 반영은 dev-front가 맡는다.
6. **개선 활용 절차** — 관리자가 기록을 보고 대화 규약·위키를 고치는 주기와 방법(chatbot-planner).
7. **운영 점검** — 한도·용량 월 점검, 실무자 PC에 Redis 토큰을 배포하지 않는 원칙(ops).

### 범위 밖

| 항목 | 이유 |
| --- | --- |
| 답변 평가 버튼(좋아요/싫어요) | 상위 지시자 확정 조건 2. 2차에 이 기록의 `turnId` 에 붙인다 |
| 기록을 대화창으로 다시 불러와 이어서 묻기 | ⑥은 "다시 보기"까지다. 이어 묻기는 이력 재구성·엔진 상태까지 얽혀 범위가 커진다 |
| 내보내기(CSV·엑셀·전체 복사)·공유 링크 | 원문에 제휴사명·금액이 들어 있을 수 있다. 관리자 화면 밖으로 나가지 않게 한다 (보안 절) |
| 리포트 본문(markdown) 원문 저장 | 길고(수 KB~수십 KB) 용량을 크게 쓴다. 제목·요약·근거·빈칸만으로 개선 목적을 충족한다. 결정 필요 D3 |
| 브라우저 안의 규칙 기반 답(`answer()`) 본문 저장 | 서버를 거치지 않는다. "모든 엔진 실패 → 규칙 기반으로 답함"은 같은 턴의 실패 기록들로 알 수 있다. 결정 필요 D5 |
| 앞 대화 이력(`history`) 저장 | 같은 `chatId` 의 앞 턴 기록으로 다시 맞출 수 있다. 중복 저장하면 용량이 몇 배가 된다 |
| 로컬 허브 기록을 배포 저장소로 보내는 수집 API | 로컬 허브에는 로그인이 없다. 보내는 쪽을 확인할 장치(PC별 기록 키 등)를 새로 설계해야 한다. 결정 필요 D1, 2차 후보 |
| 실무자 PC `.env.local` 에 Redis 토큰 넣기 | 토큰 하나로 계정 해시·모든 기록을 읽고 지울 수 있다. 보안 절 참고 |
| 관리자 열람 감사 로그(누가 언제 봤나) | 1차는 관리자 소수다. 필요해지면 2차에 둔다 |
| 기록 기반 자동 통계 리포트·대시보드 차트 | 1차는 목록·필터·건수까지 한다. 차트는 쓰임새를 본 뒤 정한다 |
| 유료 플랜 전환·별도 DB | 무료 플랜이 기준이다. 넘을 조짐이 보이면 ops가 보고하고 그때 정한다 |

## 1. 저장 단위와 항목

### 저장 단위

- **기록 1건 = 서버 `/api/ask` 요청 1회 = 엔진 1회 시도**다. 화면이 Claude 실패 → Gemini 성공으로 넘겼다면 같은 `turnId` 로 2건이 생긴다.
- 서버에 남기는 이유는 두 가지다. (1) 사용자 확인(로그인 ID)을 서버가 쿠키로 하므로 화면이 보낸 값을 믿지 않아도 된다. (2) 엔진·응답 시간·실패 코드·근거 경로를 서버가 가장 정확히 안다.
- **턴** = 같은 `turnId` 의 기록 묶음, **대화 세션** = 같은 `chatId` 의 턴 묶음이다. 관리자 화면은 턴 단위로 보여 주고, 펼치면 시도별 기록이 보인다.

### 화면이 새로 보내는 값 (요청 본문 추가, 모두 선택)

| 필드 | 만드는 곳 | 규칙 |
| --- | --- | --- |
| `chatId` | `AppStore` 가 처음 열릴 때 `crypto.randomUUID()` 로 한 번 만든다. 새로고침하면 새 값이다 | `^[a-zA-Z0-9-]{8,64}$` 이 아니면 서버가 버리고 `null` 로 저장한다 |
| `turnId` | 사용자 말풍선 ID. 한 질문의 엔진 넘기기 시도들이 같은 값을 쓴다. 「짧게 답 받기」·「리포트로 자세히 받기」로 다시 물으면 새 턴이다 | 같은 규칙. 유일성은 `chatId` 와 함께 볼 때만 보장된다 |

- `parseAskInput` 은 지금 알 수 없는 필드를 버린다(`server/knowledge.ts:53-74`). 그래서 이 두 필드를 추가해도 구버전 화면·구버전 서버와 서로 깨지지 않는다.
- **로그인 ID는 본문으로 받지 않는다.** 배포는 `guard.account.loginId`, 로컬은 결정 필요 D1에 따른다.

### 기록 항목 (JSON 한 덩어리)

| 키 | 내용 | 비고 |
| --- | --- | --- |
| `id` | 서버가 만든 기록 ID (`randomBytes` 기반, 예: `cl_` + 16자) | 화면 `newId` 는 전역에서 유일하지 않아 쓰지 않는다 |
| `chatId`, `turnId` | 위 표 | 없으면 `null` |
| `loginId` | 배포: 계정 아이디. 로컬: D1 결정에 따름 | 이름·팀은 저장하지 않는다. 화면에서 `listAccounts` 로 붙인다 |
| `where` | `'deploy'` \| `'local'` | |

### 1턴 크기 추정

한글 1자 = UTF-8 3바이트로 계산했다. 경로·URL은 영문이다.

| 구성 | 일반 답 (보통) | 리포트 (보통) | 실패 | 최악 (상한까지 꽉 참) |
| --- | --- | --- | --- | --- |
| 메타(ID·시각·엔진·모드·상태 등) | 0.35KB | 0.35KB | 0.35KB | 0.4KB |
| 질문 | 80자 ≈ 0.25KB | 120자 ≈ 0.35KB | 0.25KB | 2,000자 ≈ 6KB |
| 답 | 400자 ≈ 1.2KB | 요약 300자 ≈ 0.9KB | 없음 | 1,500자 ≈ 4.5KB |
| 근거 경로 | 2개 ≈ 0.1KB | 5개 ≈ 0.2KB | 없음 | 10개 ≈ 0.5KB |
| 리포트 부가(외부 출처·검색어·빈칸) | 없음 | ≈ 1.5KB | 없음 | ≈ 3KB |

계획용 평균은 **2.5KB/건**으로 잡는다. 리포트 비중이 작고 실패 기록이 섞이기 때문이다.

### Redis 키 구조 초안

접두어는 `hub:chatlog:` 로 계정 키와 나눈다. 최종 구조는 dev-server가 정하되 아래 조건을 지킨다. **기록 1건 저장 = 명령 6개 이하, HTTP 1회(pipeline)**, **목록 한 쪽 조회 = 명령 5개 이하.**

| 키 | 형태 | 값 | 만료 |
| --- | --- | --- | --- |
| `hub:chatlog:rec:<id>` | STRING | 기록 JSON | `SET … EX 7776000` (90일) |
| `hub:chatlog:all` | ZSET | member=`id`, score=시각(ms) | 키 자체는 만료 없음. 날마다 첫 저장 때 `ZREMRANGEBYSCORE` 로 90일 지난 항목을 지운다 |
| `hub:chatlog:user:<loginId>` | ZSET | 같음 | 저장할 때마다 `EXPIRE 7776000`. 오래된 항목은 본인이 조회할 때 정리한다 |
| `hub:chatlog:flag:nosource` | ZSET | 근거 없이 답한 기록 | `all` 과 같은 방식으로 정리 |
| `hub:chatlog:flag:fail` | ZSET | 실패·취소 기록 | 같음 |
| `hub:chatlog:n:<YYYY-MM-DD>` | STRING(정수) | 그날 저장 시도 건수(상한 판정과 사용량 표시에 함께 씀) | 첫 `INCR` 때 `EXPIRE` 100일 |
| `hub:chatlog:over:<YYYY-MM-DD>` | STRING(정수) | 그날 상한을 넘어 내용 없이 건수만 센 수 | 같음 |

- 엔진 필터는 `all` 이나 `flag:*` 에서 ID를 받아 `MGET`(명령 1개)으로 읽은 뒤 서버에서 거른다. 한 쪽은 50건, 한 번에 읽는 상한은 200건이다. 엔진별 색인은 실측해 보고 느리면 추가한다.
- 기록 본문이 먼저 만료되고 색인에 ID만 남은 경우는 `MGET` 결과가 `null` 이 된다. 읽을 때 건너뛰면 된다.
- 저장 1건의 명령은 `INCR n` + `SET rec EX` + `ZADD all` + `ZADD user` + `EXPIRE user` 로 5개다. 근거 없음·실패 기록이면 `ZADD flag` 가 하나 늘어 6개가 된다. 그날 첫 저장이면 `EXPIRE n` 과 `ZREMRANGEBYSCORE` 정리가 더 붙는데, 하루 몇 번뿐이라 무시한다.
- 지금 `redis()` 는 명령마다 HTTP를 한 번씩 쓴다. Upstash REST의 pipeline 엔드포인트로 한 번에 보내는 도우미가 필요하다. pipeline으로 보내도 명령 수는 그대로 센다.

## 2. 보관 기한과 무료 한도 계산

### 보관 기한

- 기본 **90일**이다. 기록 본문은 `SET … EX 7776000` 으로 Redis가 스스로 지운다. 지우는 작업을 따로 돌리지 않는다.
- 색인 ZSET은 항목별 만료가 없으므로 위 정리 규칙으로 지운다. 화면 기간 필터의 최대값도 90일이다.
- 보관 일수는 환경변수 `HUB_CHATLOG_DAYS`(기본 90)로 바꿀 수 있게 둔다. 바꿔도 이미 저장된 기록의 만료는 그대로다.

### 하루 저장 상한 (계정 기능 보호)

- 환경변수 `HUB_CHATLOG_DAILY_CAP`(기본 **500건/일**, 결정 필요 D2)을 둔다. 그날 `n` 이 상한을 넘으면 기록 본문을 저장하지 않고 `over` 건수만 올린다.
- 관리자 화면 사용량 칸에 "오늘 상한을 넘어 n건은 내용 없이 건수만 남았습니다"가 보인다.

### 용량 계산 (평균 2.5KB/건, 엔진 넘기기로 시도 수 ×1.1)

| 경우 | 하루 질문 | 90일 보관 기록 수 | 기록 용량 | 256MB 대비 |
| --- | --- | --- | --- | --- |
| A. 30명 × 하루 10건 (근무일 22일/월) | 300 | 300×1.1×(22/30×90) ≈ 21,800 | ≈ 55MB | 21% |
| B. 50명 × 하루 15건 | 750 | 상한 500 적용 시 최대 500×(22/30×90) ≈ 33,000 | ≈ 83MB | 32% |
| C. 상한까지 매일 꽉 참 (주말 포함 90일) | 500 이상 | 45,000 | ≈ 113MB (최악 평균 4KB면 180MB) | 44% (70%) |
| 계정·잠금·호출 제한 키 | 계정 수백 개 기준 | | 1MB 미만 | 무시 |

상한 500건이면 최악에도 256MB 안에 들고 계정 기능이 쓸 자리가 남는다. 상한이 없다면 100명이 하루 20건을 물을 때 90일 동안 ≈ 290MB가 되어 한도를 넘긴다.

### 명령 수 계산 (월 50만)

| 경우 | 월 질문 시도 | 이미 쓰는 명령 (질문당 ≈3) | 기록 저장 (건당 ≈5.5) | 조회 (관리자·본인) | 월 합계 | 50만 대비 |
| --- | --- | --- | --- | --- | --- | --- |
| A | 300×22×1.1 ≈ 7,300 | ≈ 22,000 | ≈ 40,000 | ≈ 2,000 | ≈ 64,000 | 13% |
| B | 750×22×1.1 ≈ 18,200 | ≈ 55,000 | 상한 500 적용 ≈ 11,000건 → ≈ 60,000 (+ 상한 초과분 `INCR` 2개씩 ≈ 14,000) | ≈ 3,000 | ≈ 132,000 | 26% |
| C (상한 꽉 참, 30일) | 15,000 이상 | ≈ 45,000 이상 | ≈ 83,000 | ≈ 3,000 | ≈ 131,000 이상 | 26% 이상 |

- 조회는 한 쪽에 명령 5개 이하로 잡았다. 관리자가 하루 20쪽, 실무자 30명이 하루 1번 본다고 계산했다.
- 이 외에 페이지 열 때마다 `/api/auth` 가 `GET` 1회를 쓴다. 기록 저장이 없어도 쓰는 양이라 표에서 뺐다. ops가 월 점검 때 Upstash 콘솔의 실제 명령 수와 맞춰 본다.
- 한도에 가까워지는 신호(월 35만 = 70%)가 보이면 ops가 PM 데스크에 알린다. 그 뒤 상한을 낮출지, 보관 일수를 줄일지, 유료 전환할지는 상위 지시자가 정한다.

## 3. 답 경로를 막지 않는 방식

| 규칙 | 내용 |
| --- | --- |
| 절대 throw 하지 않는다 | 공용 함수 `recordChatTurn(…)` 은 안에서 모든 오류를 잡는다. 실패하면 `console.warn('[chatlog] 저장 실패 — <분류>')` 한 줄만 남기고 끝낸다. 질문·답 원문은 로그에 쓰지 않는다 |
| 기다리는 시간 상한 | 저장 요청에 **1초** 제한을 둔다(`AbortSignal.timeout`). 넘으면 버린다 |
| 로컬 | 응답을 먼저 `res.end()` 하고 저장은 기다리지 않는다(fire-and-forget). vite 프로세스는 계속 살아 있으므로 끝까지 간다 |
| 배포 | Vercel은 응답을 돌려준 뒤 함수가 멈출 수 있다. 1차는 **응답을 만든 뒤 저장을 최대 1초까지 기다리고** 돌려준다. 답은 이미 나와 있으므로 사용자 체감은 최대 1초 늘어난다. `@vercel/functions` 의 `waitUntil` 로 응답 뒤 저장하는 방식은 의존성 추가라서 결정 필요 D6에 둔다 |
| 설정이 없으면 건너뛴다 | `readRedis(env)` 가 `null` 이면 아무것도 하지 않는다. 경고도 남기지 않는다(로컬 허브는 대부분 이 상태다). 로컬은 `hubEnv` 를 넘긴다 |
| 계정이 없으면 건너뛴다 | 배포에서 `guard.account` 가 `null`(계정 기능 꺼진 데모)이면 저장하지 않는다. 로컬은 D1에 따른다 |
| 저장 실패가 화면에 보이지 않는다 | 응답 본문·상태 코드는 저장 성공 여부와 무관하게 지금과 같다. API 계약(`AskResponse`)은 바뀌지 않는다 |
| 상한 초과 | 위 "하루 저장 상한"대로 건수만 올린다 |

### 기록을 남기는 지점

| 지점 | 배포 `api/ask.ts` | 로컬 `cliBridge` | 기록 |
| --- | --- | --- | --- |
| 입구 거절(출처·크기·로그인·호출 횟수) | `guardApi` 실패 | `readGuardedBody` 실패 | 남기지 않는다 (턴이 아니다) |
| 입력 형식 오류 400 | `parseAskInput` 실패 | 같음 | 남기지 않는다 |
| 키 없음 503·번들 누락 500 | 있음 | 키 없음 | `status:'fail'`, `errorCode:'config'` |
| 리포트 안내 | `reportUnavailable()` | Gemini에 리포트성 질문 | `status:'ok'`, `mode:'report-unavailable'` |
| 일반 답 성공 | `qaResponse` | 같음 | `status:'ok'`, `mode:'qa'` |
| 리포트 성공 | 없음 | `reportResponse` | `status:'ok'`, `mode:'report'` |
| 엔진 실패 502·리포트 시간 초과 504 | `geminiErrorBody` | 같음 | `status:'fail'`, `errorCode` |

**취소의 한계** — 배포(Vercel)에서는 화면이 요청을 끊어도 함수가 Gemini 답을 끝까지 받아 `ok` 로 기록될 수 있다. 1차는 이 차이를 받아들이고 관리자 화면 도움말에 한 줄로 적는다. Gemini 제한 시간은 90초라 취소가 드물다.

## 4. 공용 모듈 위치 — 로컬과 배포가 같은 규칙

- **새 파일 `server/chatLog.ts`** 에 기록 모양(타입), 자르기 규칙(1,500자·300자·개수 상한), `noSource` 판정, 키 이름, 저장 함수 `recordChatTurn`, 조회 함수(`listChatLog`, `listMyChatLog`, `chatLogUsage`)를 둔다. `api/ask.ts`·`api/chatlog.ts`·`server/cliBridge.ts` 가 모두 이 파일을 import 한다.
- `server/knowledge.ts` 에 두지 않는 이유가 있다. 이 파일은 입출력 없는 순수 규칙(스키마·검사·판정)만 모아 둔 곳이고, 프롬프트·스키마 공유 때문에 import 하는 곳이 많다. 네트워크 저장 코드를 섞으면 영향 범위가 커진다. `knowledge.ts` 에는 **`parseAskInput` 이 `chatId`·`turnId` 를 받는 것만** 추가한다.
- Redis 호출은 `server/accounts.ts` 의 `readRedis`·`redis` 를 export 하거나 `server/redisStore.ts` 로 떼어 함께 쓴다. 저장소 연결 코드를 두 벌 두지 않는다. pipeline 도우미도 같은 곳에 둔다. 어느 쪽으로 할지는 dev-server 재량이다. 떼어 낸다면 계정 기능이 그대로 도는지 회귀 확인을 PR에 적는다.
- `.env.example` 에 `HUB_CHATLOG_DAYS`·`HUB_CHATLOG_DAILY_CAP` 를 설명과 함께 추가한다. `KV_REST_API_*` 주석 옆에는 "실무자 PC에는 넣지 않습니다" 한 줄을 붙인다.

## 5. 조회 화면 — 흐름과 요구 (상세 설계는 wiki-ux)

### 조회 API (배포 함수는 한 파일)

| 요청 | 권한 | 돌려주는 것 |
| --- | --- | --- |
| `GET /api/chatlog?view=status` | 로그인한 누구나 (계정 기능 꺼짐이면 누구나) | `{ enabled, retentionDays }`. 저장이 켜져 있는지만 알려 준다. 고지 문구를 보일지 이걸로 정한다 |

| `GET /api/chatlog?view=usage` | **admin** | 일별 저장 건수·상한 초과 건수(최근 90일), 추정 용량, 이번 달 추정 명령 수 |
| `DELETE /api/chatlog?id=` | **admin** (D4 결정에 따름) | 기록 1건 삭제 |

- 배포 함수는 `api/chatlog.ts` **한 파일**로 둔다. `api/` 에 이미 11개가 있어 플랜별 함수 수 제한에 걸릴 수 있기 때문이다(ops가 현재 Vercel 플랜의 제한을 확인).
- 로컬 `cliBridge` 에도 같은 경로를 둔다. 로컬은 로그인이 없으므로 `view=status` 만 응답한다(`enabled` 는 Redis 설정 유무). `mine`·`all` 은 "배포 허브에서 볼 수 있어요" 안내로 응답한다.
- 모든 응답에 `Cache-Control: no-store` 를 붙인다. 한 번에 200건을 넘겨 돌려주는 경로는 만들지 않는다(대량 내려받기 차단).
- 기간 필터는 최대 90일, 기본 7일이다.

### 관리자 "대화 기록" 화면 흐름

1. 관리자 메뉴(승인 관리·계정 관리와 같은 묶음)에서 "대화 기록"에 들어간다. member에게는 메뉴가 보이지 않고, 주소를 직접 열어도 "관리자만 볼 수 있어요"가 나온다.
2. 위쪽에 **사용량 띠**가 있다. 오늘 저장 건수 / 하루 상한, 최근 90일 저장 건수, 추정 용량(MB) / 256MB, 이번 달 추정 명령 수 / 50만. 70%를 넘으면 경고색으로 바뀐다.
3. **필터**: 기간, 사용자(계정 목록에서 고름), 엔진, 모드(일반/리포트/리포트 안내), 결과(성공/실패/취소), 「근거 없이 답한 것만」 체크.
4. **목록**은 턴 단위 한 줄이다. 시각 · 사용자 이름 · 질문 앞부분 · 최종 엔진 · 결과 · 근거 수(0이면 표시) · 응답 시간. 엔진을 넘겼으면 "Claude 실패 → Gemini"처럼 보인다.
5. 줄을 펼치면 질문 전문, 답(잘렸으면 "앞 1,500자만 저장됨"), 근거 문서(위키 문서로 가는 링크, 위키에 없는 경로는 회색), 리포트면 제목·요약·빈칸·외부 출처가 보인다. "같은 대화 보기"를 누르면 같은 `chatId` 의 턴이 시간순으로 나온다.
6. **내보내기·전체 복사·인쇄용 보기 버튼은 두지 않는다.**

### 사용자 "내 대화 기록" 화면 흐름

1. 진입 위치는 wiki-ux가 정한다. 후보는 "내 요청" 화면의 탭, 또는 챗봇 창 머리의 "지난 대화" 링크다.
2. 본인 기록만 날짜별로 묶어 최신순으로 보인다. 질문과 답, 근거 문서 링크가 나온다. 엔진·응답 시간·실패 코드 같은 운영 정보는 보이지 않는다(실패는 "답을 받지 못함" 한 줄).
3. 맨 위에 "최근 90일 대화만 보관돼요." 한 줄이 있다.
4. 질문·답 복사는 한 턴씩만 된다(일반 텍스트 선택은 막지 않는다). 전체 내보내기는 없다.
5. 로컬 허브에서 열면 "내 대화 기록은 배포 허브에서 볼 수 있어요." 안내만 보인다.

## 6. 사용자 고지 문구

dev-front가 반영한다. 최종 문구는 이 표를 기준으로 하되 wiki-ux가 위치를 정한다.

| 상황 | 챗봇 창 입력칸 아래 한 줄 |
| --- | --- |
| 배포 허브, 로그인함, 저장 켜짐 | **대화 내용은 챗봇을 고치는 데 쓰려고 90일 동안 저장돼요. 관리자와 같은 팀 계정을 쓰는 팀원이 볼 수 있어요.** (2026-11-20 팀 계정 결정으로 변경 — 상용화 검토 기획서 0-1절) |
| 배포 허브, 계정 기능 꺼짐(데모) | 문구 없음 (저장하지 않음) |
| 로컬 허브, 저장 꺼짐(실무자 PC 기본) | 문구 없음 (저장하지 않음) |
| 로컬 허브, 저장 켜짐(D1에서 관리자 PC 허용 시) | **이 PC의 대화는 챗봇을 고치는 데 쓰려고 90일 동안 저장돼요. 관리자만 볼 수 있어요.** |

- "저장 켜짐"은 `GET /api/chatlog?view=status` 의 `enabled` 로 판단한다. 응답이 없거나 실패하면 문구를 보이지 않는다. 이때 서버도 저장하지 못할 가능성이 크다.
- 첫 사용 때 별도 동의 창은 띄우지 않는다. 사내 업무 도구이고, 항상 보이는 한 줄로 알린다(결정 필요 D7).
- **로그인하지 않은 사용자** — 계정 기능이 켜진 배포에서는 `/api/ask` 가 로그인을 요구하므로 로그인 없이 묻는 경우가 없다. 계정 기능이 꺼진 배포에서는 저장하지 않는다. 로컬 허브는 D1에 따른다. 정리하면 **"누가 물었는지 모르는 기록은 남기지 않는다"** 가 원칙이다. 단 D1에서 관리자 PC 예외를 둘 때는 `loginId` 가 `local:<PC 표시명>` 인 기록이 남는다.

## 7. 개인정보와 공개 원칙

| 원칙 | 구체 규칙 |
| --- | --- |
| 저장소 밖으로 안 나간다 | 기록은 Upstash Redis에만 있다. `server/chatLog.ts` 는 `server/github.ts` 를 import 하지 않는다. 기록을 파일로 쓰는 코드도 없다(로컬 파일 포함) |
| 원문 그대로 저장되는 것을 전제한다 | 질문에 제휴사명·금액이 들어갈 수 있다. 저장할 때 가리지 않는다. 가리면 ⑦ 사실 확인이 안 된다. 대신 **보는 곳을 관리자 화면 하나로 막는다** |
| 내보내기·공유 금지 | CSV·엑셀·전체 복사·공유 링크·외부 전송 기능을 만들지 않는다. API는 한 번에 200건 넘게 돌려주지 않는다 |
| 개선 작업으로 옮길 때 | 기록에서 찾은 문제를 위키 수정 PR·`docs/`·이슈·커밋 메시지로 옮길 때는 **질문 원문을 붙이지 않고 경향으로 쓴다.** 예: "PPV 쿠폰 결재선 질문에 근거 없이 답한 사례가 이번 주 여러 건". 위키 반영은 기존 공개 검사(`publicCheck`)를 거친다 |
| 로그에 원문 금지 | 서버 로그(`console.*`)에 기록 원문·Redis 응답 본문을 쓰지 않는다. 로컬 터미널의 기존 `[cli-bridge] … · <질문>` 줄은 이 PC 터미널에만 보이므로 이번 범위에서 바꾸지 않는다 |
| Redis 토큰 | 실무자 PC의 `.env.local`·설치 스크립트·허브 ZIP에 `KV_REST_API_*` 를 넣지 않는다. 토큰 하나로 계정 해시와 모든 기록을 읽고 지울 수 있다 |
| 계정 정보 최소화 | 기록에는 `loginId` 만 넣는다. 이름·팀은 조회할 때 계정 목록에서 붙인다. 계정이 지워져도 기록은 90일 뒤 사라진다 |
| 공개 저장소 문서 | 이 기획서와 후속 설계 문서·PR 설명에는 실제 질문 예시를 쓰지 않는다. 필요하면 지어낸 예시를 쓴다 |

## 수용 기준

### 저장

- 배포 허브에서 로그인한 계정으로 질문 1건을 보내면 `hub:chatlog:rec:*` 키 1개가 생긴다. 이 키의 TTL은 7,776,000초 이하이고 7,775,000초 이상이다(Upstash 콘솔 또는 `TTL` 명령).
- 그 기록에 `chatId`·`turnId`·`loginId`·`at`·`ms`·`engine`·`mode`·`intent`·`status`·`q`·`a`·`sources`·`noSource` 가 모두 있다.
- 같은 질문이 엔진을 넘겨 2번 시도되면 같은 `turnId` 로 기록 2건이 생기고, 앞의 것은 `status:'fail'` 과 `errorCode` 를 가진다.
- 2,000자 질문과 1,500자를 넘는 답은 질문 전문, 답 앞 1,500자, `aCut:true` 로 저장된다.
- 로컬 claude 리포트 1건의 기록에는 `report.title`·`summary`·`type`·`sources`·`gaps`·`chars` 가 있고, **markdown 본문이 없다.** 기록 JSON 크기는 5KB 이하다.
- 근거 경로가 빈 일반 답은 `noSource:true` 이고 `hub:chatlog:flag:nosource` 에 들어간다. `report-unavailable` 응답은 `noSource:false` 다.
- 기록 JSON 어디에도 오류 원문 메시지, `history`, 비밀번호 해시가 없다.
- 기록 1건 저장이 Upstash에 HTTP 1회, 명령 6개 이하로 간다(dev-server가 PR에 실측을 적는다).

### 답 경로 보호

- `KV_REST_API_URL` 을 틀린 주소로 바꾼 배포(또는 로컬)에서 질문하면 답이 지금과 같은 형식으로 오고, 응답 시간은 설정이 정상일 때보다 1.5초 넘게 늘지 않는다. 서버 로그에는 `[chatlog] 저장 실패` 한 줄만 있다.
- Redis 설정이 없는 로컬 허브(실무자 PC 기본)에서 질문하면 답이 지금과 같고, 터미널에 `[chatlog]` 로 시작하는 줄이 하나도 없다.
- 계정 기능이 꺼진 배포에서 질문하면 기록이 생기지 않는다.
- `/api/ask` 응답 본문과 상태 코드는 이번 작업 전후로 같다. 기존 수용 기준(리포트 모드 등)이 그대로 통과한다.
- 하루 상한을 3으로 낮춰 4번 물으면 4번째 질문의 답은 정상으로 오고, 기록은 3건, `over` 건수는 1이다.

### 조회·권한

- member 계정으로 `GET /api/chatlog?view=all` 을 부르면 403이고, 관리자 "대화 기록" 메뉴가 보이지 않는다.
- member 계정의 `view=mine` 결과에 다른 계정의 기록이 하나도 없다.
- 관리자가 「근거 없이 답한 것만」을 켜면 목록의 모든 줄이 근거 수 0이다.
- 관리자가 엔진 필터를 Gemini로 두면 목록의 모든 줄에 Gemini 시도가 들어 있다.
- 관리자 화면 사용량 띠의 오늘 건수가 `hub:chatlog:n:<오늘>` 값과 같다.
- 관리자 화면과 내 대화 기록 화면 어디에도 내보내기·전체 복사·공유 버튼이 없다.
- `view=all` 에 `limit=1000` 을 붙여도 응답은 200건 이하다.
- 로컬 허브에서 내 대화 기록을 열면 "배포 허브에서 볼 수 있어요" 안내가 보인다.

### 고지

- 저장이 켜진 배포에서 로그인하면 챗봇 창 입력칸 아래에 6절의 고지 문구가 보인다.
- 저장이 꺼진 환경(로컬 기본·데모 배포)에서는 문구가 보이지 않는다.

### 공개 원칙

- `git grep -n "chatlog" -- server/github.ts` 결과가 없다.
- 이번 작업의 PR·커밋·`docs/` 변경에 실제 사용자 질문 원문이 없다(리뷰에서 확인).
- `.env.example` 의 `KV_REST_API_*` 옆에 "실무자 PC에는 넣지 않습니다" 문구가 있다. 설치 스크립트·허브 ZIP에 `KV_REST_API` 문자열이 없다(`git grep` 로 확인).

### 빌드

- `npm run build` 통과 (`tsc -b`, `tsc -p tsconfig.server.json`, `vite build`).
