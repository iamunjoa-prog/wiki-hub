### 이번 범위가 푸는 문제

| 누가 | 어떤 상황에서 | 무엇을 못 하나 |
| --- | --- | --- |
| 마케팅 실무자 | "영화 신작 프로모션 기획하려는데 카피 추천해줘"라고 물었다 | '프로모션'+'기획'이 진행 의도로 잡혀 "진행하려는 프로모션이 있으신가요?" 확인 칩이 먼저 뜬다. 대화 규약에도 "결과물 요청" 유형이 없어 엔진은 기획 상담 규칙(2줄 이내 방향 한 줄)으로 답한다. 정작 요청한 카피 후보는 받지 못한다. |
| 마케팅 실무자 | 다음 단계 칩에서 "카피 추천받기"를 눌렀다 | 앱이 "카피 방향을 추천해줘"를 대신 보내고, 엔진은 판단 요청 규칙(선택지 2~3개)으로 답한다. 바로 쓸 수 있는 카피 후보 형식(메인/서브, 비어 있는 값은 자리 표시)이 정해져 있지 않다. |
| 마케팅 실무자 | 월정액(PPM) 프로모션을 묻거나 상품 확인 칩에서 PPM 을 골랐다 | 허브는 PPM 안의 세부 상품을 구분하지 않는다. 회사가 주력으로 미는 B tv+ 는 쿠폰·이벤트 방식 표가 따로 있는데(`지식/promotion/schemes.md` "B tv+" 절), 허브는 B tv+ 인지 일반 TV 월정액인지 묻지 않아 B tv+ 기준 답을 받으려면 실무자가 직접 "B tv+"를 적어야 한다. |

### 4. 리포트 모드와의 관계

리포트 모드는 질문 신호 점수로 자동 진입한다(`src/lib/report.ts:20-46`, 서버 쪽 규칙과 짝). '인사이트' 한 단어는 1점, "추천…근거"는 1점이다. 결과물 요청 문장·추천 칩 문장은 지금 점수 규칙으로는 리포트로 넘어가지 않지만, 문구를 바꾸면 넘어갈 수 있다. 수용 기준에 회귀 확인으로 넣는다.

## 이번 범위 / 범위 밖

### 이번 범위

1단계 — 카피·구좌 요청은 되묻지 않고 바로 답하기 (C1·C2·C3)

1. 카피·노출 구좌·이벤트명을 **달라는** 발화를 판별한다(C1). 판별되면 진행 의도 확인 칩을 붙이지 않는다.
2. 대화 규약에 "결과물 요청" 유형과 출력 형식을 넣는다(C2). 근거 문서는 `promotion/copy-principles.md`·`copy-movie-ppv.md`·`copy-genre-frames.md`·`copy-verification.md`·`banner-specs.md`·`placements.md`·`playbook.md`.
3. 다음 단계 칩의 "카피 추천받기"·"노출 구좌 추천받기"가 보내는 문장을 결과물 요청으로 잡히는 문장으로 바꾼다.
4. 결과물 요청에 답한 뒤에도 다음 단계 칩을 붙인다. 안내 문구는 **지금 문구를 그대로 쓴다**(P1 버림).
5. 규칙 기반 답변(엔진 없음)은 카피를 만들 수 없다고 한 줄로 밝히고 카피 기준 문서를 근거로 보여 준다(C3).

2단계 — PPM 세부 상품 추가 질문 (N1, 기존 상품 확인 칩 흐름에 붙는다)

6. 상품이 PPM 으로 정해지는 지점(상품 확인 칩에서 PPM 선택, 또는 대화에서 PPM·월정액이 읽힘)에서 세부 상품이 아직 없으면 "B tv+ 상품인가요, TV 상품인가요?"를 칩으로 **한 번** 묻는다. 어드민 경로(`product`)와 질문만 경로(`product-qa`) 둘 다 해당한다.
7. 대화에 "B tv+"가 이미 있으면 PPM 으로 읽고 상품 확인·세부 상품 질문을 둘 다 건너뛴다. "B tv"(플랫폼 이름)는 B tv+ 로 읽지 않는다.
8. 세부 상품은 **PPM 안의 구분**으로만 다룬다. 상품 값(`scope`)은 그대로 PPM 이고, 어드민으로 넘기는 상품 값도 PPM 이다(11/16 Q4 결정 "B tv+ 는 `[PPM]` 으로 표시"와 같은 방향). 세부 상품은 표시 이름(예: `PPM(월정액) · B tv+`)과 근거 문서 고르기(`schemes.md` B tv+ 절 우선)에만 쓴다.
9. 대화 규약에 "B tv+ 는 PPM 상품 중 하나이며 주력 상품"임을 적고, B tv+ 로 정해진 대화에서는 B tv+ 절을 먼저 근거로 삼게 한다.

## 수용 기준

### 1단계 — 결과물 요청 (C1·C2·C3)

1. "영화 신작 프로모션 기획하려는데 카피 추천해줘", "배너 문구 뽑아줘", "PPV 이벤트명 3개만 추천" 세 문장 각각에 대해, 답변 아래에 "진행하려는 프로모션이 있으신가요?" 확인 칩이 **붙지 않는다**.
2. 같은 세 문장에 엔진(claude·codex·gemini 중 하나)이 답하면, 카피 요청은 `· 메인 카피 / 서브 카피` 줄 3개, 이벤트명 요청은 `· 이벤트명 — 이유` 줄 3개가 나온다. 대화에 없던 작품명·할인율·가격은 `〈작품명〉`·`〈할인율〉` 같은 자리 표시로 남는다.
3. 위 답의 `sourcePaths` 에 `promotion/copy-` 로 시작하는 문서가 하나 이상 들어 있다.
4. "카피 추천받기" 칩을 누르면 보낸 질문이 1번 판별에 걸리고, 답 형식이 2번과 같다. "노출 구좌 추천받기"는 구좌 2~3줄과 근거 `promotion/placements.md` 또는 `promotion/playbook.md` 가 나온다.
5. 결과물 요청에 답한 메시지 아래에 다음 단계 칩(카피 · 구좌 · 프로모션 자동화로 연결 · 조금 더 정리)이 붙고, 질문 문구는 **지금 main 의 문구와 글자 그대로 같다**("이대로 프로모션 자동화 페이지로 넘겨 드릴까요? …").
6. 엔진이 없을 때(규칙 기반) 1번 문장에 대한 답 첫 줄이 "카피 후보는 AI 답변 엔진이 있어야 만들 수 있다"는 취지이고, 근거에 카피 기준 문서가 나온다.
7. 회귀: "판촉 쿠폰 품의 결재선은?", "프로모션 어떤 순서로 진행돼?", "월정액 프로모션 기획하고 싶어" 의 지금 동작(사실 답 / 절차 답 / 진행 의도 칩)이 바뀌지 않는다. "CBS 승인요청 방법"이 판단 요청이나 결과물 요청으로 잡히지 않는다.
8. 회귀: 1번 세 문장과 "카피 추천받기"가 보내는 문장은 `mayBeReport` 가 `false` 다.
9. 회귀: 기획 의도 확인 칩은 지금처럼 "네, 진행 / 아니요, 질문만" 두 개다. "기획부터" 선택지는 생기지 않는다.

### 2단계 — PPM 세부 상품 추가 질문 (N1)

10. "월정액 프로모션 기획하고 싶어" → "네, 진행"을 누르면, 어드민을 열기 전에 "B tv+ 상품인가요, TV 상품인가요?" 질문과 선택지 칩 두 개(B tv+ / TV 상품)가 뜬다. 하나를 고르면 지금과 같이 프로모션 자동화 화면이 새 탭으로 열리고, 넘어가는 상품 값은 PPM 이다(지금과 같음).
11. "프로모션 하나 하려고" → "아니요, 질문만" → 상품 확인에서 "월정액(PPM)"을 고르면 세부 상품 질문이 뜬다. "B tv+"를 고르면 "PPM(월정액) · B tv+ 기준으로 답하겠습니다"처럼 세부 상품이 들어간 안내가 나온다.
12. 11번 뒤 "쿠폰 어떤 걸로 해?"를 물으면 답의 `sourcePaths` 에 `promotion/schemes.md` 가 있고, 답이 B tv+ 절(쿠폰 종류·이벤트 방식별 조합) 내용을 근거로 한다.
13. 상품 확인에서 "단건(PPV)"을 고르면 세부 상품 질문은 뜨지 않는다.
14. "B tv+ 신규 가입 프로모션 기획하고 싶어" → "네, 진행"이면 상품 확인·세부 상품 질문이 **둘 다 뜨지 않고** 바로 PPM 으로 어드민이 열린다. "월정액 B tv+ 쿠폰 기준 알려줘"도 세부 상품 질문이 뜨지 않는다.
15. "B tv 마케팅 프로세스 알려줘", "모바일 B tv 외부연동 규격 알려줘"는 B tv+ 로 읽히지 않는다(상품이 PPM 으로 잡히지 않고, 세부 상품 질문도 뜨지 않는다).
16. 한 대화에서 세부 상품 질문은 많아야 한 번 뜬다. 이미 답했거나 대화에서 읽혔으면 다시 묻지 않는다.
17. 정리 카드의 상품 칸이 세부 상품을 고른 뒤 `PPM(월정액) · B tv+` 또는 `PPM(월정액) · TV 상품` 으로 보인다. 고르지 않았으면 지금처럼 `PPM(월정액)`.
18. `ProductScope` 타입·검색 범위 값·위키 줄 단위 태그에 `B tv+` 가 새로 생기지 않는다(11/16 Q4 결정 유지).
19. 결과물 요청(1단계)과 세부 상품 질문이 만날 때의 동작은 열린 질문 N-Q2 결정대로다. 결정 전 기본값: 결과물 요청에는 세부 상품을 되묻지 않는다(C1 우선).
20. `npm run build` 통과. 로컬 중계(`server/cliBridge.ts`)와 배포 함수(`api/ask.ts`)가 같은 `server/assistant-prompt.md` 를 읽으므로 규약 변경은 한 곳에서 끝난다.

## 보류(추후) — 편성표 등록·승격 (R4·R5)

상위 지시자 결정 Q1(11/19): **추후 진행.** 저장 방식(Q4·Q5)은 아래대로 확정됐고, 구현은 Q1 을 진행할 때 한다. 착수할 때 이 절을 새 기획 문서로 옮겨 날짜·현재 상태를 다시 확인한다.

### 확정된 저장 방식

- 편성표 원본 주소는 **공유 드라이브에만** 둔다(시스템 목록과 같은 규칙). → 편성표 등록(R4)은 공유 드라이브 JSON(`HUB_SYSTEMS_FILE` 방식 확장).
- 승격 문서는 **git PR** 로 반영한다(문서 수정·새 문서와 같은 흐름). 문서 본문에 원본 주소를 넣지 않는다.
- **Redis 는 도입하지 않는다.** 계정에만 쓴다.

### 저장 방식 비교 (결정 근거로 남김)

| 항목 | A. Redis 재도입 (PR #38 방식) | B. 공유 드라이브 JSON (`HUB_SYSTEMS_FILE` 방식 확장) | C. git (PR 이 진실의 원천, 문서 제안과 같은 방식) |
| --- | --- | --- | --- |
| 동작 위치 | 배포본만. 로컬 허브는 Redis 키가 없고 데모 계정이라 공유되지 않음 | 로컬 허브만. 배포본은 지금 시스템 화면처럼 메모리 + 안내 | 로컬 허브·배포본 둘 다(`GITHUB_TOKEN` 있으면) |

| 편성표 "등록"(R4) 에 맞나 | 맞음 | 맞음 | **맞지 않음** — 주소가 있는 목록을 공개 저장소에 둘 수 없음 |

### 보류된 범위 (구 3단계)

1. 편성표 등록을 공유 드라이브 JSON 에 쌓는다(B). 배포본은 메모리 + 시스템 화면과 같은 형식의 안내.
2. 승격 요청을 새 문서 PR 로 연다(C). 진입 이름 `편성표 승격`. 본문에 원본 주소를 넣지 않는다. 공개 검사를 거친다.
3. "내 요청"·"승인 관리"의 승격 목록을 PR 목록에서 읽고, 메모리 승격 상태·가짜 대기·"새로고침하면 사라집니다" 안내를 걷어 낸다.

### 보류된 수용 기준

- H1. 로컬 허브에서 편성표를 등록하고 허브를 껐다 켜도 목록에 남는다. `HUB_SYSTEMS_FILE` 과 같은 방식으로 공유 위치를 지정하면 다른 PC 의 허브에서도 보인다.
- H2. 배포본 편성표 등록 화면에 "저장되지 않는 화면 — 로컬 허브에서 등록해 주세요" 형식의 안내가 시스템 화면과 같은 문장 구조로 보인다.
- H3. 승격 요청을 내면 GitHub 에 브랜치 `docs/` 로 시작하는 PR 이 열리고, 본문 `- 진입: 편성표 승격` 줄이 있다. "내 요청"·"승인 관리"의 승격 목록이 이 PR 을 보여 준다.
- H4. 승격 PR 의 문서 본문과 PR 본문 어디에도 `http` 로 시작하는 편성표 주소가 없다. 금액·별표 2개 표기가 있으면 PR 이 열리지 않는다(새 문서 공개 검사와 같은 차단).
- H5. 같은 편성표에 열린 승격 PR 이 있으면 두 번째 요청은 "이미 승격 요청이 대기 중입니다"로 막힌다.
- H6. `src/pages/Approvals.tsx` 의 "새로고침하면 사라집니다 (저장소 반영 준비 중)" 문구와 `decidePromotion` 의 가짜 대기가 없어진다.
- H7. 로컬 중계(`server/cliBridge.ts`)와 배포 함수(`api/`)가 같은 진입 이름·같은 공개 검사 규칙을 쓴다. `npm run build` 통과.
