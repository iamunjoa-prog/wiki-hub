### 4. 리포트 모드와의 관계

리포트 모드는 질문 신호 점수로 자동 진입한다(`src/lib/report.ts:20-46`, 서버 쪽 규칙과 짝). '인사이트' 한 단어는 1점, "추천…근거"는 1점이다. PR #38 의 기획 정리 뒤 요청 문장("인사이트·정책에 맞게 이벤트명과 카피를 추천해줘")은 지금 점수 규칙으로는 리포트로 넘어가지 않지만, 문구를 바꾸면 넘어갈 수 있다. 수용 기준에 회귀 확인으로 넣는다.

**PM 의견: B + C 혼합. Redis 재도입은 하지 않는다.**

- **편성표 등록(R4)** 은 B. 편성표 목록은 사내 주소를 들고 있어 시스템 목록과 성격이 같다. 같은 공유 드라이브 방식으로 두면 실무자가 배울 것이 하나로 끝나고, 배포본 안내 문구도 시스템 화면과 같게 쓸 수 있다.
- **편성표 승격(R5)** 은 C. 승격의 결과물은 위키 문서이고, 위키 문서의 반영은 이미 전부 PR 로 간다. 승격만 다른 저장소에 두면 "내 요청·승인 관리" 화면이 다시 두 원천을 섞게 된다. 요약 문서 본문에는 **원본 주소를 넣지 않고** 편성표 이름·GNB·기간·담당 팀까지만 쓴다. 원본은 "편성/스케줄 화면에서 같은 이름으로 열기" 안내로 대신한다(주소는 B 의 공유 파일에서 읽음).
- Redis 는 계정에만 쓴다. 배포본 하나만 공유되는 저장소를 늘리면 로컬 허브 사용자와 기록이 갈라진다.

단, 편성표 등록·승격 자체가 지금도 쓰이는 흐름인지는 상위 지시자 확인이 먼저다(열린 질문 Q1). main 에는 그 사이 Today B tv·모바일 빅배너 실데이터 편성표 화면이 생겼다.

## 이번 범위 / 범위 밖

### 이번 범위

1단계 — 챗봇 결과물 요청 (저장 방식 결정과 무관, 바로 착수 가능)

1. 카피·노출 구좌·이벤트명을 **달라는** 발화를 판별한다(C1). 판별되면 진행 의도 확인 칩을 붙이지 않는다.
2. 대화 규약에 "결과물 요청" 유형과 출력 형식을 넣는다(C2). 근거 문서는 `promotion/copy-principles.md`·`copy-movie-ppv.md`·`copy-genre-frames.md`·`copy-verification.md`·`banner-specs.md`·`placements.md`·`playbook.md`.
3. 다음 단계 칩의 "카피 추천받기"·"노출 구좌 추천받기"가 보내는 문장을 결과물 요청으로 잡히는 문장으로 바꾼다.
4. 결과물 요청에 답한 뒤에도 다음 단계 칩을 붙이고, 안내 문구를 P1 문구로 바꾼다.
5. 규칙 기반 답변(엔진 없음)은 카피를 만들 수 없다고 한 줄로 밝히고 카피 기준 문서를 근거로 보여 준다(C3).

2단계 — 단계별 기획 질문 (Q2·Q3 결정 후)

6. 기획 의도 확인에서 "여기서 기획부터"를 고를 수 있게 한다(C5, 형태는 Q2 결정대로).
7. "기획부터"는 상품 → 진행 형태 → 기간 → 이벤트명을 하나씩 묻는다. 앞 대화에서 읽힌 값은 건너뛴다. 기간·이벤트명은 입력창으로 받고 "아직 미정"으로 건너뛸 수 있다(P2).
8. 다 모이면 정리 카드와 함께 "이 조건으로 이벤트명·카피를 추천받을까요?"를 묻는다.
9. 질문 칩이 선택지를 직접 들고 오도록 `IntentPrompt` 를 넓힌다(PR #38 의 `choices` 방식).

3단계 — 편성표 등록·승격 기록 (Q1·Q4 결정 후)

10. 편성표 등록을 공유 드라이브 JSON 에 쌓는다(B). 배포본은 메모리 + 시스템 화면과 같은 형식의 안내.
11. 승격 요청을 새 문서 PR 로 연다(C). 진입 이름 `편성표 승격`. 본문에 원본 주소를 넣지 않는다. 공개 검사를 거친다.
12. "내 요청"·"승인 관리"의 승격 목록을 PR 목록에서 읽고, 메모리 승격 상태·가짜 대기·"새로고침하면 사라집니다" 안내를 걷어 낸다.

## 수용 기준

### 1단계 — 결과물 요청

1. "영화 신작 프로모션 기획하려는데 카피 추천해줘", "배너 문구 뽑아줘", "PPV 이벤트명 3개만 추천" 세 문장 각각에 대해, 답변 아래에 "진행하려는 프로모션이 있으신가요?" 확인 칩이 **붙지 않는다**.
2. 같은 세 문장에 엔진(claude·codex·gemini 중 하나)이 답하면, 카피 요청은 `· 메인 카피 / 서브 카피` 줄 3개, 이벤트명 요청은 `· 이벤트명 — 이유` 줄 3개가 나온다. 대화에 없던 작품명·할인율·가격은 `〈작품명〉`·`〈할인율〉` 같은 자리 표시로 남는다.
3. 위 답의 `sourcePaths` 에 `promotion/copy-` 로 시작하는 문서가 하나 이상 들어 있다.
4. "카피 추천받기" 칩을 누르면 보낸 질문이 1번 판별에 걸리고, 답 형식이 2번과 같다. "노출 구좌 추천받기"는 구좌 2~3줄과 근거 `promotion/placements.md` 또는 `promotion/playbook.md` 가 나온다.
5. 결과물 요청에 답한 메시지 아래에 다음 단계 칩(카피 · 구좌 · 프로모션 자동화로 연결 · 조금 더 정리)이 붙고, 질문 문구가 P1 문구다.
6. 엔진이 없을 때(규칙 기반) 1번 문장에 대한 답 첫 줄이 "카피 후보는 AI 답변 엔진이 있어야 만들 수 있다"는 취지이고, 근거에 카피 기준 문서가 나온다.
7. 회귀: "판촉 쿠폰 품의 결재선은?", "프로모션 어떤 순서로 진행돼?", "월정액 프로모션 기획하고 싶어" 의 지금 동작(사실 답 / 절차 답 / 진행 의도 칩)이 바뀌지 않는다. "CBS 승인요청 방법"이 판단 요청이나 결과물 요청으로 잡히지 않는다.
8. 회귀: 1번 세 문장과 "카피 추천받기"가 보내는 문장은 `mayBeReport` 가 `false` 다.

### 2단계 — 단계별 기획 질문

9. 기획 의도 확인에서 "기획부터"를 고르면 상품 → 진행 형태 → 기간 → 이벤트명 순서로 **한 번에 하나씩** 질문 칩이 뜬다.
10. 앞 대화에 "PPV"와 "10월 1일 ~ 10월 14일"이 있었으면 상품·기간 질문은 뜨지 않는다.
11. 진행 형태 선택지의 글자는 `지식/promotion/schemes.md` 의 해당 상품 표/소제목 표기와 글자 그대로 같다(문서가 바뀌면 같이 바뀌는 방식은 dev-front 가 정한다).
12. 기간·이벤트명 단계에서는 입력창에 적은 말이 그 단계의 답으로 들어가고, "아직 미정" 칩으로 건너뛸 수 있다. 건너뛴 값은 정리 카드에 '미정'으로 보인다.
13. 네 단계가 끝나면 정리 카드와 "이벤트명·카피를 추천받을까요?" 칩이 뜨고, 고르면 1단계 2번 형식의 답이 온다. 이 답의 첫 줄은 선택한 상품·형태에서 정책상 걸리는 점이 있을 때만 그것을 짚는다.
14. "바로 어드민"을 고르면 지금과 같이 상품 확인 후 프로모션 자동화 화면이 새 탭으로 열린다(동작 변화 없음).

### 3단계 — 편성표 등록·승격

15. 로컬 허브에서 편성표를 등록하고 허브를 껐다 켜도 목록에 남는다. `HUB_SYSTEMS_FILE` 과 같은 방식으로 공유 위치를 지정하면 다른 PC 의 허브에서도 보인다.
16. 배포본 편성표 등록 화면에 "저장되지 않는 화면 — 로컬 허브에서 등록해 주세요" 형식의 안내가 시스템 화면과 같은 문장 구조로 보인다.
17. 승격 요청을 내면 GitHub 에 브랜치 `docs/` 로 시작하는 PR 이 열리고, 본문 `- 진입: 편성표 승격` 줄이 있다. "내 요청"·"승인 관리"의 승격 목록이 이 PR 을 보여 준다.
18. 승격 PR 의 문서 본문과 PR 본문 어디에도 `http` 로 시작하는 편성표 주소가 없다. 금액·별표 2개 표기가 있으면 PR 이 열리지 않는다(새 문서 공개 검사와 같은 차단).
19. 같은 편성표에 열린 승격 PR 이 있으면 두 번째 요청은 "이미 승격 요청이 대기 중입니다"로 막힌다.
20. `src/pages/Approvals.tsx` 의 "새로고침하면 사라집니다 (저장소 반영 준비 중)" 문구와 `decidePromotion` 의 가짜 대기가 없어진다.
21. 로컬 중계(`server/cliBridge.ts`)와 배포 함수(`api/`)가 같은 진입 이름·같은 공개 검사 규칙을 쓴다. `npm run build` 통과.
