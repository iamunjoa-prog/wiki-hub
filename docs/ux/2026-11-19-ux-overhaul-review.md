## 결론

**판정: 부분 개선으로 충분.**

- 틀(사이드바 묶음 찾기 / 업무 화면 / 내 업무, 한 번에 한 카테고리만 펼치기, 빈 메뉴 맨 아래·누를 수 없음, 독 너비 조절)은 이미 업무 단위로 나뉘어 있고, 대표 과업 5개가 모두 최단 경로 3클릭 안에 닿는다. 구조(정보구조·레이아웃)를 갈아엎을 신호는 없다.
- 개편 신호가 실제로 켜진 것은 K1(대시보드 첫 행동 없음), K3(같은 대상에 이름 2~3개), K5(문서 → 질문 방향 끊김) 세 가지이며, 모두 **화면 한두 곳의 문구·버튼 추가**로 풀린다. K1 은 1차 ①이 그대로 해결한다.
- **1차 ①②③ 결과물은 버려지지 않는다.** 아래 후속 개선은 대시보드 카드·독 패널·placeholder 위에 얹히는 것이고, 어느 것도 이 셋의 위치나 동작을 바꾸지 않는다.

## 1. 대표 과업 5개 클릭 수 (K2, 기준 3클릭, 대시보드에서 시작)

| 과업 | 현재 최단 경로 | 클릭 | 메뉴만으로 | 1차 반영 후 |
| --- | --- | --- | --- | --- |
| ① PPV 프로모션 기획 조건 묻기 | 챗봇 → 조건 문장 직접 작성 → 보내기 | 2 + 작성(되묻기 칩 +1~2) | 챗봇 → 프로모션 기획 시작하기 → 네/아니요 → PPV = 4, 조건은 그 뒤에도 직접 입력 | 카드 → 상품 → 기간 → 혜택 → 보내기 = 5, **작성 0** |
| ② 이번 주 Today B tv 편성 확인 | 챗봇 → 홈 편성 스케줄 (B tv) | 2 | 편성/스케줄 → 홈 펼치기 → Today B tv = 3 | 편성 확인 카드 = 1 |
| ③ 혜택 정책(중복 적용) 확인 | 검색 입력·Enter → PPM 정책 → 목차 | 3 | 위키 문서 › 프로모션 → 정책 → PPM 정책 → 목차 = 4 | 정책 확인 카드 → 문서 → 목차 = 3 |
| ④ 시스템 매뉴얼 특정 기능 | 검색 → ACS 매뉴얼 → 목차 | 3 | 프로모션 → 시스템 매뉴얼 → ACS → 목차 = 4 | 시스템 사용법 카드 → 문서 → 목차 = 3 |
| ⑤ 문서 수정 제안 남기기 | 검색 → 문서 → 수정 제안 (이후 다음·제출 2) | 3 (양식 진입까지) | 위키 › 카테고리 → 서브메뉴 → 문서 → 수정 제안 = 4 | 변화 없음 (3) |

- 최단 경로 기준 3클릭 초과 과업: **0개**. 메뉴만 쓰면 ③④⑤ 3개가 4클릭 → 신호 조건("2개 이상")에 걸리지만, 초과분이 모두 "문서 안 목차 이동" 또는 "서브메뉴 한 단"이고 1차 카드가 ③④를 3클릭으로 당긴다.
- ①은 1차 후 클릭이 5로 늘지만, 질문 문장을 직접 쓰는 일이 0 이 되고 상품 되묻기 왕복이 없어진다. 깊이(메뉴 단계) 문제가 아니라 고를 조건 수만큼의 선택이라 개편 신호로 보지 않는다.
- ⑤ 흐름 자체(편집 → 확인 → 제출)는 requests-planner 영역이라 진입 경로만 셌다.

## 3. 왜 "틀만 개편"도 아닌가

- K3 이름 중복 4건 중 3건이 틀(사이드바·독)에 있지만, 고칠 것은 **라벨 글자**다. 사이드바 묶음·순서·펼침 규칙, 상단바 검색, 독 배치는 그대로 두어도 과업 클릭 수가 늘지 않는다.
- 사이드바 묶음(찾기 / 업무 화면 / 내 업무)은 이미 "문서·업무 화면·요청이 섞여 보인다"는 문제를 고친 결과다(`AppShell.tsx` 주석). 다시 뒤집으면 실무자가 익힌 위치를 잃는다.
- 프로모션 서브메뉴의 성격별 재분류 기준(시작하기~시스템 매뉴얼 / 배너 규격~운영 참고자료)은 유지한다. 1차 카드 3·4 는 이 서브메뉴(`policy`·`system`)를 그대로 목적지로 쓴다.
