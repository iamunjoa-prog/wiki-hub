## 2. 설계 요약 — 입구 3개, 확인 창 1종

```
사이드바                                   위키 목록 /wiki?category=promotion
───────────────────────                    ──────────────────────────────────────────────
▾ ■ 편성                    베타            [전체 36][시작하기 1][정책 3] … [업무 프로세스 0]   [메뉴 편집]
  ▾ 영화/시리즈          0  ⋯   ← 입구①      ┌ 메뉴 편집 패널 (입구③) ───────────────────────┐
     │ + 문서 추가            ← 문서(기존)    │ 〔대기 중 메뉴 제안 n건〕                       │
  › TV 방송              0  ⋯               │ 시작하기        1  [이름 바꾸기] [↑] [↓] [지우기]│
  ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄                     │ …                                              │
  + 새 하위 메뉴              ← 입구②        │ + 새 하위 메뉴                                  │
                                             └───────────────────────────────────────────────┘
              ↓ 어느 입구든
        ┌ 메뉴 제안 확인 창 (MenuProposeDialog, op 4종) ┐
        │ 〔제목〕  입력/미리보기 · 사유(선택) · [취소][제안 올리기] │
        └───────────────────────────────────────────┘
```

### 2-1. 전 → 후 동선 (클릭 수)

| 하고 싶은 것 | 전 | 후 — 사이드바 | 후 — 위키 목록 |
| --- | --- | --- | --- |
| 이름 바꾸기 | 불가(개발자 요청) | `⋯`(1) → 이름 바꾸기(2) → 입력칸에 커서가 이미 있음 → 입력 → [제안 올리기](3) | [메뉴 편집](1) → [이름 바꾸기](2) → 입력 → 제출(3). 카테고리 칩을 먼저 눌러야 하면 +1 |
| 새 하위 메뉴 | 불가 | 카테고리가 펼쳐져 있으면 `+ 새 하위 메뉴`(1) → 이름 입력 → 제출(2). 접혀 있으면 +1 | [메뉴 편집](1) → `+ 새 하위 메뉴`(2) → 입력 → 제출(3) |
| 한 칸 올리기/내리기 | 불가 | `⋯`(1) → 위로/아래로(2) → 순서 미리보기 확인 → 제출(3) | [메뉴 편집](1) → [↑]/[↓](2) → 제출(3) |
| 빈 메뉴 지우기 | 불가 | `⋯`(1) → 지우기(2) → 제출(3) | [메뉴 편집](1) → [지우기](2) → 제출(3) |
| 왜 못 지우는지 알기 | — | `⋯`(1) → 메뉴 안 [지우기] 아래 이유 한 줄이 바로 보임 (1클릭) | [메뉴 편집](1) → [지우기] 옆 이유 한 줄 (1클릭) |

기획안 수용 기준 6 "이름 바꾸기 입력 칸까지 2번 이내 조작" → 사이드바·위키 목록 모두 2번.

순서는 한 제안에 한 칸이다(기획안 C "한 번에 하나"). 세 칸 옮기려면 제안 3건 = 9클릭. 담당자가 메뉴를 처음 꾸릴 때 불편할 수 있다 — 5장 확인 필요.

## 4. 화면 변경 — dev-front 커밋 B

### 4-1. 입구① 사이드바 하위 메뉴 줄의 `⋯`

**어느 줄에 다나**

| 줄 | `⋯` | 이유 |
| --- | --- | --- |
| 카테고리 줄 | 없음 | R4 |
| 하위 메뉴 줄 — 펼칠 수 있는 줄(`has-toggle`, 191행 `nav-count` 뒤) | 있음 | |
| 하위 메뉴 줄 — 빈 줄(`emptyRow`, "준비중") | **있음** | 프로모션 "업무 프로세스" 처럼 빈 메뉴가 이름 바꾸기·지우기의 주 대상이다. 지금 `emptyRow` 는 `div aria-disabled` 라 안에 버튼을 넣어도 되도록 `aria-disabled` 를 줄 전체가 아니라 이름 칸에만 건다 |
| `기타`(`__unassigned__`) | 없음 | 메뉴 파일에 없는 묶음이다 |
| 이용 안내 문서 줄, 모든 문서 줄 | 없음 | 문서는 메뉴가 아니다(R5) |
| `allowNewSub: false` 카테고리의 하위 메뉴 | 있음(이름 바꾸기·순서만), [지우기] 비활성 | 이름 바꾸기는 모든 하위 메뉴가 대상(기획안 범위 3). 지금 그런 카테고리는 이용 안내뿐이고 하위 메뉴가 0개라 실제로 보일 일은 없다 |

**모양과 자리**

- 줄 맨 오른쪽, 건수(`nav-count`) 뒤에 22×30px 버튼. 글자는 `⋯`, `aria-label="〔{메뉴 이름} 메뉴 편집〕"`, `aria-haspopup="menu"`, `aria-expanded`.
- 넓은 화면(마우스): 줄에 마우스를 올리거나(`:hover`) 줄 안에 포커스가 있을 때(`:focus-within`), 또는 메뉴가 열려 있을 때만 보인다. 자리(22px)는 늘 비워 두어 나타날 때 건수가 밀리지 않는다.
- 터치(`@media (hover: none)`, 휴대폰 서랍 포함): 늘 보인다. 색은 `--console-muted`.
- 색: `.nav-toggle` 과 같은 `--console-muted`, 올리면 `--console-strong`. 새 색을 만들지 않는다.
- 탭 순서: 화살표(`nav-toggle`) → 이름(`nav-label`) → `⋯`.

**펼친 메뉴(팝오버)**

- 이미 있는 `BlockEditor.tsx` 845-889행 `.bk-menu`(`role="menu"`, `role="menuitem"`, 흰 바탕 팝오버, `styles.css` 916-919행) 모양을 쓴다. 사이드바(어두운 콘솔) 위에 흰 팝오버가 뜨는 것은 의도다 — 편집 동작이 탐색과 다른 층이라는 신호.
- **잘림 주의:** 사이드바 `.nav` 는 `overflow-y: auto` 라 그 안에 `position: absolute` 로 띄우면 잘린다. `document.body` 로 포털을 띄우고 `position: fixed` 로 `⋯` 의 오른쪽 아래에 붙인다. 화면 아래 끝에 걸리면 위로 뒤집는다.
- 항목 (위에서부터):

  ```
  ┌──────────────────────────┐
  │ 이름 바꾸기               │
  │ 위로                     │  ← 맨 위 메뉴면 비활성
  │ 아래로                   │  ← 맨 아래 메뉴면 비활성 (기타는 세지 않음)
  │ ──────────────────────── │
  │ 지우기                   │  ← --danger 글자. 비활성이면 회색
  │ 〔문서가 n개 있어 지울 수 없어요〕 │  ← 비활성일 때만, 12px --muted
  └──────────────────────────┘
  ```

- [하위 메뉴 만들기]·[문서 추가]는 이 메뉴에 넣지 않는다. 하위 메뉴 아래에 메뉴를 만드는 길은 없다(R5). 문서 추가는 이미 줄 아래에 있다.
- 비활성 항목은 `disabled` 대신 `aria-disabled="true"` + `aria-describedby`(이유 줄)로 둔다. 화면 낭독기가 포커스를 줄 수 있어야 이유를 읽는다.
- 키보드: `⋯` 에서 Enter/Space/↓ = 열고 첫 항목에 포커스, ↑↓ = 이동(비활성도 멈춤), Enter = 실행, Esc·바깥 클릭 = 닫고 `⋯` 로 포커스. 기존 `.bk-menu` 에는 화살표 이동이 없어 새 컴포넌트에서 넣는다.
- 항목을 고르면 팝오버를 닫고 확인 창(4-4)을 연다. 휴대폰 서랍은 열어 둔 채 그 위에 확인 창을 띄운다(창을 닫으면 서랍 그 자리로 돌아온다).

### 4-2. 입구② `+ 새 하위 메뉴` — `+ 문서 추가` 와 헷갈리지 않게

지금 편성 사이드바에는 하위 메뉴마다 `+ 문서 추가` 줄이 있다. 둘이 나란히 보이는 경우(마지막 하위 메뉴를 펼쳤을 때)가 반드시 생긴다:

```
▾ ■ 편성                     베타
│ ▾ TV 방송               0  ⋯
│ │   + 문서 추가                    ← 3단 자리, TV 방송의 가이드선 안
│ ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄
│ + 새 하위 메뉴                     ← 2단 자리, 하위 메뉴 이름과 같은 시작선
```

| 구분 | `+ 문서 추가` (있음, 그대로) | `+ 새 하위 메뉴` (새로) |
| --- | --- | --- |
| 무엇을 만드나 | 그 하위 메뉴 안의 **문서** | 카테고리 안의 **2단 메뉴** |
| 자리 | 펼친 하위 메뉴의 문서 목록 끝(`.nav-children.depth3` 안) | 카테고리의 하위 메뉴 목록 끝(`.nav-children.depth2` 의 마지막 자식, `기타` 뒤) |
| 들여쓰기 | 문서 줄과 같음(`.nav-item.leaf`, 3단 가이드선 안) | 하위 메뉴 이름과 같은 시작선(`.nav-item.sub.no-toggle`, 22px) |
| 구분선 | 없음 | 위에 1px 점선(`--console-line`, `border-top: 1px dashed`) + 위 여백 4px. 하위 메뉴 목록이 여기서 끝난다는 표시 |
| 글자 | `+ 문서 추가` | `+ 새 하위 메뉴` |
| 크기·색 | 13px, `--console-muted`(`.nav-add`, `styles.css` 501행) | 13.5px(하위 메뉴 줄과 같음), `--console-muted` |
| 누르면 | `/wiki/new?category=&sub=` 로 **화면 이동** | 화면 이동 없이 **확인 창**(4-4 `add`) |
| 보이는 조건 | 열어 둔 카테고리(`open`) + 그 하위 메뉴를 펼쳤을 때 | 카테고리를 펼쳤고 `allowNewSub: true` 일 때. 하위 메뉴를 펼쳤는지와 상관없음 |
| 마우스 올림 설명(`title`) | `〔「TV 방송」에 문서 추가〕` | `〔편성에 하위 메뉴 추가 제안〕` |

정리: **명사(문서/하위 메뉴), 들여쓰기 단(3단/2단), 구분선, 결과(이동/창)** 네 가지가 다르다. 둘 다 `+` 로 시작하지만 "만들 것 + 자리"가 글자 그대로 읽힌다.

**한 줄 더**: `+ 문서 추가` 는 편성(열어 둔 카테고리)에만 있다. 프로모션에 새로 만든 하위 메뉴는 배포 뒤 문서가 0건이라 `emptyRow`("준비중")로 보이고, 펼칠 수도 `+ 문서 추가` 도 없다 — 첫 문서는 위키 목록 [+ 새 문서] → 하위 메뉴 고르기로만 올릴 수 있다. 방금 만든 메뉴에 "준비중"이 붙는 것은 어색하다. 5장 확인 필요 Q2.

### 4-4. 메뉴 제안 확인 창 (`MenuProposeDialog`, 동작 4종 공용)

**왜 창인가:** 사이드바 줄 안에서 이름을 바로 고치는(인라인) 방식은 폭이 좁고(하위 메뉴 이름 칸 약 150px), 사유 칸을 둘 자리가 없으며, 누르는 즉시 바뀐 것처럼 보여 R2("다음 배포 때 바뀐다")와 어긋난다. 그래서 4종 모두 같은 창으로 모은다.

**모양:** 기존 `SubmitEditDialog.tsx` 145-153행의 `.modal-back.submit-back` › `.modal.submit-modal` 구조, `role="dialog" aria-modal="true"`. 폭은 `submit-modal` 그대로.

```
┌ 〔제목: '영화/시리즈' 이름 바꾸기〕                     ✕ ┐
│ 〔대기 중 안내: 이 카테고리에 승인 기다리는 메뉴 제안이 1건 있어요〕  ← 있을 때만, .hint
│                                                          │
│ (op별 본문 — 아래 표)                                      │
│                                                          │
│ 사유 (선택)                                               │
│ [ 〔placeholder〕                                    ]    │  ← textarea 2줄
│ 〔반영 시점 한 줄: 승인되면 다음 반영 때 사이드바에 보여요〕   ← .muted 12.5px
│                                        [취소] [제안 올리기] │
└──────────────────────────────────────────────────────────┘
```

| op | 본문 | 제출 버튼 | 제출 가능 조건(화면 검사) |
| --- | --- | --- | --- |
| `rename` | 이름 입력칸(지금 이름이 채워지고 전체 선택된 채 포커스). 오른쪽 아래 `n/20`. 아래에 `전 → 후` 한 줄 미리보기 | `.btn.primary` | 앞뒤 공백 뺀 1~20자, 지금 이름과 다름, 같은 카테고리 다른 이름과 겹치지 않음(공백·대소문자 무시) |
| `add` | 이름 입력칸(빈 칸, 포커스). `n/20` | `.btn.primary` | 위와 같음(지금 이름 비교 없음) |
| `move` | 카테고리의 하위 메뉴 목록을 작게(`.hint` 상자 안 번호 목록) 보이고, 옮길 메뉴를 굵게 + `↑`/`↓` 표시로 바뀐 순서를 그린다 | `.btn.primary` | 늘 가능(맨 위/아래는 메뉴에서 이미 막힘) |
| `remove` | `〔'업무 프로세스' 메뉴를 지우자는 제안을 올려요〕` 한 줄 | `.btn.danger` (`styles.css` 150행, 테두리형 위험 색) | 문서 0건이고 `fixed` 가 아님 |

- 입력 오류는 입력칸 바로 아래 `.err` 한 줄(빈 이름·21자 이상·겹치는 이름·공개 규칙). 서버가 돌려준 오류(400·409·503)도 같은 자리에 그대로 쓴다. 문구는 requests-planner.
- Enter = 제출(입력칸에서), Esc = 취소. 제출 중에는 버튼 글자를 `〔올리는 중…〕` 으로 바꾸고 창 닫기를 막는다(`SubmitEditDialog` 145행 `!busy && onClose()` 와 같은 방식).
- **제출 뒤:** 같은 창이 완료 상태로 바뀐다(`SubmitDoneDialog` 353-380행 모양). 본문은 `〔제출 직후 문구 — "지금은 안 바뀜 + 언제 바뀌는지" 한 줄〕`, `add` 는 `〔승인·반영 뒤에 이 메뉴에 문서를 올릴 수 있어요〕` 를 더한다. 버튼: [내 요청에서 보기](`.btn`) · [닫기](`.btn.primary`). 사이드바는 그대로다(R2). 줄을 즉시 옮기거나 이름을 바꿔 그리지 않는다.
- PR·머지·배포·id·JSON 같은 말은 본문에 쓰지 않는다(기획안 C 문구 원칙). 제출 결과 링크는 [자세히 보기 ↗].

### 4-5. 입구③ 위키 목록 [메뉴 편집]

**자리:** `WikiIndex.tsx` 111-130행 하위 메뉴 칩 줄(`.filter-bar`) 맨 끝, `margin-left: auto` 로 오른쪽 끝. `.btn.sm`(테두리형). 보이는 조건: 카테고리를 골랐고(`active`) 그 카테고리가 `allowNewSub: true` 이거나 하위 메뉴가 1개 이상일 때. 이용 안내·전체 보기에서는 없다.

**누르면:** 칩 줄 바로 아래, 문서 목록(`.panel.wiki-list`) 위에 **편집 패널**이 펼쳐진다(화면 이동·창 없음). 버튼은 `aria-expanded="true"` 와 글자 `〔편집 닫기〕` 로 바뀐다. 주소는 바꾸지 않는다.

```
┌ .panel  메뉴 편집 · 프로모션 ──────────────────────────────────────────┐
│ 〔안내 한 줄: 바꾸자는 제안을 올리면 승인 뒤 다음 반영 때 바뀌어요〕          .muted
│ 〔대기 중 메뉴 제안 2건〕  · 배너 규격 → 배너 사양  · + 이벤트 문구         ← 있을 때만
├────────────────────────────────────────────────────────────────────────┤
│ 1  시작하기          문서 1   [이름 바꾸기] [↑] [↓] [지우기]               .row
│ 2  정책              문서 3   [이름 바꾸기] [↑] [↓] [지우기]
│ …                                                       (지우기 비활성 + 이유 title·한 줄)
│ 8  업무 프로세스      문서 0   [이름 바꾸기] [↑] [↓] [지우기]
├────────────────────────────────────────────────────────────────────────┤
│ + 새 하위 메뉴                                                          ← 사이드바와 같은 글자
└────────────────────────────────────────────────────────────────────────┘
```

- 줄 모양: 기존 `.panel` + `.row`(`.wiki-row` 와 같은 높이). 버튼은 모두 `.btn.sm`. [지우기]만 `.btn.sm.danger`. 비활성 [지우기]는 `disabled` + 옆에 `〔이유〕` 12px `--muted`(넓은 화면), 좁은 폭에서는 줄 아래로 내린다.
- `[↑]`/`[↓]` 는 글자 대신 화살표지만 `aria-label="〔{이름} 위로〕"` 를 단다.
- 각 버튼은 4-4 확인 창을 연다. 패널은 직접 값을 바꾸지 않는다.
- 대기 중 제안: `proposals`(`AppStore.tsx` 769행 `ensureProposals`) 중 `kind: 'menu'` 이고 이 카테고리인 것. 패널을 열 때 `ensureProposals()` 를 부른다. 카드 한 줄 모양은 기획안 C(`카테고리 › 전 → 후`, `+ 이름`, `− 이름`, `이름 ↑/↓`)를 따르고 문구는 requests-planner.
- 사이드바에는 대기 중 표시를 달지 않는다. 사이드바는 탐색 자리라 조용히 둔다. 대기 중 정보는 패널과 확인 창 머리(4-4)와 내 요청에서만 본다.

### 4-7. 휴대폰 폭(760px 이하, 서랍)
