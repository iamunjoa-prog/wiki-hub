## 3. 문서 화면 형태

### UI-1. 넓은 창에서 본문 한 줄이 너무 길다 — 심각도 높음

- 근거: `.md`·`.doc-body`에 최대 폭이 없다(`styles.css:553,578`). 1920 창에서 본문 폭 = 1920 − 사이드바 248 − 좌우 여백 36(`:552`) − 목차 200(`:26,554`) − 간격 18 = 약 1418px. 16px 한글로 한 줄에 약 90자다(스크린샷 1920). 1366 창은 약 864px, 55자 안팎.
- 개선안 (화면): `.doc-body`에 `max-width: 820px`(한글 약 48자, 머리·버튼 포함)를 두고, 목차는 본문 바로 오른쪽에 붙인다. 표가 많은 문서(CBS 표 14개)를 생각해 `.md table`만 본문 폭을 넘게 두는 안은 쓰지 않는다. 표는 UI-6의 가로 스크롤로 처리한다. 폭 값은 `:root`에 `--w-doc` 토큰으로 하나만 추가한다.
- 효과: 1920 창에서 한 줄 약 90자 → 약 48자. 1366 창(864px)도 820px 안쪽으로 들어온다.
- 반영: dev-front (`styles.css:24-30, 552-553`).

### UI-2. 굵게 표시가 깨져 `**`가 그대로 보인다 — 심각도 높음

- 근거: CommonMark 규칙에서 닫는 `**` 앞이 문장부호(`)` 등)이고 바로 뒤에 한글 조사가 붙으면 굵게가 끝나지 않는다. 예: `**CBS(Contents Billing System, 가입자관리시스템)**를`이 화면에 별표째 나온다(스크린샷 1920·1366의 "이 문서는" 첫 줄). 파서로 세어 보니 문서 7개에 `**` 34개(약 17곳)가 남아 있다: acs 12, cbs 8, swing 4, targeting 4, glossary 2, ppv 2, promotion-map 2.
- 개선안: 렌더러 쪽에서 해결한다. remark에 한중일 문자용 강조 규칙 플러그인(예: `remark-cjk-friendly`)을 `WikiDoc.tsx:232`의 remarkPlugins에 추가한다. 문서를 고치는 방식(괄호 뒤에 띄어쓰기)은 한국어 띄어쓰기를 망가뜨리고 새 문서마다 다시 생긴다. 챗봇 답변 렌더러에 같은 파서를 쓰면 함께 적용한다.
- 반영: dev-front (패키지 추가는 빌드 확인 필요). 적용 전까지 ops가 해당 7개 문서를 임시로 고칠지는 PM이 정한다.

### UI-3. 제목 위계가 약하다. h3가 본문보다 작다 — 심각도 중간

- 근거: 본문 16px(`styles.css:578`), h2 18px(`:579`, 본문의 1.125배), h3 15.5px(`:580`, 본문보다 0.5px 작음), h1 23px(`:567`). h3는 굵기로만 구분되고, h2 위 여백 26px은 본문 줄간격(16×1.8 ≈ 29px)보다 작아서 장이 바뀌는 것이 눈에 띄지 않는다(스크린샷 1366의 "메뉴 구성", "이 문서 안의 챕터").
- 개선안 (화면): h1 24px · h2 20px(위 여백 36px + 위쪽 1px `--border` 구분선) · h3 17px(위 여백 24px). 본문 16px / 1.8은 그대로 둔다(한글 본문으로 적당하다).
- 반영: dev-front (`styles.css:567,579-580`).

### UI-4. 현재 위치(breadcrumb)가 없다 — 심각도 중간

- 근거: 본문 머리에는 카테고리 태그와 문서 코드만 있다(`WikiDoc.tsx:198-203`). 서브메뉴(예: 배너 규격)는 본문 화면 어디에도 없고, 태그는 눌러도 아무 일이 없다. 편성/스케줄은 이미 `편성/스케줄 › B tv › 홈 › 오핫콘` 경로 줄을 만든다(`scheduleNav.ts:63-75`).
- 개선안 (화면): 제목 위에 `위키 문서 › 프로모션 › 배너 규격` 경로 줄을 둔다. 각 칸은 `/wiki?category=…&sub=…`로 이동한다. 편성/스케줄 경로 줄과 같은 모양으로 쓰고, 카테고리 태그는 지운다. 사이드바가 접히는 좁은 화면(UI-8)에서는 이 줄이 유일한 위치 표시가 된다.
- 효과: 같은 서브메뉴의 다른 문서로 가는 길이 사이드바를 쓰지 않아도 2클릭(경로 줄 → 행)이 된다.
- 반영: dev-front.

### UI-5. 목차가 일부 제목에서 동작하지 않는다 — 심각도 중간

- 근거: 목차 id는 원문 줄에서 만들고(`WikiDoc.tsx:115-121`), 본문 제목 id는 `String(children)`으로 만든다(`:234-235`). 제목 안에 굵게·코드가 있으면 children이 배열이라 `…,[object Object],…`가 되어 두 id가 다르다. 해당 제목: `지식/guide/writing.md:141`(`**하나만**`), `지식/promotion/channel.md:50`(`` `[PPM]` ``). 이 두 제목은 목차를 눌러도 스크롤되지 않고, 목차 글자에 `**`가 그대로 보이며, 현재 위치 강조도 켜지지 않는다. 같은 글자의 제목이 두 번 나오면 id도 겹친다.
- 개선안: 본문 제목 id를 children이 아니라 마크다운 노드의 원문 글자에서 만들어 목차와 같은 함수(`headingId`)를 쓰게 한다. 목차 글자에서는 `**`, `` ` `` 기호를 지운다. `npm run check:anchors`가 이 경우도 잡는지 함께 확인한다.
- 반영: dev-front.

### UI-6. 표가 좁은 폭에서 넘친다 — 심각도 낮음

- 근거: `.md table { width: 100% }`(`styles.css:584`)이고 가로 스크롤 감싸개가 없다. 넘치면 표만이 아니라 본문 영역(`.content`, `:423`) 전체가 옆으로 밀린다. 1366·915 폭에서는 칸 안에서 줄이 바뀌어 넘치지 않았다(스크린샷). 390 폭에서는 본문이 약 140px이라 표가 읽히지 않는다.
- 개선안: `components.table`로 표를 `overflow-x: auto` 상자로 감싼다. 첫 열(항목 이름)은 `white-space: nowrap`.
- 반영: dev-front.

### UI-7. 한글 단어가 줄 끝에서 중간에 끊긴다 — 심각도 낮음

- 근거: `.md`에 `word-break`가 없다(`styles.css:578`). 제목·메타에는 `keep-all`이 있다(`:567-568`). 1366 캡처에서 "생성·승 / 인·발급"처럼 단어 중간에서 줄이 바뀐다.
- 개선안: `.md p, .md li, .md td { word-break: keep-all; overflow-wrap: anywhere; }` (긴 영문·URL은 `anywhere`로 넘침을 막는다).
- 반영: dev-front.

### UI-8. 챗봇 창을 열거나 창이 좁으면 목차가 사라지고 대신할 것이 없다 — 심각도 중간

- 근거: 본문 폭 720px 이하에서 목차를 숨긴다(`styles.css:571-573`, 최근 커밋 739dcd0). 1366 창에서 챗봇 창(`--w-dock` 33vw, `:28`)을 열면 본문 폭이 약 667px라 목차가 꺼진다(스크린샷 915). 커밋 덕분에 본문이 찌그러지지는 않지만, 제목이 22~25개인 시스템 매뉴얼(CBS 298줄)에서 챗봇과 함께 읽을 때 장 사이 이동 수단이 없어진다.
- 개선안 (화면): 720px 이하에서는 제목 머리 아래에 접힌 `목차 (n)` 줄을 두고, 펼치면 같은 목록이 나온다(기존 `.panel` 재사용). 기본은 접힘.
- 반영: dev-front.

### UI-9. 목차가 길면 아래쪽이 잘리고, 챗봇 버튼이 목차를 가린다 — 심각도 낮음

- 근거: `.doc-toc`가 `position: sticky; top: 0`이고 최대 높이와 스크롤이 없다(`styles.css:554`). CBS 목차 25줄 × 약 26px = 약 650px라 768 높이 창에서 끝 항목(`다음에 볼 문서`)이 화면 밖에 있다. 오른쪽 아래 고정 챗봇 버튼(`.fab`, `:596-600`)이 목차 끝 항목과 겹친다(스크린샷 1366).
- 개선안: `.doc-toc { max-height: calc(100vh - var(--h-topbar) - 32px); overflow-y: auto; padding-bottom: 64px; }` (아래 여백은 챗봇 버튼 높이만큼).
- 반영: dev-front.

### UI-10. 회색 글자의 대비가 낮다 — 심각도 중간

- 근거: `--muted: #999`(`styles.css:4`)는 흰 바탕에서 대비 약 2.8:1로, 본문 글자 기준(WCAG AA 4.5:1)에 못 미친다. 이 색으로 쓰는 곳: 목차 기본 글자(`:559`), 문서 메타 "최종 수정…"(`:568`), 사이드바 건수(`:273`), `.label`(`:55`), 목록 행의 코드·날짜(`WikiIndex.tsx:89-92` `.muted`).
- 개선안: 읽어야 하는 글자(목차, 메타)는 `--text-2`(#555, 약 7.5:1)로 바꾸고, `#999`는 건수·구분 기호 같은 장식에만 쓴다. 토큰을 새로 만들지 않는다.
- 반영: dev-front.

### UI-11. 링크가 본문 글자와 거의 구분되지 않는다 — 심각도 중간

- 근거: 전역 `a { color: inherit; text-decoration: none; }`(`styles.css:48`) 위에 인라인 스타일로 밑줄 `1px solid var(--line)`(#d4d4d4)만 준다(`WikiDoc.tsx:249,256`). 연한 회색 1px 선이라 "원본 매뉴얼·첨부" 같은 링크가 잘 안 보이고(스크린샷 1366), 문서 안 이동과 외부 새 창 링크의 모양이 같다.
- 개선안: 인라인 스타일을 `.md a` 규칙으로 옮기고, 밑줄을 `--text-2`, 2px 아래로 띄운다. 외부 링크 뒤에는 `↗`를 붙인다.
- 반영: dev-front.

### UI-12. 휴대폰 폭에서 사이드바가 화면의 2/3를 차지한다 — 심각도 중간

- 근거: 사이드바 최소 200px·기본 248px(`AppShell.tsx:280,291`)이고 좁은 화면에서 접히지 않는다(`styles.css`에 사이드바용 `@media`가 없음, 화면 폭 규칙은 `:1323` 하나뿐). 390 폭에서 본문이 약 140px이고 수정 제안 버튼이 잘린다(스크린샷 390).
- 판단: 실무자 PC용 도구라 우선순위는 중간으로 둔다.
- 개선안: 760px 이하에서 사이드바를 화면 밖 서랍으로 빼고, 상단바 왼쪽에 메뉴 버튼을 둔다. UI-4 경로 줄이 위치 표시를 대신한다.
- 반영: dev-front.

### UI-13. 단축키 표시가 맥 기준이다 — 심각도 낮음

- 근거: 검색창에 `⌘K`로 표시된다(`AppShell.tsx:470`). 실제로는 Ctrl도 받는다(`:444`). 실무자 PC는 Windows다(`start-hub.bat`).
- 개선안: Windows에서는 `Ctrl K`로 표시한다(`navigator.platform` 확인).
- 반영: dev-front.

### UI-14. 문서 첫 줄 "적용대상" 인용 상자가 무겁다 — 심각도 낮음

- 근거: 40개 중 34개 문서가 `> 적용대상 …` 인용으로 시작한다. 인용 스타일(`styles.css:590`, 왼쪽 검은 선 + 회색 바탕)이라 본문 첫 화면의 큰 상자 하나를 메타 한 줄이 차지하고, 진짜 주의 문구 인용(예: "B포인트도 생성할 수 있으나…")과 모양이 같다(스크린샷 1366).
- 개선안: 본문 첫 인용이 `적용대상`으로 시작하면 메타 줄(`.doc-meta`) 옆 태그로 옮겨 보여 준다. 문서 원문은 그대로 둔다.
- 반영: dev-front.

### UI-15. 다크 모드가 없고, 색이 코드에 직접 박혀 있다 — 심각도 낮음

- 근거: `prefers-color-scheme`나 테마 전환 규칙이 없다. 본문·코드·강조 색이 토큰이 아니라 값으로 들어가 있다: `.md` 글자 `#222`(`styles.css:578`), 인라인 코드 바탕 `#f4f4f4`(`:587`), 강조 `#fff2b8`(`:592`, `:876`), 사이드바 글자 `#444`·`#555`(`:212,231`).
- 판단: 요청된 적이 없으므로 다크 모드 자체는 지금 하지 않는다. 다만 이 값들을 `--text`, `--surface-subtle` 같은 기존 토큰으로 바꿔 두면 나중에 `:root` 한 곳만 바꿔서 다크 모드를 만들 수 있다.
- 반영: dev-front (토큰 정리만).
