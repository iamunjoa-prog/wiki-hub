# 챗봇 대화 기록 검토 — 관리자가 기록을 보고 챗봇을 고치는 절차

작성 `chatbot-planner` · 2026-11-20
기준 문서 `docs/plan/2026-11-20-chat-history-log.md` (PR #92, D1~D8 확정). 담당 분배표의 chatbot-planner 행과 1절 기록 항목을 따른다.

이 문서는 **절차**만 정한다. `server/assistant-prompt.md` 는 이번에 고치지 않는다. 검토에서 나온 규약 수정은 아래 4절대로 chatbot-planner에게 따로 넘긴다.

---

## 0. 먼저 알아 둘 것

### 기준점

- 대화 규약을 판단하는 기준점은 **AX 앱의 대화 설계와 `ax-campaign` 규약**이다. 기록 속 답이 "잘못됐는지"는 아래 다섯 가지를 지켰는지로 본다.

| `ax-campaign` 규약 | 기록에서 어긴 모습 |
| --- | --- |
| 결론부터 | 첫 줄이 "확인해 보니", "관련 문서에 따르면" 같은 서론이다 |
| 과정을 중계하지 않는다 | "문서를 읽어보겠습니다", "찾았습니다"가 답에 남았다 |
| 이미 들은 것을 다시 묻지 않는다 | 같은 `chatId` 앞 턴에서 사용자가 밝힌 상품 유형·기간을 다시 묻는다 |
| 되묻기는 유형당 한 번 | 같은 대화에서 같은 종류의 되묻기가 두 번 이상 나온다 |
| 문서에 없으면 없다고 말한다 | 근거 문서 없이 정책·수치·절차를 단정한다 |

- 고칠 방향이 `ax-campaign` 규약과 어긋나면 고치지 않는다. 규약 자체를 바꿔야 할 것 같으면 PM 데스크에 검토 요청 표로 올린다.

### 기록에서 쓰는 항목 (기획서 1절)

| 항목 | 검토에서 쓰는 곳 |
| --- | --- |
| `noSource` | 근거 없이 답한 일반 답. 2-2 |
| `sources` | 근거 문서 경로 원문. 위키에 없는 경로(관리자 화면에서 회색)는 지어낸 근거 신호다 |
| `status`, `errorCode` | 실패·취소. 2-3 |
| `engine`, `model`, `ms` | 엔진별 실패율·응답 시간. 2-5 |
| `mode`, `intent`, `modeOverride` | 자동 판정 오판. 2-4 |
| `chatId`, `turnId` | 같은 질문의 엔진 넘기기 시도, 같은 대화의 앞뒤 턴 |
| `report.gaps` | 리포트가 스스로 밝힌 위키 빈칸. 2-2와 함께 본다 |
| `where` | `deploy`(Gemini만) / `local`(관리자 PC만, D1) |

### 기록의 한계 — 검토 결론을 낼 때 반드시 감안한다

- **배포는 Gemini만, 로컬 기록은 관리자 PC 것만 남는다**(D1). Claude·Codex·리포트 기록은 표본이 작고 관리자의 질문 습관에 치우친다.
- **배포에서는 취소가 잡히지 않는다.** 화면이 끊어도 `ok` 로 남을 수 있다(기획서 3절 "취소의 한계").
- **규칙 기반 답은 기록이 없다**(D5). 같은 `turnId` 의 시도가 모두 `fail` 이면 사용자는 규칙 기반 답을 받은 것이다.
- **답은 앞 1,500자, 리포트는 본문 없이 제목·요약·빈칸만** 남는다(D3). 리포트 본문의 잘못은 기록만으로 판단하지 않는다.
- **하루 상한 500건을 넘은 날은 내용 없이 건수만** 남는다(D2). 사용량 띠에 상한 초과가 보이면 그 주 통계는 일부라고 적는다.

## 2. 주 1회 검토 순서

순서는 "답을 못 받은 것 → 틀리게 답한 것 → 빈칸 → 판정"이다. 사용자 피해가 큰 것부터 본다.

### 2-1. 사용량 띠 (1분)

- 오늘 건수 / 하루 상한, 추정 용량 / 256MB, 이번 달 추정 명령 수 / 50만을 본다.
- 어느 하나라도 **70%를 넘었거나 상한 초과 건수가 있으면** 원인 분류 없이 바로 ops로 넘긴다(4절). 로그인 기능과 같은 저장소를 쓰기 때문이다.

### 2-2. 「근거 없이 답한 것만」 (`noSource`)

필터: 기간 7일 · 「근거 없이 답한 것만」 체크. 펼쳐서 답 본문을 읽고 셋 중 하나로 가른다.

| 가름 | 알아보는 법 | 다음 |
| --- | --- | --- |
| (가) 정상 — 근거가 필요 없는 답 | 편성표로 답했다(본문에 "Today B tv 편성표"처럼 편성표를 밝힘. 규약상 `sourcePaths` 를 비운다). 되묻기 한 줄, 방향만 한 줄 답, 인사, 범위 밖 안내 | 넘어간다. 세지 않는다 |
| (나) 없다고 바르게 답함 | "문서에 없다", "다시 물어봐 달라"로 답했다 | **위키 빈칸** 후보. 같은 주제가 몇 번 나왔는지만 센다 |
| (다) 근거 없이 내용을 단정함 | 정책·수치·절차·결재선을 근거 문서 없이 말했다 | **대화 규약** 위반(근거 규칙). 최우선. 위키에 실제로 그 내용이 있는지도 확인해 빈칸 여부를 함께 적는다 |

함께 본다.

- `noSource` 가 아니어도 **`sources` 에 회색(위키에 없는) 경로**가 있으면 (다)와 같게 본다. 엔진이 근거를 지어낸 것이다.
- 리포트 기록의 `report.gaps` 는 리포트가 스스로 밝힌 빈칸이다. (나)와 주제가 겹치면 위키 빈칸으로 묶는다.

### 2-3. 실패·취소 턴 (`status` = `fail` / `cancelled`)

필터: 결과 = 실패, 그다음 결과 = 취소. 목록은 턴 단위라 "Claude 실패 → Gemini"처럼 넘기기가 한 줄에 보인다.

| 보이는 것 | 뜻 | 분류 |
| --- | --- | --- |
| `errorCode: config` | 키 없음·번들 누락. 설정 문제 | **엔진 문제** → ops |
| 같은 `errorCode` 가 한 엔진에 몰림(시간 초과·한도 등) | 그 엔진의 상태 문제 | **엔진 문제** |
| 같은 `turnId` 의 시도가 **모두** 실패 | 사용자가 규칙 기반 답을 받았다(D5) | **엔진 문제**. 이 턴은 따로 센다 |
| 리포트 `timeout` 뒤 같은 질문이 `modeOverride: 'qa'` 로 다시 옴 | 리포트를 기다리다 짧은 답으로 돌렸다 | 2-4에서 함께 본다 |
| `cancelled` 뒤 같은 질문이 `modeOverride: 'qa'` 로 다시 옴 | 「그만하고 짧게 답 받기」를 눌렀다 | 2-4에서 함께 본다 |
| 특정 질문 모양에서만 실패(아주 긴 질문, 특정 문서를 묻는 질문 등) | 엔진이 아니라 입력·번들 문제일 수 있다 | 판단이 서지 않으면 **엔진 문제**로 두고 dev-server에 재현을 맡긴다 |

### 2-4. "짧게 답해줘"로 다시 물은 턴 — 자동 판정 오판 찾기

화면은 리포트 뒤 "짧게 답해줘"·「짧게 답 받기」·「그만하고 짧게 답 받기」를 모두 **같은 질문 + `modeOverride: 'qa'` 의 새 턴**으로 보낸다(`src/store/AppStore.tsx` 의 짧은 답 다시 보내기). 그래서 기록에서는 아래 모양으로 찾는다.

| 찾는 모양 (같은 `chatId`, 시간순) | 뜻 |
| --- | --- |
| 앞 턴 `mode: 'report'`(또는 `intent: 'report'` 로 실패·취소) → 다음 턴 같은 `q` + `modeOverride: 'qa'` | 리포트로 판정했지만 사용자는 짧은 답을 원했다. **과잉 판정** 후보 |
| 앞 턴 `mode: 'qa'` → 다음 턴 같은 `q` + `modeOverride: 'report'` | 짧게 답했지만 사용자는 리포트를 원했다. **과소 판정** 후보 |
| `intent: 'offer'` 뒤 다음 턴이 없음 | 리포트 제안 칩을 무시했다. 많으면 제안이 잦다는 신호 |
| 배포에서 `mode: 'report-unavailable'` 가 잦음 | 배포에서 리포트를 찾는 수요. 판정 오판이 아니라 안내 문구·사용처 문제다. PM 데스크에 경향만 알린다 |

- `modeOverride` 가 있는 턴은 자동 판정을 건너뛴 것이므로 오판 여부는 **앞 턴**의 `intent` 로 판단한다.
- 과잉·과소 판정이 같은 말투에서 반복되면 **판정 오판**으로 분류한다(3절). 한두 번이면 메모에 남기고 다음 주에 다시 본다.
- 다시 물은 턴의 답 자체가 틀렸으면 그건 2-2·2-6의 대상이다. 판정 오판과 따로 센다.

### 2-5. 엔진별 실패율

필터: 엔진을 하나씩 바꿔 가며 결과를 본다. 시도 단위(기록 1건 = 엔진 1회 시도)로 센다.

| 보는 값 | 계산 |
| --- | --- |
| 시도 수 | 그 엔진 기록 건수 |
| 실패율 | `fail` 건수 ÷ 시도 수 |
| 취소율 | `cancelled` 건수 ÷ 시도 수 (로컬만 의미 있음) |
| 느린 응답 | `ms` 가 긴 쪽 몇 건의 모드·질문 길이 |
| 주된 실패 코드 | `errorCode` 별 건수 |
| 예비 모델로 넘어간 비율 | `model` 이 기록된 경우만 |

- **시도 20건 미만인 엔진은 판단을 미룬다.** 메모에 "표본 적음"이라고만 쓴다.
- 배포(Gemini)와 로컬(관리자 PC)의 수치를 한 줄로 비교하지 않는다. 쓰는 사람·질문 종류가 다르다.
- 실패율이 전주보다 뚜렷이 오르거나 한 엔진에 실패 코드가 몰리면 **엔진 문제**로 분류한다.

### 2-6. 성공 턴 표본 — 상품 유형 섞임 확인

`noSource` 도 실패도 아닌 답이 이 챗봇의 최대 결함(상품 유형 혼동)을 숨긴다. 자동 표시가 없으니 사람이 본다.

- 지난 7일 성공 턴에서 **5건**을 고른다. 질문에 PPV·PPM·B tv+ 중 하나가 들어간 것을 먼저 고른다.
- 확인하는 것.
  - PPV 질문의 답에 PPM 전용 정책(전환 동의·자동 해지·약정)이 섞였는가
  - "그 외 월정액" 질문의 답에 B tv+ 전용 줄(Today B tv+ 배너, B tv+ 타겟 그룹 등)이 섞였는가
  - 같은 `chatId` 에서 어시스턴트가 되물은 상품 유형("월정액인가요?")이 사용자 답 없이 조건으로 굳었는가
  - 문서의 과거 사례 금액·날짜·카피가 현재 건의 값처럼 쓰였는가
  - `**아직 못 채운 것** —`·`(보완 필요)` 줄을 답으로 인용했는가
  - 답 형식(결론부터, 표·제목·코드블록 없음, 목록 `· `)을 지켰는가
- 하나라도 걸리면 **대화 규약**으로 분류한다. 근거 문서가 상품을 섞어 적어 생긴 일이면 **위키 빈칸**(문서 정리)을 함께 붙인다.

## 3. 원인 분류

한 턴은 하나의 주 원인을 갖는다. 둘 이상이면 아래 판정 순서에서 먼저 걸리는 것을 주 원인으로, 나머지를 부 원인으로 적는다.

### 판정 순서

1. 답을 받지 못했나(`fail`·`cancelled`, 모두 실패해 규칙 기반 답) → **엔진 문제**
2. 모드가 틀렸나(2-4의 다시 물은 모양) → **판정 오판**
3. 위키에 답이 있나
   - 없다 → **위키 빈칸**. 챗봇이 내용을 지어냈으면 **대화 규약**을 부 원인으로 붙인다
   - 있다, 그런데 답이 틀렸거나 섞였거나 형식을 어겼다 → **대화 규약**
   - 있다, 그런데 다른 엔진으로는 바르게 답한다 → **엔진 문제**(엔진별 품질 차이)

### 분류표

| 분류 | 정의 | 대표 신호 | 넘기는 담당 |
| --- | --- | --- | --- |
| 위키 빈칸 | 위키에 그 내용이 없거나, 있어도 상품 유형을 섞어 적었거나, 문서끼리 어긋난다 | 2-2 (나), `report.gaps`, 같은 주제의 "문서에 없다"가 반복 | ops (문서 보완) |
| 대화 규약 | 위키에 근거가 있는데 답이 근거 규칙·상품 유형 규칙·되묻기 규칙·형식 규칙·`ax-campaign` 규약을 어겼다 | 2-2 (다), 회색 근거 경로, 2-6 걸림 | chatbot-planner (`server/assistant-prompt.md` 수정) |
| 판정 오판 | 서버의 리포트 자동 판정(`server/knowledge.ts` 의 `detectReportIntent` — 리포트 신호·짧은 답 신호·판단 요청 신호·수정 요청 신호)이 사용자 의도와 다르게 갈랐다 | 2-4 과잉·과소 판정이 같은 말투에서 반복 | dev-server (판정 신호 조정) |
| 엔진 문제 | 엔진·모델·설정 때문에 답을 못 받았거나 품질이 엔진마다 다르다 | 2-3, 2-5 | 설정·키·한도는 ops, 코드(제한 시간·넘기기·응답 파싱)는 dev-server |

헷갈리기 쉬운 경우.

- 사용자가 문서와 다른 말을 썼는데(예: "진행 절차" ↔ "프로모션 운영 프로세스") "문서에 없다"고 답했다 → 위키 빈칸이 아니라 **대화 규약**(용어 동치 규칙). 같은 말 바꿈이 여러 문서에서 반복되면 ops에 문서 용어 정리를 부 원인으로 붙인다.
- 편성표 범위 밖 날짜를 물어 "없다"고 답했다 → 정상. 분류하지 않는다. 편성표가 늦게 갱신된 것이 원인이면 ops에 알린다.
- 리포트 본문의 오류는 기록에 본문이 없어 판정하지 않는다. 사용자 문의로 들어오면 사용자가 저장한 `.md` 를 받아 본다.

### 넘기는 길

```
관리자(주간 검토) → PM 데스크 → 담당 에이전트 → PM 데스크 → 반영 확인(5절 다음 주 검토)
```

관리자는 담당에게 직접 넘기지 않는다. 주간 검토 메모를 PM 데스크에 주고, PM 데스크가 CLAUDE.md 절차대로 나눈다. 같은 파일을 건드리는 일(예: 규약 수정 두 건)은 한 번에 하나씩 보낸다.

### 넘길 때 적는 칸 (모두 6절 공개 규칙을 지킨 문장으로)

| 칸 | 쓰는 법 |
| --- | --- |
| 분류 | 위키 빈칸 / 대화 규약 / 판정 오판 / 엔진 문제 (부 원인이 있으면 함께) |
| 경향 | 원문 없이 한 문장. "PPV 질문 답에 PPM 해지 조건이 섞인 사례가 이번 주 여러 건" |
| 규모 | "한 번", "여러 건", "지난주보다 늘었다" 같은 표현. 정확한 건수·비율은 쓰지 않는다 |
| 관련 위치 | 위키 문서 경로(`promotion/playbook.md` 등), 규약 절 이름("근거 규칙"), 판정 신호 이름. 이건 이미 공개된 것이라 써도 된다 |
| 기대 동작 | 챗봇이 어떻게 답했어야 하는지 한 줄 |
| 재현 질문 | **지어낸 질문** 1~3개. 원문의 구조(상품 유형·질문 종류·대화 순서)만 살리고 고유명사·수치·문구를 바꾼다 |
| 다시 찾는 법 | 관리자 화면 필터 조건(기간·엔진·모드·결과·근거 없음). 기록 ID·`chatId`·로그인 ID는 쓰지 않는다 |

## 5. 반영 확인

| 단계 | 하는 일 | 끝내는 기준 |
| --- | --- | --- |
| 1. 기준선 남기기 | 넘길 때 주간 검토 메모에 "이 경향이 지난 7일에 어느 정도였는지"를 경향 표현으로 적는다. 기록은 90일 뒤 사라지므로 비교 기준을 메모에 남긴다 | 메모에 기준선이 있다 |
| 2. 반영 | 담당 PR이 머지되고 배포된 날을 메모에 적는다. 위키 문서는 승인 뒤 다음 배포에서 반영된다 | 배포일이 있다 |
| 3. 재현 질문 다시 묻기 | 배포 허브에서 재현 질문(지어낸 것)을 그대로 물어 기대 동작대로 답하는지 본다. 로컬 엔진 문제였으면 관리자 PC 로컬 허브에서 묻는다 | 재현 질문이 모두 기대대로 답한다 |
| 4. 다음 두 번의 주간 검토 | 배포일 뒤 기간으로 필터를 걸어 같은 경향이 다시 나오는지 본다 | **2주 연속 다시 보이지 않으면 닫는다** |
| 5. 다시 나오면 | 분류를 다시 한다. 같은 분류로 두 번 실패했으면 PM 데스크에 검토 요청 표로 올린다(예: 규약으로 안 막히니 판정 신호나 문서 구조로 옮길지) | PM 데스크 결정 |

- 다른 변경이 같은 주에 함께 배포되면 어느 변경이 효과를 냈는지 메모에 "함께 배포됨"이라고 적는다.
- 고친 뒤 **다른 곳이 깨졌는지**도 본다. 규약 수정 뒤에는 2-6 표본을 평소보다 늘려(10건) 한 번 본다.

## 6. 공개 저장소로 옮길 때의 규칙

기록은 Redis에만 있고 관리자 화면 밖으로 나가지 않는다(기획서 7절). 기록에서 찾은 문제를 **이슈·PR·커밋 메시지·`docs/`·위키 문서**로 옮길 때는 아래를 지킨다.

### 빼는 것

| 빼는 것 | 이유 |
| --- | --- |
| 질문·답 원문, 원문을 조금 바꾼 문장 | 원문에 제휴사명·금액·내부 일정이 섞여 있을 수 있다 |
| 제휴사 실명, 채널·콘텐츠 계약 상대 이름 | 공개 저장소 규칙 |
| 매출·단가·할인 금액, 실적 수치 | 공개 저장소 규칙. 인사이트는 수치 대신 경향 |
| 사용자 로그인 ID·이름·팀 | 누가 물었는지는 개선에 필요 없다 |
| 기록 ID·`chatId`·`turnId`·정확한 시각 | 공개 문서에서 특정 대화를 가리키지 않는다. 다시 찾을 때는 필터 조건을 쓴다 |
| 정확한 건수·비율 | "여러 건", "대부분", "늘었다"로 쓴다 |
| 오류 원문·서버 로그 원문 | 기록에도 없는 값이다. 다른 곳에서 가져와 붙이지 않는다 |

### 남겨도 되는 것

- 위키 문서 경로, 문서 코드, 규약 절 이름, 판정 신호 이름, 엔진 이름, `errorCode` 분류 이름.
- 상품 유형(PPM·PPV·B tv+)과 질문 종류(절차·판단·결과물·기획 상담).
- 지어낸 재현 질문.

### 예시 (모두 지어낸 것)

| 나쁜 예 | 좋은 예 |
| --- | --- |
| "사용자가 'OO제휴사 [금액] 쿠폰 결재 누가 해?'라고 물었는데 근거 없이 팀장 전결이라고 답함" | "PPV 쿠폰 결재선 질문에 근거 문서 없이 결재 단계를 단정한 사례가 이번 주 여러 건. 위키에 PPV 결재선 항목이 없음 → 위키 빈칸 + 대화 규약(근거 규칙)" |
| "kim 계정이 11/18 14:02에 물은 턴(cl_xxxx)에서 PPM 해지 조건이 섞임" | "PPV 영화 프로모션 질문 답에 PPM 전용 자동 해지 조건이 섞임. 근거는 `promotion/playbook.md` 의 상품 혼합 표. 재현 질문: '단편 영화 PPV 첫 주 할인 배너 어떻게 해요?'" |
| "Gemini 실패율 23.4% (47건 중 11건)" | "배포 Gemini에서 시간 초과 실패가 지난주보다 늘었다. 다른 실패 코드는 비슷하다" |
| "'짧게 답해줘'로 다시 물은 질문: '[제휴사] 월정액 이번 달 실적 비교해줘'" | "'비교' 한 단어만 들어간 짧은 사실 질문이 리포트로 판정돼 사용자가 짧은 답으로 다시 물은 경우가 반복됨 → 판정 오판(리포트 신호 가중치). 재현 질문: 'PPV랑 PPM 쿠폰 차이 비교해줘'" |


## 7. 2차 👍/👎 평가 버튼에 넘길 요구사항

평가 버튼은 2차 범위다(확정 조건 2). 이 절차를 돌리면서 필요해진 것을 미리 적는다. 2차 기획(plan-pm) 때 이 표를 입력으로 쓴다.

| # | 요구 | 이유 |
| --- | --- | --- |
| R1 | 평가는 기록의 **`turnId`(와 `chatId`)에 붙인다.** 엔진 넘기기가 있었으면 그 턴의 마지막 성공 기록에 붙는다 | 기획서 범위 밖 표의 약속. 검토가 턴 단위다 |
| R2 | 서버 기록이 있는 답에만 버튼을 보인다. 규칙 기반 답과 되묻기 칩에는 보이지 않는다 | 규칙 기반 답은 기록이 없다(D5). 붙일 곳이 없다 |
| R3 | 👎을 누르면 이유를 **고정 선택지 하나**로 받는다. 선택지는 원인 분류와 맞춘다. "문서와 다름" · "다른 상품 얘기가 섞임" · "문서에 없는데 지어냄" · "원하는 답 길이가 아님" · "기타" | 3절 분류로 바로 이어진다. "다른 상품 얘기가 섞임"은 2-6을 사람 표본에서 사용자 신고로 넓힌다 |
| R4 | 자유 입력은 두지 않거나, 두더라도 100자 이내·Redis에만·관리자만 본다 | 자유 입력에는 제휴사명·금액이 들어간다. 기록 원문과 같은 보호를 받아야 한다 |
| R5 | 한 사용자는 한 턴에 하나만 평가하고 바꿀 수 있다. 취소도 된다 | 실수 클릭이 통계를 흐리지 않게 |
| R6 | 관리자 "대화 기록" 화면에 「👎만」 필터와 목록 줄의 평가 표시를 둔다. 「근거 없이 답한 것만」과 함께 걸 수 있다 | 주간 검토 2-2·2-6의 우선 대상이 된다 |
| R7 | 평가 저장은 기록과 같은 규칙을 따른다. 90일 만료, 답 경로를 막지 않음, 실패해도 화면에 오류를 띄우지 않음, 저장 1건 명령 3개 이하 | 무료 한도와 로그인 기능 보호(기획서 2절) |
| R8 | 리포트 카드에도 버튼을 둔다. 👎 선택지에 "리포트가 필요 없었음"을 더한다 | 2-4 과잉 판정을 사용자 신호로도 잡는다 |
| R9 | 사용자 "내 대화 기록"에서 본인 평가가 보인다. 다른 사람의 평가 수는 보이지 않는다 | 다른 사람 평가가 판단을 끌지 않게 |
| R10 | 평가 통계도 공개 저장소로 옮길 때는 6절 규칙을 따른다(비율 대신 경향) | 공개 원칙 |
