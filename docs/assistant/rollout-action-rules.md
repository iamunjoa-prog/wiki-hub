기준 `docs/plan/2026-11-20-rollout-wiki-contribution-review.md` 2-3절, 5절 1단계 chatbot-planner 행, 6절 "2026-11-20 확정"(D7 ① 요청 안내만, 0-1절 팀 계정 4개 + 관리자 1개).

## 0. 지금 규약에서 찾은 문제 (재현)

실제 엔진은 돌리지 않았다. 지금 `server/assistant-prompt.md` 문장과 `server/knowledge.ts`·`server/edit-prompt.md` 동작을 대조해 오답 경로를 적었다.

| # | 질문 (지어낸 예) | 지금 규약에서 나올 수 있는 오답 | 원인이 된 지금 문장 |
| --- | --- | --- | --- |
| R1 | "제휴 쿠폰 분류 하나 새로 추가해줘" | `new` 초안을 만들고 `subcategory` 에 목록에 없는 값을 지어 넣는다. 서버 `isKnownPlace` 가 거절해 카드 제출이 실패한다 | 판단 기준 "문서를 **고치거나 추가하거나** 남겨 달라는 말이 있으면 지식 입력·수정이다" → 1절 "처음 걸리는 단계에서 멈춘다"의 3·5단계(`new`)에서 멈춘다. "카테고리 신설은 `none`" 문장은 **그 뒤 5절**에 있어 닿지 않는다 |
| R2 | "「주말 쿠폰 안내 (PPC-Z-01)」 제목을 '주말 특가 안내'로 바꿔줘" | `edit` 초안이 나온다. 수정 제안은 본문만 바꾸고 프론트매터 제목은 그대로 둬서, 사용자는 제목이 바뀐다고 믿고 제출한다 | 1절 4단계 "고칠 문서가 정해졌다 → `edit`". 5절은 "삭제·이동·카테고리 신설"만 `none` 으로 두고 **제목·적용 상품 바꾸기는 빠져 있다** |
| R3 | "이 PPM 문서를 PPV 문서로 바꿔줘" | `edit` 의 `instruction` 이 "PPV 기준으로 고쳐라"가 되어, 편집 도우미가 PPM 본문(전환 동의·자동 해지)을 PPV 문서처럼 다시 쓴다. **상품 유형 혼동이 초안에 박힌다** | R2와 같다. 적용 상품 바꾸기는 `scope` 프론트매터 변경인데 `edit` 으로 흘러간다 |
| R4 | "PPM 안내 문서에 '주의사항' 섹션 추가해줘" | "대화로는 문서 수정과 새 문서 초안만 만들 수 있습니다."로 거절한다. 실제로는 본문 소제목 추가라 `edit` 이 맞다 | "섹션"이 메뉴 분류인지 문서 안 소제목인지 가르는 기준이 없다 |
| R5 | "문서 삭제 요청은 어디에 해?" | 요청 경로가 위키에 없는데 "관리자에게 메일로 요청하세요"처럼 일반 지식으로 채운다 | 거절 문장에 요청 방법이 없고, 기댈 문서도 아직 없다 |

R1~R3은 **문장을 더해서가 아니라 자리를 옮기고 범위를 맞춰서** 막는다(변경안 A-1). R5는 요청 안내 문서가 생긴 뒤에만 막을 수 있다(A-2).

## 1. 지금 규약 유지 확인과 답 문장 (변경안 A)

### 유지하는 것

- 삭제·이동·분류 신설은 **`action.type: none`** 을 유지한다. `REPLY_SCHEMA` 의 enum(`none`·`edit`·`new`)은 그대로다. D7 ①(상용화 전엔 요청 안내만)과 맞는다.
- 제출은 사람만 한다는 원칙, 쓰지 않는 말 목록, 가림 규칙은 그대로다.

### A-1. 구조 요청을 1절 맨 앞으로 옮긴다 (문장 이동, 범위 보강)

지금 5절의 한 줄을 지우고, 1절 "의도는 다섯 단계로 가린다" 맨 앞에 0단계로 둔다. 단계를 위에서부터 보고 처음 걸리는 곳에서 멈추므로, 0단계에 있어야 `new`·`edit` 보다 먼저 걸린다.

**지울 문장 (5절)**

> · 문서 삭제·이동·카테고리 신설은 `none`이고 "대화로는 문서 수정과 새 문서 초안만 만들 수 있습니다." 한 줄로 답한다.

**넣을 문장 (1절 0단계)**

> 0. **위키 구조를 바꿔 달라고 했다** — 문서 삭제, 문서 이동(다른 분류로 옮기기, 제목·적용 상품 바꾸기), 카테고리·서브메뉴 신설 → `none`. 아래 **구조 요청** 문장으로 답한다. 문서 **안의** 줄·소제목을 지우거나 더하는 것은 구조 요청이 아니다 — 1단계부터 본다.

판단 기준(발화 유형 절)의 첫 줄도 "문서를 고치거나 추가하거나 남겨 달라는 말" 뒤에 "(위키 구조 변경은 지식 입력·수정 1절 0단계)"만 덧붙인다. 새 규칙을 만드는 게 아니라 R1의 갈림길을 한 곳으로 모으는 것이다.

**"섹션"·"분류"를 가르는 기준** (R4)

| 사용자가 가리킨 것 | 판정 |
| --- | --- |
| 특정 문서를 말하고 그 안에 "섹션·항목·소제목"을 더하거나 지운다 | 문서 안 변경 → `edit` (1단계부터) |
| 문서를 말하지 않고 "분류·메뉴·카테고리·폴더"를 새로 만든다 | 구조 요청 (분류 신설) |
| "섹션"만 말하고 문서도 메뉴도 안 짚었다 | 구조 요청으로 보지 않는다. 1절 5단계(기존 문서에 넣을까요, 새 문서로 만들까요)로 간다 |

### A-2. 구조 요청의 답 문장

**끝에 "요청 방법" 안내를 붙인다.** 단 **요청 안내 문서가 main에 머지된 뒤**에만 이 문장을 프롬프트에 넣는다. 문서가 없는데 안내를 붙이면 근거 없는 경로를 말하게 된다(R5).

요청 안내 문서는 requests-planner·wiki-ux가 만드는 중이라 아래는 **가칭**이다.

| 항목 | 가칭 |
| --- | --- |
| 문서 제목 | 「분류 추가·문서 삭제·이동 요청 방법」 |
| 문서 코드 | `HUB-07` (이용 안내의 다음 번호, 확정 아님) |
| 경로 | `guide/structure-request.md` |

**문장 (삭제·이동)**

> 문서 삭제와 이동은 대화로 할 수 없고, 요청을 받아 관리자가 처리합니다.
> 요청 방법은 「분류 추가·문서 삭제·이동 요청 방법 (HUB-07)」에 정리돼 있습니다.

**문장 (제목·적용 상품 바꾸기)** — 이동의 한 종류로 같은 문장을 쓰되 첫 줄만 바꾼다.

> 제목과 적용 상품은 수정 제안으로 바꿀 수 없고, 요청을 받아 관리자가 처리합니다.
> 요청 방법은 「분류 추가·문서 삭제·이동 요청 방법 (HUB-07)」에 정리돼 있습니다.

**연결 위치**

- 본문 둘째 줄에 문서 제목과 코드를 적는다. 지금 규약의 "다시 물어볼 문서 코드처럼 규칙이 문서를 짚으라고 한 곳"에 이 문장을 더한다(읽히게 쓴다 절의 예외 목록).
- `sourcePaths` 에 그 문서 경로(`guide/structure-request.md`)를 담는다. 이 답의 근거가 그 문서이므로 근거 규칙에 맞고, 화면의 근거 문서 표시가 곧 링크가 된다.
- 그 문서에 적힌 절차를 본문에 옮겨 쓰지 않는다. 받는 사람·양식은 문서가 말한다. 5줄 규칙과 "문서에 없는 것은 말하지 않는다"를 함께 지킨다.

**요청 안내 문서가 생기기 전(지금~4단계)** 은 지금 문장 "대화로는 문서 수정과 새 문서 초안만 만들 수 있습니다." 한 줄을 그대로 쓴다. A-1(자리 옮기기·범위 보강)만 먼저 반영해도 된다.

**쓰지 않는 말에 더한다**: "요청했습니다", "관리자에게 전달했습니다", "삭제했습니다", "옮겼습니다". 어시스턴트는 요청을 대신 넣지 않는다.

### 이 변경으로 막히는 오답

- R2 "제목 바꿔줘" → 지금은 `edit` 초안(제목은 안 바뀜). 변경 후 `none` + 위 문장.
- R3 "이 PPM 문서를 PPV로 바꿔줘" → 지금은 PPM 본문을 PPV처럼 고쳐 쓰는 `edit`. 변경 후 `none` + 위 문장. **PPM 정책이 PPV 문서로 둔갑하는 경로가 닫힌다.**
- R5 "삭제 요청 어디에 해?" → 지금은 일반 지식으로 채울 수 있다. 변경 후 요청 안내 문서를 근거로 짚는다.

## 2. 분류(섹션) 추가 요청의 답 규약

D7 ①에 따라 분류 신설은 상용화 전에도 후에도(메뉴 정의를 한 파일로 모으기 전까지) 대화로 만들지 않는다.

| 경우 | `action.type` | 답 |
| --- | --- | --- |
| 분류만 만들어 달라고 했다 ("제휴 쿠폰 분류 새로 만들어 줘") | `none` | 아래 두 줄 |
| 분류를 만들고 **그 안에 넣을 내용까지** 말했다 ("제휴 쿠폰 분류 만들고 이 내용 넣어줘: …") | `new` | 가장 가까운 기존 서브메뉴에 새 문서 초안을 만든다. 분류는 따로 요청하라고 한 줄 붙인다 |
| 이미 있는 분류 이름과 같은 걸 만들어 달라고 했다 | `none` | 있는 분류 이름을 한 줄로 밝힌다. 만들지 않는다 |

**문장 (분류만)**

> 새 분류는 대화로 만들 수 없고, 요청을 받아 관리자가 추가합니다.
> 요청 방법은 「분류 추가·문서 삭제·이동 요청 방법 (HUB-07)」에 정리돼 있습니다.

**문장 (내용까지)** — 지금 규약 4절 "초안 턴의 본문"을 따르되 첫 줄에 이유를 붙인다.

> 새 분류는 만들 수 없어, 새 문서 「제휴 쿠폰 운영 기준」 초안을 프로모션 › 운영 참고자료에 잡았습니다.
> 아래 카드에서 위치를 확인하고 **[제안 제출]**을 눌러 주세요.
> 분류 신설 요청 방법은 「분류 추가·문서 삭제·이동 요청 방법 (HUB-07)」에 있습니다.

규칙

- `subcategory` 는 지금 목록(`start`·`policy`·…·`free`) 안에서만 고른다. 사용자가 말한 새 분류 이름을 `subcategory` 에 넣지 않는다(R1).
- 위치를 묻지 않는다. 지금 규약대로 어시스턴트가 고르고 사용자가 카드에서 바꾼다. `ax-campaign` 의 "추론해서 먼저 제안" 원칙과 같다.
- 사용자가 말한 분류 이름은 초안 제목에 그대로 쓰지 말고, 내용을 보고 명사형 제목을 짓는다.

**막히는 오답**: R1. 지금은 `subcategory: 'partner-coupon'` 같은 지어낸 값으로 `new` 를 만들고 제출에서 실패한다. 변경 후 `none`, 또는 기존 서브메뉴에 `new`.

## 3. 상용화 후 `delete`·`move` 초안 규약 (변경안 B, 초안)

전제: 기획서 2-3절 "챗봇 삭제를 되게 하려면" 1~3번이 먼저 끝나 있다 — 사람이 화면에서 삭제·이동 제안을 할 수 있고, 승인 목록이 종류를 구분하고, dev-server가 `REPLY_SCHEMA` enum에 `delete`·`move` 를 더했다. 그 전에는 이 절을 프롬프트에 넣지 않는다.

### 3-1. 기준이 되는 원칙

| `ax-campaign` 규약 | 삭제·이동에서 |
| --- | --- |
| 결론부터 | 첫 줄은 "「제목 (코드)」 삭제 초안입니다." |
| 과정 중계 금지 | "링크를 찾아보겠습니다"를 쓰지 않는다. 가리키는 문서 수는 카드가 보인다 |
| 이미 들은 것을 다시 묻지 않는다 | 사용자가 말한 대상·사유는 다시 묻지 않는다. 되묻기는 항목당 한 번, 카드 전 최대 두 번(지금 규약 2절 그대로) |
| 추론해서 먼저 제안, 잡은 것을 되짚어 확인 | 대상을 추론했으면 첫 줄에 제목과 코드를 밝혀 사용자가 바로잡을 수 있게 한다. 확인은 카드가 한다 |
| 문서에 없으면 없다고 | 대체 문서·사유를 지어내지 않는다 |
| 고친 척하지 않는다 | "삭제했습니다", "옮겼습니다" 금지. 제출은 카드 버튼뿐 |

### 3-2. 언제 초안을 만드나

지금 1절 0단계(구조 요청)를 아래처럼 나눈다. 분류 신설은 계속 `none`(2절).

| 발화 | 판정 |
| --- | --- |
| "「…」 지워줘", "이 문서 없애줘", "폐지됐으니 내려줘" | `delete` |
| "「…」를 운영 참고자료로 옮겨줘", "제목을 …로 바꿔줘", "적용 상품을 공통으로 바꿔줘" | `move` |
| 문서 안의 줄·소제목을 지우거나 옮긴다 | `edit` (구조 요청 아님) |
| "A 내용을 B에 합치고 A는 지워줘" | 이번 턴 `edit`(B에 더하기). 본문에 "A 삭제는 이 제안을 낸 뒤 이어서 말해 주세요." 한 줄. **삭제를 먼저 만들지 않는다** — 먼저 지우면 옮길 내용이 사라진다 |
| 묻기만 ("이 문서 지울 수 있어?") | 사실 질문. 이용 안내 문서로 답하고 `none` |

한 턴에 초안은 하나다. 문서 여러 개를 지워 달라고 하면 첫 문서만 초안을 만들고 나머지 제목을 한 줄로 밝힌다.

### 3-3. 대상 정하기와 되묻기

삭제는 되돌리기 어렵고 승인자도 내용보다 제목을 보고 넘기기 쉽다. 그래서 **대상만큼은 수정보다 좁게** 정한다.

- 대상이 정해진 경우는 셋뿐이다: 사용자가 제목·코드를 말했다 / "이 문서"라고 했고 직전 답의 근거 문서가 하나다 / 사용자가 연 문서 화면에서 물었다(화면이 경로를 넘길 때).
- 그 밖에는 후보를 최대 3개 `· 제목 (코드)` 줄로 보이고 한 번 묻는다. **바꿀 값이 적힌 문서가 하나뿐이라는 이유로 삭제 대상을 고르지 않는다**(수정 4단계와 다른 점).
- **상품 유형**: "PPV 쿠폰 문서 지워줘"에서 `promotion/ppm.md` 를 후보에 올리지 않는다. 어시스턴트가 되물은 상품은 조건이 아니다.
- **상품이 섞인 문서**(플레이북·인사이트처럼 PPM·PPV·B tv+를 한 문서에 담은 글)를 지우려 하면, 첫 줄 뒤에 "이 문서는 PPV 외에 PPM, B tv+ 줄도 담고 있습니다." 한 줄을 붙인다. 사용자가 한 상품 줄만 빼려던 것이면 `edit` 으로 바꾸면 된다는 뜻이다. 이 경고는 묻는 턴을 쓰지 않는다(카드 전 되묻기 횟수에 안 센다).
- 물을 수 있는 항목은 지금처럼 **대상·내용·근거** 셋이다. 삭제의 **내용**은 "왜 없어지나 + 대신 볼 문서", 이동의 **내용**은 "어디로·무엇으로 바꾸나"다. 내용이 비면 한 번 묻고, 답이 없으면 비워 둔 채 초안을 만든다(카드에서 사유를 받는다 — requests-planner 몫).
- 근거만 물으려고 한 턴을 쓰지 않는 규칙은 그대로다.

### 3-4. `action` 칸 (지금 형식 재사용)

새 칸을 만들지 않고 지금 칸을 쓴다. 쓰지 않는 칸은 `''`.

| 칸 | `delete` | `move` |
| --- | --- | --- |
| `type` | `delete` | `move` |
| `docPath` | 지울 문서 경로. `<document path>` 그대로 | 옮길 문서 경로 |
| `reason` | 사용자가 밝힌 삭제 사유와 대신 볼 문서. 없으면 `''` | 사용자가 밝힌 이유. 없으면 `''` |
| `category`·`subcategory` | `''` | **바뀌는 경우만** 새 값. 지금 목록 안에서만. 목록에 없는 곳으로 옮기라면 `move` 를 만들지 않고 2절(분류 신설)로 |
| `title` | `''` | 바뀌는 경우만 새 제목 |
| `scope` | `''` | 바뀌는 경우만. 사용자가 **직접 말한** 상품만 쓴다 |
| `instruction`·`body` | `''` | `''` — 본문은 건드리지 않는다 |

- `sourcePaths` 에는 `docPath` 만 담는다.
- **적용 상품 바꾸기**: 본문에 원래 상품 전용 정책(PPM의 전환 동의·자동 해지·약정)이 있으면 첫 줄 뒤에 "본문에 PPM 전용인 전환 동의 내용이 남아 있어, 적용 상품만 바꾸면 내용과 어긋납니다." 한 줄을 붙인다. 본문을 대신 고치지 않는다(R3 재발 방지).

## 4. 팀 계정(4팀)이 대화 규약에 주는 영향

계정이 팀 단위라 PR·내 요청·대화 기록에 남는 "누가"는 팀 이름까지다(기획서 0-1절, D4 작업 없음). 챗봇은 지금도 질문자 이름·팀을 받지 않는다(`AskInput` 에 없음). 그래서 규약 변경은 작다.

| 영향 | 규약 |
| --- | --- |
| 질문자를 모른다 | "○○님이 요청하신", "○○팀 문서라서" 같은 말을 쓰지 않는다. 문서의 `updatedBy` 가 팀 이름이어도 "작성한 팀에 물어보세요"로 사람을 짚지 않는다. 지금 규약에 문장을 더할 필요는 없다(근거 규칙으로 막힌다) |
| 사유가 유일한 사람 흔적이 된다 | 삭제·이동 승인자는 PR에서 팀 이름만 본다. 그래서 상용화 후 `delete`·`move` 의 사유를 **내용** 항목으로 올렸다(3-3). 사유에 사람 이름이 나오면 지금 가림 규칙(`김*수 팀장`)을 그대로 쓴다 |
| 요청 상태 질문 | "우리가 낸 삭제 요청 어떻게 됐어?"에 챗봇은 상태를 모른다. 이용 안내 문서에 적힌 범위에서 "내 요청 화면에서 볼 수 있다"까지만 답하고, 그 화면에 팀 계정 요청이 함께 보인다는 말은 **문서에 적혀 있을 때만** 쓴다 |
| 대화 이력 | 대화 기록 화면은 팀원끼리 보이지만 그 대화를 이어 묻는 기능은 없다(`docs/ux/2026-11-20-chat-history.md` "이어 묻기 없다"). 그래서 "이미 들은 것"은 지금처럼 **같은 대화창 안**에서만 사실이다. 다른 팀원이 앞서 한 말을 조건으로 삼는 경로는 없다 — 이어 묻기가 생기면 다시 본다 |
