# 챗봇 대화 초안 카드 — 문구·진입 표시·PR 본문 (1단계)

작성 `requests-planner` · 2026-11-13 · 기획안 `docs/plan/2026-11-13-chat-doc-draft-and-attachments.md` 차례 1-1
확정 전제(상위 지시자): 반영은 PR 승인(머지) 경유 유지. 제휴사 실명은 1차에 패턴 경고만 한다(제출을 막지 않음).
2단계(첨부 안내·오류 문구)는 이 문서에 절을 덧붙인다(차례 2-1).

이 문서는 문구와 규칙만 정한다. 코드는 dev-server·dev-front 가 옮긴다. 아래 `「」` 안이나 코드 칸 안의 문자열은 **그대로** 옮긴다. `{ }` 는 채워 넣는 값이다.

## 1. 지금 실제로 일어나는 일 (문구의 근거)

| 순간 | 실제 동작 | 근거 |
| --- | --- | --- |
| 카드가 뜰 때 | 아무것도 저장되지 않는다. 초안은 이 브라우저의 대화 기록에만 있다 | 기획안 "방치" |
| [제안 제출] 수정 | `/api/proposeEdit` → main 버전과 `baseVersion` 비교(다르면 409) → 새 브랜치 `docs/edit-{코드}-…` → 파일 1개 커밋 → PR 열림 | `server/github.ts` `createEditPR` |
| [제안 제출] 새 문서 | `/api/createDoc` → 코드 자동 부여 → 새 브랜치 `docs/{코드}-…` → 파일 1개 커밋 → PR 열림 | `server/github.ts` `createDocPR` |
| PR 이 열린 순간 | **공개 저장소에 바로 올라간다.** 반려(닫힘)돼도 브랜치·PR diff 는 남는다 | 공개 저장소 |
| 머지 | main 에 들어간다. 위키 화면은 **다음 배포 전까지 그대로**다 | `MyRequests.tsx` 안내, `ProposeEdit.tsx` 완료 화면 |
| 내 요청 목록 | GitHub PR 50건을 읽는다. 허브 진입 후 **한 번만** 읽고, 그 뒤엔 [새로고침] 을 눌러야 다시 읽는다 | `AppStore.tsx` `ensureProposals`·`refreshProposals` |
| 승인 | 허브에 승인 버튼은 없다. GitHub PR 화면에서 머지한다 | `Approvals.tsx` |

그래서 카드는 "반영했습니다"·"수정했습니다"를 쓰지 않는다. 제출 뒤에 쓸 수 있는 말은 "제안을 올렸습니다"까지다.

## 2. 상태 이름 — 한 가지로 쓴다

내 요청 화면의 현재 태그(`MyRequests.tsx` `PrStatusTag`)를 기준으로 카드·PR 본문·안내가 같은 말을 쓴다.

| 단계 | 저장소에서 | 내 요청 태그 (현행 유지) | 카드·안내에서 부르는 말 |
| --- | --- | --- | --- |
| 초안 | 없음 (브라우저에만) | 안 뜸 | 초안 |
| 제출 | PR 열림 | `대기 중` | 제안을 올렸습니다 · 대기 중 |
| 머지 | main 에 들어감 | `머지됨` | 승인(머지)됨 · 다음 배포 때 위키에 반영 |
| 다음 배포 반영 | 배포됨 | (구분 못 함, `머지됨` 그대로) | 위키에 반영됨 |
| 반려 | PR 닫힘(머지 없이) | `닫힘` | 반려(닫힘) |

규칙
- 본문에서는 "제안·승인·반영"을 쓰고, "PR·머지"는 괄호나 버튼 옆 보조 설명으로만 쓴다.
- "승인" 뒤에는 항상 "다음 배포 때 위키에 반영"을 붙인다. 승인 = 바로 반영으로 읽히지 않게 한다.
- 이 문서는 내 요청 태그 이름을 바꾸지 않는다. 태그 이름 정리(`닫힘` → `반려됨` 등)는 11절 결정 항목 R1.

## 3. 권한표

| 화면·동작 | 실무자 | 관리자 | 화면에서 숨김 / 서버가 막음 |
| --- | --- | --- | --- |
| 대화에서 초안 카드 받기 | 된다 | 된다 | 엔진이 하나도 없으면 카드 없음(규칙 기반 안내만). 서버 `/api/ask` 는 GitHub 을 부르지 않는다 |
| [제안 제출] | 된다 | 된다 | 서버가 막음: 로그인(401), 하루 30건(429), 크기(413), 버전 충돌(409). 화면이 막음: 가린 표기 되살림(`maskLeaks`) |
| 공개 누출 경고가 있을 때 제출 | 된다 | 된다 | 막지 않음(확정 전제). 경고만 |
| 내 요청 — 내 제안 보기 | 내 것만 | 내 것만 | 화면에서 거름(`requestedBy === session.name`). 서버는 전체 목록을 준다 — 보안 경계 아님 |
| 승인 관리 — 대기 중 제안 보기 | 못 들어감 | 된다 | 화면에서 숨김(`session.role`). 서버 `/api/proposals` 는 로그인만 본다 |
| 머지 | GitHub 저장소 쓰기 권한이 있으면 된다 | 같음 | 허브가 아니라 **GitHub 권한**이 막는다. 허브 관리자 = 머지 권한이 아니다 (11절 R6) |

## 4. 카드 상태 전이

```
(대화) ─ action 수신 ─▶ [만드는 중] ─ /api/edit 성공 ─▶ [초안]
                          │ 실패                         │ [제안 제출]
                          ▼                              ▼
                       [만들기 실패]                  [올리는 중] ─ 성공 ─▶ [올림 완료]
                                                         │ 409 ─▶ [충돌]
                                                         │ 그 밖 ─▶ [제출 실패] ─ [다시 제출] ─▶ [올리는 중]
                       [초안]·[충돌]·[제출 실패] ─ [취소] 또는 "취소" ─▶ [버림]
```

새 문서는 [만드는 중]이 없다(초안이 답변에 함께 온다). 바로 [초안]부터 시작한다.

| 상태 | 서버 호출 | 보이는 버튼 |
| --- | --- | --- |
| 만드는 중 | `/api/edit` 진행 중 | [취소] |
| 초안 | 없음 | [제안 제출] · [편집 화면에서 열기] · [취소] |
| 올리는 중 | `/api/proposeEdit` 또는 `/api/createDoc` 진행 중 | 모두 꺼짐 (취소 불가 — 이미 GitHub 으로 보냈다) |
| 올림 완료 | 없음 | [내 요청에서 보기] · [제안 보기 ↗] |
| 충돌 (409) | 없음 | [다시 만들기] · [취소] (5-7 참고) |
| 제출 실패 | 없음 | [다시 제출] · [편집 화면에서 열기] · [취소] |
| 만들기 실패 | 없음 | [닫기] |
| 버림 | 없음 | 없음 (한 줄로 접힘) |

## 5. 카드 문구

말투: 화면 안내 문구와 같은 합니다체, 권유는 `~주세요`. (기획안 수용 기준 일부는 해요체로 적혀 있다 — 11절 R2.)

### 5-1. 머리말

| 칸 | 수정 | 새 문서 |
| --- | --- | --- |
| 머리 (굵게) | `「{제목} ({코드})」 수정 초안` | `새 문서 초안 · {카테고리 이름} › {서브메뉴 이름}` (서브메뉴 없으면 `새 문서 초안 · {카테고리 이름}`) |
| 머리 아래 한 줄 (회색) | `v{버전} 기준 · 추가 {n}줄 / 삭제 {n}줄` | `제목 「{제목}」 · 적용 상품 {공통 \| PPM(월정액) \| PPV(단건)} · 문서 코드는 제출할 때 자동으로 매겨집니다` |
| 비슷한 문서 (있을 때만) | — | `비슷한 문서: 「{제목} ({코드})」` (최대 3개, `·` 로 잇기) |
| diff 왼쪽·오른쪽 이름 | `지금 문서 v{버전}` / `초안` | — (전체 미리보기) |
| 사유 칸 이름 | `수정 사유 *` | `등록 사유 *` |
| 사유 칸 안내(placeholder) | `무엇을 왜 바꾸는지 적어 주세요 — 승인하는 사람이 판단하는 근거가 됩니다` | `왜 이 문서가 필요한지 적어 주세요 — 승인하는 사람이 판단하는 근거가 됩니다` |

카테고리·서브메뉴는 id 가 아니라 화면 이름(`src/data/docs.ts` 의 `label`)으로 보인다. 위치·제목·적용 상품은 카드에서 바꿀 수 있다(기획안 흐름 B).

**사유 칸 기본값** (화면이 채우고, 사용자가 고칠 수 있다)

```
{요약}
근거: {action.reason}
```

- `{요약}` 수정은 `/api/edit` 의 `summary`, 새 문서는 `새 문서 등록`.
- `action.reason` 이 비면 둘째 줄은 `근거: 근거 미기재`.
- 사유 칸이 비면 [제안 제출]이 꺼진다(서버도 빈 사유를 400 으로 막는다 — 수정 제안).

### 5-2. 미리보기 아래 고정 문구 (회색, 항상)

| 위치 | 문구 |
| --- | --- |
| 미리보기 바로 아래 | `사람 이름·부서명이 가려졌는지(예: 홍*동, 미디어*팀) 확인해 주세요.` |
| [제안 제출] 버튼 옆 | `제출하면 공개 저장소(GitHub)에 바로 올라갑니다. 반려돼도 기록은 지워지지 않습니다.` |

### 5-3. 경고

두 상자를 쓴다. 제목은 수정 제안 화면(`ProposeEdit.tsx`)과 같은 문장이다.

**빨강 — 제출 막음** (수정만)

| 칸 | 문구 |
| --- | --- |
| 제목 | `제출할 수 없습니다 — 가려 둔 표기를 건드렸습니다` |
| 항목 | `maskLeaks` 메시지 그대로 (`· ` 로 시작) |
| 끝줄 | `[편집 화면에서 열기]로 해당 부분을 원래 표기로 되돌리거나, 대화로 다시 고쳐 달라고 해 주세요.` |

**노랑 — 제출은 됨**

제목: `제출은 할 수 있지만 확인해 주세요`

| 경고 | 수정 | 새 문서 | 항목 문구 |
| --- | --- | --- | --- |
| 금액 | ○ | ○ | `{n}번째 줄 「{표기}」 — 금액으로 보입니다. 매출·거래액이면 "늘어나는 추세"처럼 경향으로 바꿔 주세요. 쿠폰 할인 금액이면 그대로 두셔도 됩니다.` |
| 회사 표기 | ○ | ○ | `{n}번째 줄 「{표기}」 — 회사 이름으로 보입니다. 제휴사 이름이면 "제휴사"로 바꿔 주세요.` |
| 주소(URL) | ○ | ○ | `{n}번째 줄 「{표기}」 — 인터넷 주소입니다. 사내 주소면 "(URL 생략)"으로 바꿔 주세요.` |
| 이메일 | ○ | ○ | `{n}번째 줄 「{표기}」 — 이메일 주소입니다. 지워 주세요.` |
| 전화번호 | ○ | ○ | `{n}번째 줄 「{표기}」 — 전화번호입니다. 지워 주세요.` |
| (보완 필요) | ○ | ○ | `채워야 할 칸 "(보완 필요)"가 {n}곳 있습니다. 그대로 제출해도 되지만, 아는 값이면 채워 주세요.` |
| 근거 미기재 | ○ | ○ | `언제·어디서 정해진 내용인지 없어서 사유에 "근거 미기재"로 남깁니다.` |
| `editWarnings` | ○ | — | 메시지 그대로 |
| `brokenAnchors` | ○ | — | 수정 제안 화면과 같은 문장 (`· 다른 문서에서 이 문서의 소제목을 가리키는 링크가 끊깁니다 — …`) |
| 열린 제안 있음 | ○ | — | `이 문서에 대기 중인 제안이 이미 {n}건 있습니다 — 둘 다 승인하면 나중 것이 충돌할 수 있습니다.` |

공개 누출 경고 5종(금액·회사·URL·이메일·전화)은 하나의 공용 검사(`publicLeakWarnings`)가 만든다. 같은 문구를 **카드·수정 제안 화면·새 문서 화면**이 함께 쓴다.

검사 대상은 본문만이 아니다. **제목·본문·사유** 셋을 모두 본다. 사유는 PR 본문에, 제목은 PR 제목·커밋 메시지에 그대로 실리기 때문이다. 사유·제목에서 걸리면 `{n}번째 줄` 대신 `수정 사유` / `등록 사유` / `제목` 으로 위치를 적는다.

### 5-5. 만드는 중 (수정만)

| 칸 | 문구 |
| --- | --- |
| 카드 한 줄 | `「{제목} ({코드})」 수정 초안을 만드는 중입니다… ({엔진 이름} {기다리는 시간} 내외)` |

기다리는 시간은 수정 제안 화면의 값(`AI_WAIT_HINT`: Claude 1~2분, Codex 2~3분, Gemini 20~40초)을 그대로 쓴다. 대화 본문에 "문서를 고치는 중입니다" 같은 과정 중계를 따로 쓰지 않는다.

### 5-6. 올리는 중 · 올림 완료

| 상태 | 문구 |
| --- | --- |
| 올리는 중 (버튼 옆) | `제안을 올리는 중입니다. 몇 초 걸립니다.` |
| 올림 완료 — 제목 | `제안을 올렸습니다` |
| 올림 완료 — 수정 | `「{제목} ({코드})」 수정 제안이 '대기 중'으로 올라갔습니다. 관리자가 승인(머지)하면 다음 배포 때 위키에 반영됩니다. 지금 위키 문서는 그대로입니다.` |
| 올림 완료 — 새 문서 | `새 문서 「{제목}」({코드})이 '대기 중'으로 올라갔습니다. 관리자가 승인(머지)하면 다음 배포 때 위키에 새 문서로 보입니다.` |
| 올림 완료 — 끝줄(회색) | `진행 상태는 내 요청 현황에서 볼 수 있습니다.` |

[내 요청에서 보기]는 `/requests` 의 `문서 수정 제안` 탭으로 간다. 제출이 성공하면 화면이 제안 목록을 **바로 다시 읽어야** 한다(`refreshProposals`). 지금은 한 번만 읽으므로, 다시 읽지 않으면 방금 올린 제안이 내 요청에 안 보인다.

### 5-7. 충돌 (409 — 문서가 그사이 바뀜)

409 는 "화면이 본 버전 ≠ 저장소 main 버전"이다. 다른 제안이 먼저 머지됐는데 아직 배포 전인 경우가 대부분이다. 이때 **화면이 가진 문서 본문은 옛 것**이라, 같은 본문으로 초안을 다시 만들면 다시 409 가 난다.

| 칸 | 문구 |
| --- | --- |
| 제목 | `문서가 그사이 바뀌었습니다` |
| 본문 | `이 초안은 v{화면 버전} 기준인데, 저장소의 문서는 이미 v{저장소 버전}입니다. 다른 제안이 먼저 승인된 것 같습니다. 제출하지 않았고, 초안은 그대로 있습니다.` |
| 할 일 (A안: 서버가 최신 본문을 준다) | `[다시 만들기]를 누르면 바뀐 문서를 기준으로 같은 내용의 초안을 새로 만듭니다.` |
| 할 일 (B안: 서버가 최신 본문을 안 준다) | `새 내용이 위키에 반영된 뒤(다음 배포 뒤) 다시 요청해 주세요.` — 이때 [다시 만들기]는 두지 않는다 |

- 충돌 상태에서는 [편집 화면에서 열기]를 숨긴다. 수정 제안 화면도 옛 본문을 열어 같은 409 가 난다.
- A안이 기획안 수용 기준 A13("[다시 만들기]가 뜬다")을 만족한다. A안은 dev-server 가 409 응답에 `{ code: 'stale', mainVersion, mainBody }` 를 실어야 한다 (11절 R3). 그 전까지는 B안 문구로 둔다.

### 5-8. 실패 문구

서버 원문(HTTP 상태, GitHub 오류, 환경변수 이름)은 실무자에게 보이지 않는다. 화면이 **상태 코드로 문장을 고른다**. 모든 실패 문구 끝에 `초안은 그대로 있습니다.` 를 붙인다(만들기 실패 제외).

**제출 실패** (`/api/proposeEdit`·`/api/createDoc`)

| 경우 | 문구 | 버튼 |
| --- | --- | --- |
| 400 (입력 문제) | `제출하지 못했습니다 — {서버 문장}` (400 문장은 이미 쉬운 한국어다. 예: "저장소의 현재 본문과 같습니다. 변경 사항이 없습니다") | [편집 화면에서 열기] · [취소] |
| 401 | `로그인이 끝났습니다. 다시 로그인한 뒤 [다시 제출]을 눌러 주세요.` | [다시 제출] · [취소] |
| 404 (수정 대상 문서 없음) | `이 문서를 저장소에서 찾지 못했습니다. 옮겨졌거나 지워졌을 수 있습니다. 관리자에게 알려 주세요.` | [취소] |
| 413 | `내용이 너무 깁니다. 본문을 줄여 [편집 화면에서 열기]로 다시 제출해 주세요.` | [편집 화면에서 열기] · [취소] |
| 429 | `오늘 올릴 수 있는 제안 수(하루 30건)를 넘었습니다. 내일 다시 제출해 주세요.` | [취소] |
| 503 | `지금은 제안을 올릴 수 없습니다(허브 설정 문제). 관리자에게 알려 주세요.` | [다시 제출] · [취소] |
| 502·네트워크 끊김·그 밖 | `GitHub에 제안을 올리지 못했습니다. 잠시 뒤 [다시 제출]을 눌러 주세요. 계속되면 관리자에게 알려 주세요.` | [다시 제출] · [취소] |
| 새 문서 코드 자동 부여 불가 | `이 서브메뉴에는 자동으로 문서 코드를 매길 수 없습니다. 카드에서 다른 서브메뉴를 골라 주세요.` | [다시 제출] · [취소] |

관리자(`session.role === 'admin'`)에게만 문구 끝에 `· HTTP {상태}` 를 붙인다(엔진 실패 안내 `docs/plan/2026-11-12-engine-failure-notice.md` 와 같은 방식). 보안 경계가 아니라 원인 찾기용이다.

**만들기 실패** (`/api/edit`, 수정만)

엔진 실패 안내의 분류 코드를 그대로 쓰고, "규칙 기반으로 답했습니다" 대신 "초안을 만들지 못했습니다"로 바꾼다. (엔진 실패 안내 열린 질문 4에 대한 답: 같은 분류를 쓴다.)

| 코드 | 문구 |
| --- | --- |
| `overloaded` | `AI 엔진이 잠시 붐벼 초안을 만들지 못했습니다. 잠시 후 다시 요청해 주세요.` |
| `timeout` | `AI 엔진 응답이 늦어 초안을 만들지 못했습니다. 잠시 후 다시 요청해 주세요.` |
| `quota` | `AI 엔진 사용 한도에 걸려 초안을 만들지 못했습니다. 계속되면 관리자에게 알려 주세요.` |
| `auth`·`model` | `AI 엔진 연결 설정에 문제가 있어 초안을 만들지 못했습니다. 관리자에게 알려 주세요.` |
| `unknown` | `AI 엔진 응답을 받지 못해 초안을 만들지 못했습니다. 계속되면 관리자에게 알려 주세요.` |
| 바뀐 줄 0 | `바뀐 줄이 없는 초안이 나왔습니다. 무엇을 무엇으로 바꿀지 한 번 더 알려 주세요.` |
| `action` 이 검증에서 `none` 이 됨 | `초안을 만들지 못했습니다. 바꿀 내용을 한 번 더 알려 주세요.` (이 줄은 대화 본문 끝에 붙는다 — 기획안 A10) |

### 5-9. 취소·대화로 제출하려 할 때

| 경우 | 문구 | 비고 |
| --- | --- | --- |

## 6. [편집 화면에서 열기]

| 항목 | 수정 | 새 문서 |
| --- | --- | --- |
| 여는 화면 | 수정 제안 화면 `/wiki/{문서}/propose`, 1단계(편집)에 초안 본문·사유를 채움 | 새 문서 화면 `/wiki/new`, 카테고리·서브메뉴·제목·적용 상품·본문·사유를 채움 |
| 그 화면에 이미 임시저장본이 있을 때 (수정만) | 확인 창 한 번: `이 문서에 저장해 둔 편집 내용이 있습니다. 챗봇 초안으로 바꿀까요? 바꾸면 저장해 둔 내용은 사라집니다.` [바꾸기] [그대로 두기] | — |
| 열린 화면 위 안내(회색 한 줄) | `챗봇 대화에서 만든 초안을 채웠습니다. 고친 뒤 제출해 주세요.` | 같음 |
| 진입 값 | 그 화면에서 제출해도 `챗봇 대화` 로 남긴다 (초안이 시작된 곳 기준) | 같음 |
| 카드 쪽 | 카드는 그대로 남는다(대화 기록). 편집 화면에서 제출하면 카드는 바뀌지 않는다 | 같음 |

새 문서 화면에는 지금 사유 칸이 없다. 챗봇 초안의 사유를 옮기려면 `등록 사유` 칸이 필요하다 (11절 R4).

## 7. 진입 표시 — 이름과 위치

### 7-1. 이름 (네 가지만)

| `via` 값 | 화면·PR 본문에 쓰는 이름 | 쓰는 곳 |
| --- | --- | --- |
| `propose` | `수정 제안 화면` | 수정 |
| `form` | `새 문서 화면` | 새 문서 |
| `chat` | `챗봇 대화` | 수정·새 문서 |
| `attachment` | `첨부 파일` | 수정·새 문서 (2단계) |

`server/github.ts` 에 이미 있는 `챗봇 대화`·`수정 제안 화면` 은 그대로 둔다. 새로 생기는 것은 `새 문서 화면`·`첨부 파일` 둘이다.
진입 줄이 없는 옛 PR 은 **아무것도 표시하지 않는다**(추측해 채우지 않는다 — `parseProposalPr` 의 기존 원칙).

### 7-2. 내 요청 현황 (`MyRequests.tsx`, 문서 수정 제안 탭)

| 위치 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 줄 머리 태그 | `수정` / `새 문서` | 그대로 |
| 제목 아래 회색 줄 | `{사유}` | `{진입 이름} · {사유}` (진입을 모르면 `{사유}` 만) |

예: `챗봇 대화 · 판촉 쿠폰 결재 단계를 팀장 전결로 변경`

### 7-3. 승인 관리 (`Approvals.tsx`, 문서 수정 탭)

| 위치 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 왼쪽 목록 회색 줄 | `{요청자} · {월-일}` | `{요청자} · {월-일} · {진입 이름}` |
| 오른쪽 상세 회색 줄 | `{요청자} · {날짜} · {새 문서 \| 문서 수정} · PR #{번호}` | `{요청자} · {날짜} · {새 문서 \| 문서 수정} · {진입 이름} · PR #{번호}` |

| 사유 줄 이름 | `수정 사유 —` | 수정은 그대로, 새 문서는 `등록 사유 —` |

## 8. PR 본문

`parseProposalPr` 가 읽는 형식(첫 줄 `{이름}님이 `, `- 문서: …`, `- 문서 코드: …`, `## 수정 사유`, 끝줄)을 깨지 않는다. 진입은 **따로 한 줄**이고, 판정(2단계) 같은 다른 정보를 같은 줄에 붙이지 않는다.

### 8-1. 수정 PR (`createEditPR`)

```
{요청자}님이 위키 허브에서 문서 수정을 제안했습니다.

- 문서: {제목} ({코드})
- 경로: 지식/{경로}
- 버전: v{기준} → v{새 버전}
- 진입: {수정 제안 화면 | 챗봇 대화 | 첨부 파일}

## 수정 사유

{사유}

내용을 확인하고 이상 없으면 머지해 주세요. 머지되면 다음 배포에서 위키에 반영됩니다.
```

바뀌는 것: `- 진입:` 값에 `첨부 파일` 추가뿐. 나머지는 지금 그대로.

### 8-2. 새 문서 PR (`createDocPR`)

```
{요청자}님이 위키 허브에서 새 문서를 제안했습니다.

- 카테고리: {카테고리 id} › {서브메뉴 id}
- 문서 코드: {코드}
- 진입: {새 문서 화면 | 챗봇 대화 | 첨부 파일}

## 등록 사유

{사유}

내용을 확인하고 이상 없으면 머지해 주세요. 머지되면 다음 배포에서 위키에 반영됩니다.
```

바뀌는 것

| 줄 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 첫 줄 | `{요청자}님이 위키 허브 "+"로 새 문서를 요청했습니다.` | `{요청자}님이 위키 허브에서 새 문서를 제안했습니다.` (`님이 ` 는 유지 — 요청자 읽기에 쓴다) |
| 진입 | 없음 | `- 진입: …` 추가 |
| 사유 | 없음 | `## 등록 사유` 절 추가. 사유가 비면 절을 넣지 않는다(새 문서 화면에 사유 칸이 생기기 전 대비) |

`parseProposalPr` 는 `## 수정 사유` 와 `## 등록 사유` 를 모두 읽어야 한다. 진입은 `^- 진입: (.+)$` 한 줄을 읽어 `ProposalPr` 에 `via` 이름으로 싣는다.

### 8-3. PR 본문에 넣지 않는 것

- 첨부 파일 이름 (제휴사명이 들어 있을 수 있다 — 기획안 B8).
- 공개 누출 경고에 걸린 표기 자체. (경고 개수만 남기는 안은 11절 R5.)
- 엔진 이름, 대화 원문.
