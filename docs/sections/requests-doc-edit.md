# 문서 화면에서 바로 편집 — 제출 뒤 흐름·상태·권한·문구

작성 `requests-planner` · 2026-11-25 · 상위 지시 "위키 문서를 선택했을 때 보여지는 문서를 쉽게 편집할 수 있는 개편안"

범위: 편집을 **제출한 뒤**(그리고 제출 직전의 검사·임시 저장·충돌)의 흐름·상태·권한·안내 문구. 문서 화면 안에서 장 단위로 고치는 화면 자체는 wiki-ux 설계안(`docs/ux/2026-11-25-doc-editing.md`)이 정한다. 이 문서는 그 설계안이 어떤 모양이 되든 **제출 버튼을 누른 순간부터** 같은 규칙을 쓰게 한다.

이 문서는 흐름·상태·규칙·문구만 정한다. 코드는 dev-server·dev-front 가 옮긴다. `「」` 안 문자열은 그대로 옮기고 `{ }` 는 채워 넣는 값이다. 말투는 기존 섹션 문서와 같은 합니다체다.

## 1. 지금 실제로 일어나는 일 (문구의 근거)

| 순간 | 실제 동작 | 근거 |
| --- | --- | --- |
| 편집 시작 | `/wiki/:id/propose`. 본문 **전체**를 textarea 로 연다. 장 단위 편집은 없다 | `src/pages/ProposeEdit.tsx` |
| 임시 저장 | 2초 멈추면 `localStorage` `wikihub.draft.{docId}` 에 본문 전체만 저장. **어느 버전 기준인지·누가 썼는지 저장하지 않는다** | `ProposeEdit.tsx` |
| 다시 열 때 | 임시 저장이 있으면 **묻지 않고** 그 본문으로 연다. 그 사이 문서가 새 버전으로 배포됐어도 그대로 연다 | 같은 곳 |
| [다음 · 변경 확인] | 이때서야 규칙 검사(`maskLeaks` 차단, `editWarnings`·`brokenAnchors`·공개 검사 경고)와 "같은 문서 열린 제안 n건" 경고가 보인다 | `src/lib/docEdit.ts`, `ProposeEdit.tsx` |
| [제안 제출] | `requestDocEdit` → `/api/proposeEdit` → `parseEditDocInput`(사유 비면 400) → `createEditPR` | `src/lib/proposeEdit.ts`, `server/github.ts` |
| 서버 공개 검사 | **없다.** `createEditPR` 은 `publicLeaks` 를 부르지 않는다. 화면 공개 검사도 수정(`target:'edit'`)은 전부 경고다. D2 ②(이름·별표 2개 차단, 금액 경고)는 결정만 되고 반영 전 | `server/github.ts`, `server/publicCheck.ts:212`, 상용화 검토 D2 |
| 최신성 검사 | 화면이 본 `version` ≠ main 의 `version` 이면 PR 을 열지 않고 409 + `mainVersion`·`mainBody` 를 돌려준다 | `createEditPR` |
| 409 뒤 화면 | 「제출하지 못했습니다 — 이 문서는 그 사이 v{n}으로 바뀌었습니다. 문서를 다시 열어 수정해 주세요」. **`mainBody` 는 화면 어디에서도 쓰지 않는다** | `ProposeEdit.tsx`, `src/` 전체에 `mainBody` 사용 없음 |
| PR 이 열린 순간 | 새 브랜치 `docs/edit-{코드}-…` + 파일 1개 커밋(프론트매터 version+1·updatedBy·updatedAt) + PR. 공개 저장소라 **이 순간 공개**된다 | `createEditPR` |
| 완료 화면 | 「…PR #{n}을 만들었습니다. 관리자가 확인하고 머지하면 다음 배포에서 위키에 반영됩니다.」 「머지한 뒤에도 재배포하기 전까지는 이 화면의 문서가 그대로입니다」 | `ProposeEdit.tsx` |
| 내 요청 | `/api/proposals` (GitHub PR 최근 50건)를 **화면 진입 시 1회**만 읽는다. 상태는 PR 상태 그대로: 열림 `대기 중`, 머지 `머지됨`, 머지 없이 닫힘 `닫힘`. 내 것은 `requestedBy === session.name` (**이름**으로 묶음) | `MyRequests.tsx`, `AppStore.tsx` `ensureProposals` |
| 승인 관리 | 관리자만 보이게 화면이 숨김(`session.role`). 문서 제안은 읽기 전용, 머지는 GitHub 에서. 반려 사유 입력은 문서 제안에 없다 | `Approvals.tsx` |
| 서버 권한 | `/api/proposeEdit`·`/api/proposals` 는 로그인(배포본)·호출 횟수(하루 30건)만 본다. 관리자 여부는 보지 않는다 | `api/proposeEdit.ts`, `server/guard.ts` |
| 머지 | 허브가 아니라 GitHub 쓰기 권한자가 한다(D5 ①: 관리자 계정 담당자 = GitHub 승인자) | 상용화 검토 D5 |
| 위키에 보이는 때 | 화면의 문서는 빌드 때 묶인 `지식/**/*.md` 다. 머지 뒤 **다음 배포(로컬 허브는 업데이트)** 때 바뀐다 | `src/data/knowledgeDocs.ts` `import.meta.glob` |
| 문서 담당자 | 없다. 문서 43건의 `ownerId` 가 모두 `ppc-team` 이다 | `지식/**` 프론트매터 |

그래서 어떤 문구도 제출 순간에 "반영했습니다"·"수정했습니다"를 쓰지 않는다. 제출 순간에 일어나는 일은 "제안(PR)이 열렸다"뿐이다.

## 2. 실무자가 헷갈리는 지점

| # | 지점 | 왜 헷갈리나 | 이 문서의 해법 |
| --- | --- | --- | --- |
| C1 | 제출하면 문서 화면이 옛 내용으로 돌아간다 | "내가 고친 게 사라졌다"로 읽힌다. 다시 고치거나 또 제출한다 | 장 옆에 "대기 중인 내 제안" 표시(6-2) |
| C2 | `머지됨` 인데 위키에 안 보인다 | 배포가 언제인지, 이미 반영됐는지 화면이 구분하지 못한다 | 버전 비교로 "배포 대기 / 위키에 반영됨" 보조 표시(6-3) |
| C3 | 반려 사유가 허브에 안 온다 | 안내 문서(HUB-02)는 "반려되면 사유가 함께 전달"이라 하지만 실제로는 PR 을 닫을 뿐이다 | 문구를 사실대로 + 닫을 때 PR 코멘트 운영 규칙(9절 O3) |
| C4 | 임시 저장이 버전을 모른다 | 문서가 v3→v4 로 배포된 뒤 v3 기준 초안을 열면 묻지 않고 열리고, 화면 버전이 v4 라 409 도 안 난다. **그 사이 바뀐 내용을 조용히 되돌리는 PR 이 열린다** | 초안에 기준 버전 저장, 다르면 묻기(4-1) — 결함 수정 |
| C5 | 409 의 "문서를 다시 열어 수정해 주세요" | 배포 전이면 다시 열어도 같은 옛 본문이라 같은 409 가 난다. 할 수 있는 일이 없다 | 서버가 이미 주는 `mainBody` 로 내 장을 최신본에 다시 얹기(4-3) |
| C6 | 같은 문서 대기 제안 경고가 제출 직전에야 보인다 | 다 고친 뒤에 알게 된다. 내 것인지 남의 것인지도 모른다 | 편집 시작 때 알림, 내 것/남의 것 구분(4-2) |
| C7 | 같은 문서 대기 제안 둘은 뒤에 머지되는 쪽이 대부분 충돌한다 | 두 PR 이 모두 프론트매터 `version`·`updatedBy`·`updatedAt` 줄을 고친다. 같은 사람·같은 날이면 충돌 없이 합쳐지지만 버전이 한 번만 오른다 | 먼저 머지된 쪽이 있으면 남은 쪽을 "다시 올려야 함"으로 표시(6-3) |
| C8 | 내 요청이 이름으로 묶인다 | D4 대신 "계정 이름 = 팀 이름" 규칙을 쓰면 **같은 팀 사람의 제안이 모두 내 요청에 섞인다**. 로컬 허브는 데모 이름이라 전부 섞인다 | 열린 질문 Q3 |
| C9 | 상태가 안 바뀐다 | 내 요청은 진입 시 1회만 읽는다. 승인돼도 알림이 없다 | 앱 진입 시 1회 읽고, 바뀐 것만 메뉴 배지·배너(6-4) |
| C10 | 수정 제안은 공개 검사가 경고뿐이다 | 실명을 넣어도 제출되고, 화면을 거치지 않으면 경고도 없다 | D2 ② 서버 반영(S1) |
| C11 | "제출 버튼 하나"와 수정 사유 필수가 부딪친다 | 서버가 사유 빈 값을 400 으로 막는다 | 사유 기본값을 채운 채 버튼 하나(3-2) |

## 3. 흐름 제안

### 3-1. 경로 (바꾼 뒤)

```
문서 화면 · 장 [편집]                              ← wiki-ux 설계안
  │ 편집 시작 때: 같은 문서 대기 제안 확인(4-2), 임시 저장 복원 확인(4-1)
  ▼
장 수정 (임시 저장: 기준 버전·장 이름과 함께)
  ▼
[제출] 한 번
  │ 화면 검사 (브라우저, 서버 호출 없음): maskLeaks · editWarnings · brokenAnchors
  │ 공개 검사 /api/publicCheck (target:'edit')
  │   차단 ≥1 → 제출 안 함, 걸린 줄 표시 (5-2)          ← 버튼 1번으로 끝, PR 없음
  │   경고만   → 확인 상자 [그래도 제출] [고치기]        ← +1클릭
  │   0       → 바로 진행
  ▼
/api/proposeEdit {docPath, code, title, body(문서 전체), reason, baseVersion, via:'propose', section}
  → parseEditDocInput → publicLeaks(서버, S1) → createEditPR
  │ 400 public-leak → 5-2 차단 문구
  │ 409 stale      → 4-3 (내 장을 최신본에 다시 얹기 → [다시 제출])
  ▼
PR 열림 = 「대기 중」 → 장 옆 표시 + 완료 줄 (5-1)
  ▼
GitHub 에서 머지 = 「머지됨 · 배포 대기」 → 다음 배포 = 「머지됨 · 위키에 반영됨」
GitHub 에서 닫힘 = 「닫힘」
```

- 장 단위로 고쳐도 **서버에는 지금처럼 문서 전체 본문**을 보낸다. 서버 계약(`createEditPR`)은 그대로고, 장 이름은 PR 본문 한 줄로만 더한다(S2).
- 진입 이름은 기존 `수정 제안 화면`(`via:'propose'`)을 그대로 쓴다. 문서 화면 편집이 기존 수정 제안 화면을 대신하는 것이기 때문이다. 둘이 함께 남는다면 새 진입 이름이 필요한지 wiki-ux 와 정한다(Q7).

### 3-2. 수정 사유 — 버튼 하나를 지키는 방법

서버는 사유를 필수로 유지한다(승인자가 읽는 유일한 설명이다). 화면은 사유 칸을 **미리 채운 채** 접어 둔다.

| 상황 | 사유 기본값 |
| --- | --- |
| 손으로 고침 | 「「{장 제목}」 장 수정」 |
| AI 로 고침 | 「{AI 요약} (AI 수정 · {엔진})」 — 지금 `ProposeEdit` 과 같다 |
| 장 제목이 없는 머리말 | 「문서 첫머리 수정」 |

제출 버튼 옆에 회색 한 줄: 「수정 사유: {기본값} · [고치기]」. 사유를 고치지 않아도 제출된다.

### 3-3. 선택이 필요한 것

| 항목 | 현재 | 제안 | 영향 | 의견 |
| --- | --- | --- | --- | --- |
| 작은 수정·큰 수정 구분 | 구분 없음 | **B. 흐름은 하나, 표시만 다르게.** 서버가 main 본문과 비교해 규칙으로 `작은 수정` 을 판정해 PR 제목 앞(`[작은 수정] 문서 수정: …`)과 승인 관리 배지에 붙인다. 기준(안): 바뀐 줄 5줄 이하 · 한 장 안 · 소제목·표 행 수·코드 블록 변화 없음 · 화면 경고 0 | 승인자가 작은 것부터 빨리 머지한다. 실무자 흐름은 같다. 서버 판정이라 위조할 수 없다 | B 권장. C(작은 수정 자동 머지)는 공개 저장소에 사람 확인 없이 들어가고 D5 ①과 어긋나 비권장. 기준 수치는 Q5 |
| 실무자 권한 | 로그인하면 모든 문서 제안 가능 | 그대로 | 없음 | 유지 |
| 관리자 본인 수정 | 실무자와 같은 PR → GitHub 에서 본인이 머지 | **A. 지금 유지.** 완료 줄에 관리자에게만 [PR에서 바로 머지하기 ↗] 를 보인다(GitHub 화면으로 이동, 허브는 머지하지 않음) | 관리자 동선: 제출 1 + GitHub 머지 2 클릭. 그래도 **배포 전에는 위키가 안 바뀐다** — 허브가 머지해도 마찬가지다 | A 권장. B(허브에 관리자 전용 [제출하고 바로 머지], 서버가 토큰으로 머지·관리자 검사)는 D5 ② 검토 때 함께. C(main 직접 커밋)는 PR 기록이 없어 비권장 |
| 문서 담당자 | 개념 없음(`ownerId` 전부 `ppc-team`) | **A. 시범 기간엔 두지 않는다.** 대신 승인 관리에 카테고리 표시를 붙여 관리자가 나눠 본다 | 없음 | 담당자 도입(B: `ownerId` 를 팀·계정으로 채우고 그 담당자에게 승인 관리 열기)은 머지 권한이 GitHub 에 있는 한 "보기만 하는 승인자"가 된다. Q2 |
| 같은 문서 대기 제안이 있을 때 | 제출 직전 경고만, 제출은 됨 | **B. 편집 시작 때 알리고 제출은 허용.** 먼저 머지된 쪽이 생기면 남은 쪽을 `대기 중 · 다시 올려야 함` 으로 표시 | 실무자가 미리 안다. 막힘 없음 | B 권장. C(대기 제안 있으면 제출 차단)는 승인이 늦으면 문서가 오래 묶여 비권장 |
| 내 대기 제안을 고치고 싶을 때 | 새 PR 이 하나 더 열린다 | **A(지금). 새 제안으로 올리되 안내로 앞 제안과의 관계를 알린다.** 나중에 B(서버가 내 대기 PR 브랜치에 커밋을 덧붙이는 "내 제안 고치기", 기존 `api/proposeEdit.ts` 확장) | B 는 PR 이 하나로 유지돼 승인자가 덜 헷갈린다. 남의 PR 에는 못 덧붙이게 서버가 요청자를 확인해야 한다(Q3 과 엮임) | 시범은 A, 시범 뒤 대기 제안 중복이 잦으면 B |
| 409 (문서가 그사이 바뀜) | 다시 열라는 안내뿐(해결 불가) | **B. 화면이 `mainBody` 로 내 장을 최신본에 다시 얹고 [다시 제출] 1클릭.** 내가 고친 장이 최신본에서도 그대로일 때만 자동, 아니면 나란히 보여 주고 직접 합치게 | 서버 변경 없음(이미 `mainBody` 를 준다) | B 권장. C(서버가 다시 얹기)는 서버가 장 경계를 알아야 해 일이 크다 |
| 수정 제안 서버 공개 검사 | 없음 | D2 ② 그대로: 비공개 이름 목록·별표 2개 **차단**, 금액 **경고** | 수정 제안도 새 문서와 같은 기준. 이미 문서에 있던 줄은 짚지 않는다(화면과 같은 기준) | 결정 완료 항목. 상용화 전 반영(S1) |

### 3-4. 권한표

| 화면·동작 | 실무자 | 관리자 | 화면에서 숨김 / 서버가 막음 |
| --- | --- | --- | --- |
| 장 [편집] 버튼 | 보임 | 보임 | 배포본에서 로그인 전에는 화면 전체가 로그인 뒤에 있다(`AuthGate`) |
| [제출] — 차단 없음 | 된다 | 된다 | 서버: 로그인(401, 배포본)·하루 30건(429)·크기(413)·입력(400)·최신성(409) |
| [제출] — 차단 있음 | 못 함 | 못 함 | 화면이 막음 **그리고** 서버가 막음(S1, 400 `public-leak`). 지금은 서버가 안 막는다 |
| 사유 고치기 | 된다 | 된다 | 비면 서버 400 — 화면은 기본값을 채워 둬 비지 않게 한다 |
| 내 요청 (내 제안 보기) | 된다 | 된다 | 숨김 없음. 서버 `/api/proposals` 는 모든 제안을 준다(PR 은 어차피 공개). "내 것" 판정은 화면이 한다(이름 → Q3) |
| 같은 문서 대기 제안 알림의 요청자 이름 | 보임 | 보임 | PR 에 공개된 이름이라 숨기지 않는다 |
| 승인 관리 | 못 들어감 | 된다 | **화면만 숨김**(`session.role`). 서버는 관리자를 따로 보지 않는다 — 읽기 전용 화면이라 지금은 문제없음 |
| 머지·닫기 | GitHub 쓰기 권한이 있으면 된다 | 같음 | 허브가 아니라 GitHub 권한이 막는다(D5 ①) |
| [PR에서 바로 머지하기 ↗] | 안 보임 | 보임 | 화면만 숨김. 실제 권한은 GitHub |
| 내 대기 제안 고치기(나중 B) | 내 것만 | 내 것만 | 서버가 요청자 확인으로 막아야 한다(화면 숨김만으로는 부족) |

## 4. 제출 전 상황별 안내와 다음 행동

### 4-1. 임시 저장(초안)

저장 형태(dev-front): 키 `wikihub.draft.{계정 아이디}.{docId}`, 값 `{ baseVersion, section, body, savedAt }`. 다른 계정의 초안을 열지 않는다. 로그아웃 때 그 계정의 초안을 지우지 **않는다**(긴 수정 보호) — 대신 다시 열 때 묻는다.

| 상황 | 문구 | 다음 행동(버튼) |
| --- | --- | --- |
| 저장됨 (편집 중 상시) | 「임시 저장됨 · {시:분} · 이 PC의 이 브라우저에만 있습니다. 아직 제출하지 않았습니다.」 | 없음 |
| 다시 열 때 · 같은 버전 | 「{월/일 시:분}에 임시 저장한 수정이 있습니다 (「{장 제목}」).」 | [이어서 고치기] · [버리고 새로 고치기] |
| 다시 열 때 · 문서가 새 버전, 내 장은 그대로 | 「임시 저장한 수정은 v{a} 기준인데 문서가 v{b}로 바뀌었습니다. 내가 고친 장은 바뀌지 않아 최신 문서 위에 다시 얹었습니다.」 | [이어서 고치기] · [버리기] |
| 다시 열 때 · 내 장도 바뀜 | 「임시 저장한 수정은 v{a} 기준인데 문서가 v{b}로 바뀌었고, 내가 고친 장도 바뀌었습니다. 그대로 제출하면 그 사이 바뀐 내용을 되돌리게 됩니다.」 | [나란히 보며 합치기] · [버리기] ([이어서 고치기] 없음) |
| 화면을 떠날 때 | 「아직 제출하지 않았습니다. 수정은 이 브라우저에 임시 저장돼 있어 다음에 이어서 고칠 수 있습니다.」 | [계속 고치기] · [나가기] |
| 내 요청 화면 | 문서 제안 탭 위에 한 줄: 「제출하지 않은 임시 저장 {n}건」 펼치면 문서 제목·저장 시각·[이어서 고치기] | 상태표의 `초안` — 태그는 붙이지 않는다 |

- "저장했습니다"·"반영했습니다"를 임시 저장에 쓰지 않는다. 항상 "임시 저장"·"아직 제출하지 않았습니다"를 쓴다.
- 기존 키(`wikihub.draft.{docId}`, 버전 없음)의 초안은 기준 버전을 모르므로 "내 장도 바뀜" 줄과 같이 다룬다(합치기·버리기만).

### 4-2. 같은 문서에 대기 중 제안이 있을 때

판정: `/api/proposals` 의 `kind:'edit'`, `status:'pending'`, `docCode` 일치. 편집을 시작하는 순간 한 번 보인다(제출 직전이 아니라). 제안 목록을 못 읽었으면 알림을 띄우지 않고 제출도 막지 않는다.

| 상황 | 문구 | 다음 행동 |
| --- | --- | --- |
| 남의 대기 제안 | 「이 문서에 승인을 기다리는 제안이 {n}건 있습니다 ({요청자} · {월/일}). 같은 문서를 고치면 나중에 승인되는 쪽은 다시 올려야 할 수 있습니다.」 | [그래도 고치기] · [대기 중 제안 보기 ↗](PR) |
| 내 대기 제안 | 「이 문서에 내가 올린 제안이 대기 중입니다 (PR #{n} · {월/일}). 지금 고친 것은 별도 제안으로 올라가고, 둘 중 나중에 승인되는 쪽은 다시 올려야 할 수 있습니다. 앞 제안을 고치려는 것이면 그 PR 에 의견으로 남겨 주세요.」 | [그래도 고치기] · [내 제안 보기 ↗] |
| 같은 장을 고친 대기 제안 (S2 뒤, PR 에 장 이름이 있을 때) | 위 문구 끝에 「이 제안도 「{장 제목}」 장을 고쳤습니다.」 | 같음 |
| 제출 확인 상자(경고가 있을 때) | 경고 목록 맨 위에 같은 사실 한 줄: 「이 문서에 대기 중인 제안이 {n}건 있습니다.」 | [그래도 제출] · [고치기] |

### 4-3. 409 — 문서가 그사이 바뀜

409 는 "화면이 본 버전 ≠ 저장소 main 버전"이다. 대개 다른 제안이 먼저 머지됐는데 아직 배포 전이다. 서버는 이미 `{ code:'stale', mainVersion, mainBody }` 를 준다.

화면 처리: 내가 고친 장을 (a) 화면이 가진 옛 본문, (b) `mainBody` 에서 같은 소제목으로 찾는다. 두 장이 글자까지 같으면 `mainBody` 의 그 장만 내 수정으로 바꿔 새 본문을 만들고 `baseVersion = mainVersion` 으로 둔다. 다르거나 소제목을 못 찾으면 자동으로 얹지 않는다.

| 상황 | 문구 | 다음 행동 |
| --- | --- | --- |
| 내 장이 최신본에서도 그대로 | 「문서가 그사이 v{b}로 바뀌었습니다 (다른 제안이 먼저 승인됨). 내가 고친 「{장 제목}」 장은 바뀌지 않아 최신 문서 위에 다시 얹었습니다. 아직 제출하지 않았습니다.」 | [다시 제출] (1클릭) · [바뀐 곳 보기] |
| 내 장도 바뀜 / 소제목을 못 찾음 | 「문서가 그사이 v{b}로 바뀌었고, 내가 고친 「{장 제목}」 장도 바뀌었습니다. 제출하지 않았습니다. 최신 내용과 내 수정을 나란히 보여 드립니다. 합친 뒤 다시 제출해 주세요. 내 수정은 그대로 있습니다.」 | [나란히 보며 합치기] · [취소] |
| `mainBody` 가 없음(옛 서버) | 「문서가 그사이 v{b}로 바뀌었습니다. 제출하지 않았고, 내 수정은 임시 저장돼 있습니다. 새 내용이 위키에 반영된 뒤(다음 배포 뒤) 다시 열어 제출해 주세요.」 | [닫기] |

- 화면의 위키 본문은 다시 얹어도 **여전히 옛 버전**이다(배포 전). [바뀐 곳 보기]는 v{a}→v{b} 사이 남이 바꾼 줄을 보여 준다.
- 다시 얹은 뒤 임시 저장의 `baseVersion` 도 v{b} 로 바꾼다.

### 5-2. 막힘·실패

| 경우 | 문구 | 버튼 |
| --- | --- | --- |
| 화면 차단 (`maskLeaks`) | 「제출하지 못했습니다 — 가려 둔 표기를 건드렸습니다」 + 걸린 항목 + 「해당 부분을 원래 표기로 되돌려 주세요. 수정은 그대로 있습니다.」 (기존 문구 유지) | [고치기] |
| 공개 검사 차단 (화면 또는 서버 400 `public-leak`) | 「제출하지 못했습니다 — 위키는 공개 저장소라 올릴 수 없는 표현이 있습니다」 + 걸린 줄(`hitLines`) + 「고친 뒤 다시 제출해 주세요. 수정은 그대로 있습니다.」 | [고치기] |
| 경고만 | 「제출할 수 있지만 확인해 주세요 — 위키는 공개 저장소에 올라갑니다」 + 경고 목록 | [그래도 제출] · [고치기] |
| 바뀐 것 없음 (400) | 「바뀐 곳이 없어 제출하지 않았습니다.」 | [닫기] |
| 그 밖 400·401·404·413·429·502·503 | `docs/sections/requests-chat-draft.md` 5-8 "제출 실패" 표 문구를 그대로 쓴다. 끝말 「초안은 그대로 있습니다.」 는 이 화면에서 「수정은 그대로 있습니다.」 로 바꾼다 | 같은 표 |

- 서버 원문(HTTP 상태·GitHub 오류·환경변수 이름)은 실무자에게 보이지 않는다. 관리자에게만 끝에 「· HTTP {상태}」 (기존 규칙).

## 6. 상태 이름과 내 요청 표시

### 6-1. 상태 전이표 (이름은 기존 그대로)

| 단계 | 저장소에서 | 내 요청 태그 (유지) | 보조 표시 (새로) | 안내에서 부르는 말 |
| --- | --- | --- | --- | --- |
| 초안 | 없음 (이 브라우저) | 안 뜸 | 「제출하지 않은 임시 저장」 줄 | 임시 저장 · 아직 제출 전 |
| 제출 | PR 열림 | `대기 중` | — | 제안을 올렸습니다 · 대기 중 |
| 다시 올려야 함 | PR 열림, 같은 문서의 다른 제안이 먼저 머지됨 | `대기 중` | 「다시 올려야 함」 | (6-3) |
| 머지 | main 에 들어감 | `머지됨` | 「배포 대기」 | 승인(머지)됨 · 다음 배포 때 위키에 반영 |
| 다음 배포 반영 | 배포됨 | `머지됨` | 「위키에 반영됨 · v{n}」 | 위키에 반영됨 |
| 반려 | 머지 없이 닫힘 | `닫힘` | — | 반려(닫힘) |

- 태그 이름은 바꾸지 않는다. 문서 제안은 `대기 중`·`머지됨`·`닫힘`, 편성표·시스템 요청은 `대기 중`·`승인됨`·`반려됨` 그대로다.
- 보조 표시는 태그 옆 회색 글자다. 새 태그를 만들지 않는 이유: 태그는 GitHub PR 상태 그대로라 GitHub 에서 직접 머지·닫아도 어긋나지 않는다. 보조 표시는 화면이 계산하는 값이라 틀릴 수 있어 태그와 나눈다.
- 이름 정리 제안(바꾸지는 않음): `닫힘` → `반려됨`. 다른 두 탭과 같은 말이 되고 안내 문서의 "반려"와 맞는다. 다만 작성자가 스스로 닫은 PR 도 `반려됨`으로 보이게 된다. 기존 R1 과 같은 항목이라 함께 결정(Q8).

### 6-2. 계산 규칙 (dev-front, S2·S3 뒤)

| 보조 표시 | 규칙 |
| --- | --- |
| 배포 대기 | `status:'approved'` 이고 화면 묶음 문서의 `version` < PR 의 목표 버전(`- 버전: v{a} → v{b}` 의 b). 새 문서는 그 코드의 문서가 화면 묶음에 없을 때 |
| 위키에 반영됨 · v{n} | `status:'approved'` 이고 묶음 `version` ≥ b. 새 문서는 코드가 묶음에 있을 때 |
| 다시 올려야 함 | `status:'pending'` 이고, 같은 `docCode` 의 **다른** 제안이 `approved` 이며 그 목표 버전 ≥ 이 PR 의 목표 버전 |
| (판정 불가) | 버전 줄이 없는 옛 PR — 보조 표시를 붙이지 않는다. 추측하지 않는다 |

### 6-3. 내 요청 한 줄 문구 (문서 제안 탭)

| 상태 | 둘째 줄 (회색) | 버튼 |
| --- | --- | --- |
| `대기 중` | 「관리자 확인을 기다리는 중입니다. 승인(머지)되면 다음 배포 때 위키에 반영됩니다.」 | [PR 열기 ↗] |
| `대기 중` · 다시 올려야 함 | 「같은 문서의 다른 제안이 먼저 승인돼, 이 제안은 그대로는 승인할 수 없습니다. 최신 문서에서 다시 고쳐 제출해 주세요. 이 PR 은 관리자가 닫습니다.」 | [문서에서 다시 고치기] · [PR 열기 ↗](내 수정 내용 확인용) |
| `머지됨` · 배포 대기 | 「승인(머지)됐습니다. 다음 배포 때 위키에 반영됩니다. 그 전까지 위키 화면은 그대로입니다.」 | [PR 열기 ↗] |
| `머지됨` · 위키에 반영됨 | 「위키에 반영됐습니다 (v{n}).」 | [문서 보기] |
| `닫힘` | 「반려(닫힘)됐습니다. 사유는 PR 의 의견에서 확인해 주세요. 의견이 없으면 관리자에게 물어 주세요.」 | [사유 보기 ↗] · [수정해서 다시 제안] |

- 기존 탭 위 안내(「문서 제안은 GitHub PR 입니다. 머지돼도 다음 배포 전까지는 위키 화면에 반영되지 않습니다.」)는 유지한다.
- 「이 PR 은 관리자가 닫습니다」는 운영 규칙(O3)이 정해진 뒤에만 쓴다. 정해지기 전에는 그 문장을 뺀다.

### 6-4. 반영 알림

알림 수단은 허브 화면뿐이다(메일·메신저 없음). 앱 진입 때 `/api/proposals` 를 1회 읽고(지금은 내 요청·승인 관리 진입 때만), 이 브라우저에 저장한 "마지막으로 본 상태"(키 `wikihub.seen.{계정 아이디}`, PR 번호 → 상태·보조 표시)와 비교해 **내 제안 중 바뀐 것**만 알린다.

## 7. 클릭 수와 기다리는 단계

| 동선 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 오탈자 한 곳 고쳐 제출 | 문서 → [✎ 수정 제안] → 전체 본문에서 위치 찾기 → [다음 · 변경 확인] → 사유 입력 → [제안 제출] = **3클릭 + 사유 입력** | 장 [편집] → 고침 → [제출] = **2클릭, 입력 없음** (경고 있으면 +1) |
| 제출 후 상태 확인 | 완료 화면 [내 요청 현황] 1클릭. 나중에 다시 보려면 메뉴 → 내 요청 → [새로고침] 2클릭 | 성공 줄 [내 요청에서 보기] 1클릭. 나중엔 배지가 있는 메뉴 1클릭(앱 진입 때 읽음) |
| 409 를 만났을 때 | 해결 길 없음 (다음 배포까지 대기) | 내 장 그대로면 [다시 제출] **1클릭** |
| 반영됐는지 알기 | 알 길 없음 (문서를 열어 눈으로 비교) | 배지 → 내 요청 「위키에 반영됨 · v{n}」 1클릭 |
| 관리자 본인 수정 반영 | 제출 + GitHub 에서 머지 2클릭 + 배포 대기 | 같음 (완료 줄에서 GitHub 로 바로 가는 1클릭 단축) |

기다리는 단계 (사람·시스템 기준): ① PR 만들기 — 몇 초 ② 관리자 확인(머지) — 사람, 정해진 시간 없음 ③ 다음 배포 — 머지 뒤 배포까지 걸리는 시간은 확인 필요(O2). 로컬 허브는 업데이트할 때.
