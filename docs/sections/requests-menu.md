# 하위 메뉴 편집 제안 — 제출 뒤 흐름·상태·권한·문구

작성 `requests-planner` · 2026-11-26 · 기획안 `docs/plan/2026-11-26-wiki-submenu-editing.md` 의 requests-planner 몫

범위: 하위 메뉴 **이름 바꾸기 · 새 하위 메뉴 · 순서 바꾸기 · 빈 메뉴 지우기** 제안이 생기고 결정되는 흐름. 입구(사이드바 `⋯`, `+ 새 하위 메뉴`, 위키 목록 [메뉴 편집])의 자리와 모양은 wiki-ux 설계안이 정한다. 이 문서는 **[제안 올리기]를 누르기 직전 검사부터 반영될 때까지**의 상태·권한·막힘·충돌·문구를 정한다.

이 문서는 흐름·상태·규칙·문구만 정한다. 코드는 dev-server·dev-front 가 옮긴다. `「」` 안 문자열은 그대로 옮기고 `{ }` 는 채워 넣는 값이다. 화면 문구는 합니다체다.

### 이 문서가 따르는 확정 사항

| # | 확정 | 이 문서에 미치는 것 |
| --- | --- | --- |
| R1 | 메뉴 정의는 `지식/<카테고리>/_menu.json` 카테고리별 한 장 | 충돌은 **같은 카테고리 안에서만** 생긴다. 편성 제안과 프로모션 제안은 서로 막지 않는다 |
| R2 | 제안 → 승인(머지) → 다음 배포 | 관리자도 바로 바꾸는 길이 없다. 제출 순간에 바뀌는 것은 없다 |
| R3 | 이용 안내는 하위 메뉴 만들기를 막는다 | 이용 안내에는 하위 메뉴가 없으므로 이번에 이용 안내에서 할 수 있는 메뉴 동작은 **없다** |
| R4 | 1단(편성·프로모션·이용 안내) 이름 바꾸기는 범위 밖 | 1단 줄에는 `⋯` 를 두지 않는다 |
| R5 | **메뉴는 2단까지만**(예: 「프로모션 › 배너 규격」). 3단 없음. 스키마에 `parent` 자리도 두지 않는다 | 기획안 A 표의 `subs[].parent` 줄은 **지운다**(dev-server·ops 에 전달, 12절). 새 하위 메뉴는 늘 1단 바로 아래에 생긴다. 하위 메뉴 아래에 메뉴를 만드는 입구·문구·상태는 없다 |
| R6 | 하위 메뉴는 `_menu.json` 순서 그대로 보인다 | 순서 제안이 승인·반영되면 화면 순서가 그대로 바뀐다. "바꿨는데 다시 섞인다"가 없다 |
| R7 | 문서 옮기기·문서 있는 메뉴 지우기는 다음 차수 | 문서가 있는 메뉴의 [지우기]는 막고 이유를 보인다 |
| R8 | 편성 코드 머리글 `PGM`, 메뉴별 `PGM-S01-` 꼴 | 새 하위 메뉴 완료 문구에 코드를 보이지 않는다(코드는 첫 문서가 올라갈 때 정해진다) |

**R5 와 기획안의 차이:** 기획안 "범위 밖" 표의 3단 줄("스키마에 `parent` 칸 자리만 남겨 둔다")과 A 표의 `subs[].parent` 줄은 R5 확정으로 무효다. 빈 칸을 남겨 두면 ops 가 값을 넣거나 dev-server 가 읽기 코드를 미리 쓰게 되고, 화면이 그 값을 모른 채 메뉴를 그리면 사이드바와 서버 검사가 갈라진다. 그래서 **자리를 두지 않고, 빌드 검사가 `subs[]` 항목에 정해진 칸 밖의 이름(`parent` 포함)이 있으면 실패**하게 한다(S9). 문서 프론트매터의 `parent`(문서 트리, `knowledgeDocs.ts` `flattenTree`)는 메뉴가 아니므로 이 결정과 관계없다.

## 1. 지금 실제로 일어나는 일 (문구의 근거)

| 순간 | 실제 동작 | 근거 |
| --- | --- | --- |
| 메뉴 이름·목록 | 코드 두 곳(`src/data/docs.ts` `subcategories`, `server/knowledge.ts` `DOC_SUBCATEGORIES`)과 챗봇 프롬프트에 손으로 적혀 있다. 허브 화면에 편집 입구가 없다 | 기획안 "현재 상태" 1 |
| 지금의 요청 방법 | 「섹션(서브메뉴) 추가·이름 바꾸기」는 메신저로 관리자에게 요청 → 개발 PR | `docs/sections/requests-rollout.md` 8-1 |
| 제안 목록 | `/api/proposals` 가 GitHub PR 최근 50건 중 `docs/` 브랜치만 읽는다. **`docs/edit-` 가 아니면 전부 `kind:'new'`(새 문서)** | `server/github.ts` `parseProposalPr` |
| 새 문서 브랜치 이름 | `docs/{문서 코드 소문자}-{시각}`. 코드가 `MENU-` 로 시작하면 `docs/menu-…` 가 되어 메뉴 제안 브랜치와 겹친다 | `server/github.ts` `slugify`·`createDocPR` |
| 사유 읽기 | `## 수정 사유` / `## 등록 사유` 절만 읽고, 끝의 `내용을 확인하고 이상 없으면 머지해 주세요.` 앞에서 자른다 | `PR_FOOTER`, `parseProposalPr` |
| 상태 | PR 상태 그대로: 열림 `대기 중`, 머지 `머지됨`, 머지 없이 닫힘 `닫힘` | `MyRequests.tsx` `PrStatusTag` |
| 내 요청 | 화면 진입 때 1회 읽음 + [새로고침]. "내 것"은 `requestedBy === session.name`(이름) | `MyRequests.tsx`, `AppStore.tsx` `ensureProposals` |
| 승인 관리 | 관리자만 화면에 보임(`session.role`). 문서 제안은 읽기 전용, 머지는 GitHub. `대기 중`만 목록에 나온다 | `Approvals.tsx` |
| 서버 권한 | 제안 API 는 로그인(배포본)·하루 30건(`RATE_PR`)만 본다. 관리자 여부는 보지 않는다 | `server/guard.ts` |
| 반영 시점 | 화면은 빌드 때 묶은 파일을 쓴다. 메뉴 파일도 빌드에 묶인다 → 머지 뒤 **다음 배포** 때 화면과 서버 검사가 함께 바뀐다. 로컬 허브는 업데이트 때 | 기획안 A "반영 시점" |
| 새 문서 서버 검사 | `isKnownPlace` 는 **배포된(묶인) 메뉴**를 본다. 저장소 main 의 메뉴는 보지 않는다 | `server/knowledge.ts` |

그래서 메뉴 제안의 어떤 문구도 제출 순간에 "바꿨습니다"·"만들었습니다"·"지웠습니다"를 쓰지 않는다. 제출 순간에 일어나는 일은 "제안이 올라갔다"뿐이고, 사이드바는 **승인되고 다음 반영이 끝날 때까지 그대로**다.

## 2. 실무자가 헷갈리는 지점

| # | 지점 | 왜 헷갈리나 | 이 문서의 해법 |
| --- | --- | --- | --- |
| M1 | 이름을 바꿨는데 사이드바가 그대로다 | "안 됐다"로 읽고 같은 제안을 또 올린다 | 제출 직후 문구 + 사이드바 그 줄 옆 「바꾸는 중」 표시(8절) |
| M2 | 새 메뉴를 만들었는데 그 메뉴에 문서를 올릴 수 없다 | 승인·반영 전에는 화면에도 서버 검사에도 메뉴가 없다 | 완료 문구에 「반영된 뒤에 문서를 올릴 수 있습니다」(8절). 반영 전에는 고르기 목록에 나오지 않으니 막힐 일 자체가 없다 |
| M3 | 승인됐는데 화면이 그대로다 | 승인과 반영 사이에 시간이 있다 | 상태 보조 표시 「반영 대기」 → 「반영됨」(4절) |
| M4 | 같은 메뉴에 남도 제안을 올렸다 | 먼저 승인된 쪽 때문에 내 제안이 승인될 수 없게 된다 | 편집 시작 때 알림, 승인될 수 없게 되면 「다시 올려야 함」 + [다시 올리기] 1클릭(7절) |
| M5 | 이미 지우기로 승인된 메뉴가 화면에 아직 보인다 | 반영 전이라 보이는데, 이름을 바꾸거나 문서를 올리려 하면 막힌다 | 막힐 때 이유를 「지우기로 승인돼 다음 반영 때 없어집니다」로 쓴다(7절) |
| M6 | [지우기]가 꺼져 있다 | 왜 꺼졌는지 모른다 | 꺼진 이유 한 줄을 버튼 바로 아래에(6절) |
| M7 | "메뉴" 제안이 "새 문서"로 보인다 | 지금 판정이 `docs/edit-` 가 아니면 전부 새 문서 | 서버 분기를 **화면보다 먼저** 넣는다(S1) |

## 3. 흐름 (바꾼 뒤)

```
사이드바 하위 메뉴 줄 ⋯ / + 새 하위 메뉴 / 위키 목록 [메뉴 편집]     ← 자리는 wiki-ux
  │ 열 때: 같은 카테고리의 대기 중 메뉴 제안 확인(7-1)
  │ 화면이 바로 끄는 것: [지우기](문서 있음·고정 메뉴), [위로](맨 위), [아래로](맨 아래)
  ▼
이름 입력 (이름 바꾸기·새 하위 메뉴만) · 사유는 선택
  ▼
[제안 올리기] 한 번
  │ 화면 검사(서버 호출 없음): 이름 규칙(6-1)
  │ 공개 검사 /api/publicCheck — 이름은 경고도 차단(6-1), 사유는 새 문서 기준
  ▼
/api/proposeMenu {category, op, subId?, label?, direction?, reason, via:'menu', base}
  → 서버: main 의 _menu.json 읽기 → 기준 확인(base, 7-3) → 동작 하나 적용 → 검사(6-2) → 브랜치·커밋·PR
  │ 400 → 6-2 문구 (아무것도 안 생김)
  │ 409 → 7-3 문구 (아무것도 안 생김)
  ▼
PR 열림 = 「대기 중」 → 제출 직후 줄(8절) + 사이드바 그 줄 옆 「바꾸는 중」
  ▼
GitHub 에서 머지 = 「머지됨 · 반영 대기」 → 다음 배포 = 「머지됨 · 반영됨」
GitHub 에서 닫음 = 「닫힘」
다른 메뉴 제안이 먼저 머지돼 이 제안을 그대로 승인할 수 없음 = 「대기 중 · 다시 올려야 함」
```

- 제안 하나에 동작 하나(기획안 C). 순서는 한 칸씩이다. 세 칸 옮기려면 제안 세 건이 된다 — 같은 메뉴의 연속 순서 제안은 7-2 의 충돌을 낳으므로, 화면은 **같은 메뉴에 내 순서 제안이 대기 중이면 [위로]/[아래로]를 끄고** 이유를 보인다(6-1). 여러 칸 옮기기는 Q4.
- 사유는 비워도 된다. 비우면 PR 본문에 「근거 미기재」로 올라간다(기획안 C). 서버는 메뉴 제안에서 사유를 필수로 보지 않는다(문서 수정과 다름 — 메뉴 이름은 diff 한 줄이라 승인자가 사유 없이도 판단할 수 있다).
- 진입 이름은 하나: `메뉴 편집` (`VIA_LABEL.menu`). 사이드바와 위키 목록 어느 쪽에서 올려도 같다.

## 4. 상태 전이표 (이름은 문서 제안과 같다)

| 단계 | 저장소에서 | 내 요청 태그 (현행 유지) | 보조 표시 (회색, 새로) | 안내에서 부르는 말 |
| --- | --- | --- | --- | --- |
| 막힘 | **아무것도 안 생김** | 안 뜸 | — | 올리지 않았습니다 |
| 제출 | PR 열림 | `대기 중` | — | 제안을 올렸습니다 · 승인을 기다립니다 |
| 다시 올려야 함 | PR 열림, 그대로는 머지할 수 없음(7-2) | `대기 중` | 「다시 올려야 함」 | 다른 제안이 먼저 승인돼 다시 올려야 합니다 |
| 머지 | main 에 들어감 | `머지됨` | 「반영 대기」 | 승인됐습니다 · 다음 반영 때 바뀝니다 |
| 다음 배포 반영 | 배포됨 | `머지됨` | 「반영됨」 | 사이드바에 반영됐습니다 |
| 반려 | 머지 없이 닫힘 | `닫힘` | — | 반려됐습니다 |

- 태그 이름은 문서 제안 탭과 같은 `대기 중`·`머지됨`·`닫힘` 을 그대로 쓴다. 한 탭 안에서 문서 제안과 메뉴 제안이 다른 태그를 쓰면 "상태 이름은 하나" 원칙이 깨지기 때문이다. 태그에 들어 있는 "머지"를 쉬운 말로 바꾸는 일(`머지됨` → `승인됨`, `닫힘` → `반려됨`)은 모든 위키 제안에 한꺼번에 적용해야 하므로 Q1 로 올린다.
- 보조 표시는 화면이 계산하는 값이다. 태그(GitHub 상태 그대로)와 나눠, 계산이 틀려도 태그는 틀리지 않게 한다(`requests-doc-edit.md` 6-1 과 같은 원칙).

### 4-1. 보조 표시 계산 (dev-front, S3 뒤)

화면이 묶어 가진 메뉴(`_menu.json`, 지금 배포본)와 PR 에서 읽은 값(S3)을 비교한다. **못 읽으면 붙이지 않는다. 추측하지 않는다.**

| 동작 | 「반영 대기」 (`머지됨` 인데) | 「반영됨」 |
| --- | --- | --- |
| 이름 바꾸기 | 묶인 메뉴에서 `menuId` 의 이름 ≠ 새 이름 | 같음 |
| 새 하위 메뉴 | 묶인 메뉴에 `menuId` 가 없음 | 있음 |
| 순서 바꾸기 | 묶인 메뉴에서 `menuId` 와 `neighborId` 의 앞뒤가 아직 옛 순서 | 새 순서 |
| 지우기 | 묶인 메뉴에 `menuId` 가 있음 | 없음 |

「다시 올려야 함」은 서버가 내려 준 `needsResubmit`(S4)이 참일 때만 붙인다.

## 5. 권한표

메뉴 제안은 문서 제안과 같은 권한을 쓴다. 관리자라고 바로 바뀌는 길은 없다(R2).

| 화면·동작 | 실무자 | 관리자 | 화면에서 숨김 / 서버가 막음 |
| --- | --- | --- | --- |
| 하위 메뉴 `⋯` · [메뉴 편집] 보기 | 보임 | 보임 | 배포본에서 로그인 전에는 화면 전체가 `AuthGate` 뒤. 운영 배포에서 계정 기능이 꺼지면 입구를 숨기고 서버도 닫는다(「허브 점검 중」, `server/guard.ts`) |
| 1단(편성·프로모션·이용 안내) `⋯` | 없음 | 없음 | R4. 화면에 입구 없음. 서버 계약에 1단 동작이 없다 |
| 이름 바꾸기 | 된다 | 된다 | 서버: 로그인(401)·하루 30건(429, 문서 제안과 같은 한도를 나눠 씀)·이름 규칙·공개 검사(400)·기준 확인(409) |
| 새 하위 메뉴 | 프로모션·편성에서 된다 | 같음 | 화면: `allowNewSub:false`(이용 안내)면 `+ 새 하위 메뉴` 숨김. **서버도 400** |
| 하위 메뉴 아래에 메뉴 만들기 | 없음 | 없음 | R5. 입구 없음. 서버 요청 형식에 위 메뉴를 고르는 칸이 없고, 빌드 검사가 `parent` 칸을 거부한다 |
| 순서 바꾸기 | 된다 | 된다 | 화면: 맨 위의 [위로]·맨 아래의 [아래로] 끔. 서버: 같은 조건 400, 이웃이 바뀌었으면 409 |
| 빈 메뉴 지우기 | 문서 0건 · 고정 아님 · 그 메뉴로 가는 대기 중 새 문서 없음일 때 된다 | 같음 | 화면이 끄고 이유를 보임(6-1). **서버가 main 기준으로 다시 확인해 400** — 화면은 배포본 기준이라 그 사이 머지된 문서를 모를 수 있다 |
| 고정 메뉴(챗봇·리포트가 쓰는 메뉴) 이름 바꾸기 | 된다 | 된다 | 이름은 바뀌어도 id 가 그대로라 챗봇이 계속 쓴다 |
| 고정 메뉴 지우기 | 못 함 | 못 함 | 화면 끔 + 서버 400 |
| 내 요청 — 내 메뉴 제안 보기 | 내 것만 | 내 것만 | 화면에서 거름(이름 기준, Q3 과 같은 약점). 서버는 전체 목록을 준다 — PR 은 어차피 공개라 보안 경계 아님 |
| [다시 올리기] (다시 올려야 함일 때) | 내 것만 | 내 것만 | 화면: 내 것일 때만 버튼. 서버: 옛 제안 번호를 받으면 그 PR 의 요청자 이름 = 지금 계정 이름일 때만 옛 PR 을 닫는다(S6, Q2) |
| 승인 관리 — 메뉴 제안 보기 | 못 들어감 | 된다 | 화면만 숨김(`session.role`). 읽기 전용이라 서버는 따로 막지 않는다 |
| 머지·닫기 | GitHub 쓰기 권한이 있으면 된다 | 같음 | 허브가 아니라 GitHub 권한이 막는다(D5 ①: 관리자 계정 담당자 = GitHub 승인자) |

## 6. 막힘 조건과 문구

원칙: 막힐 때는 **이유 한 줄 + 지금 할 일 한 줄**. 막히면 저장소에 아무것도 생기지 않는다. 화면 문구에 id·JSON·PR·머지·배포·코드라는 말을 쓰지 않는다.

### 6-1. 화면이 미리 끄거나 막는 것 (서버 호출 전)

| 조건 | 자리 | 문구 |
| --- | --- | --- |
| [지우기] — 문서가 있음 | 꺼진 버튼 아래 회색 | 「문서가 {n}개 있어 지울 수 없습니다. 문서를 다른 메뉴로 옮긴 뒤 지워 주세요. 옮기는 기능은 다음에 생깁니다. 지금은 관리자에게 알려 주세요.」 |
| [지우기] — 고정 메뉴 | 같은 자리 | 「이 메뉴는 챗봇 답변과 리포트가 쓰는 메뉴라 지울 수 없습니다. 이름은 바꿀 수 있습니다.」 |
| [지우기] — 이 메뉴로 올라온 새 문서가 대기 중 | 같은 자리 | 「이 메뉴에 승인을 기다리는 새 문서가 {n}건 있어 지울 수 없습니다. 그 문서가 정리된 뒤에 지워 주세요.」 |
| [위로] — 맨 위 / [아래로] — 맨 아래 | 버튼 꺼짐 | (문구 없음. 버튼 이름 옆 「맨 위」/「맨 아래」 회색) |
| [위로]/[아래로] — 이 메뉴에 내 순서 제안이 대기 중 | 꺼진 버튼 아래 | 「이 메뉴의 순서 바꾸기 제안이 이미 승인을 기다리고 있습니다. 승인된 뒤에 한 칸 더 옮겨 주세요.」 |
| 이름이 비었음 | 입력 칸 아래 | 「이름을 적어 주세요.」 |
| 21자 이상 | 같은 자리 (글자 수 `{n}/20` 상시 표시) | 「이름은 20자까지 쓸 수 있습니다.」 |
| 두 줄 이상(줄바꿈) | 같은 자리 | 「이름은 한 줄로 적어 주세요.」 |
| 같은 카테고리에 같은 이름(공백·대소문자 무시) | 같은 자리 | 「'{이름}'은(는) 이 메뉴에 이미 있습니다. 다른 이름을 적어 주세요.」 |
| 지금 이름과 같음(이름 바꾸기) | [제안 올리기] 꺼짐 + 같은 자리 | 「지금 이름과 같습니다.」 |
| 공개 검사 — 이름에 걸림(차단·경고 모두) | 같은 자리 | 「위키는 누구나 볼 수 있는 곳이라 이 이름은 쓸 수 없습니다 — {걸린 낱말}. 회사 이름·금액이 없는 이름으로 바꿔 주세요.」 |
| 공개 검사 — 사유에 차단 | 사유 칸 아래 | 「위키는 누구나 볼 수 있는 곳이라 사유에 올릴 수 없는 표현이 있습니다 — {걸린 줄}. 고친 뒤 다시 올려 주세요.」 |
| 공개 검사 — 사유에 경고만 | 확인 상자 | 「올릴 수 있지만 확인해 주세요 — 사유는 누구나 볼 수 있는 곳에 남습니다.」 + 경고 목록 · [그래도 올리기] [고치기] |

- **이름은 경고도 차단한다.** 메뉴 이름은 사이드바에 늘 보이고 메뉴 파일에 계속 남는다. 짧은 칸이라 "그래도 올리기"를 줄 이유가 없다. 사유는 새 문서와 같은 기준(차단은 막고 경고는 확인)이다.
- `/` 와 `·` 는 허용한다(예: 「영화/시리즈」).

### 6-2. 서버가 막는 것 (400 — 화면 검사를 지나쳤거나 우회했을 때)

서버는 6-1 의 이름 규칙·공개 검사를 **모두 다시** 한다(요청을 직접 보내 우회할 수 있다). 서버 문장은 아래를 그대로 쓰고, 화면은 「올리지 못했습니다 — {서버 문장}」으로 보인다.

| `code` | 조건 | 서버 문장 (화면에 그대로) |
| --- | --- | --- |
| `label-empty` · `label-long` · `label-line` | 이름 규칙 | 「이름을 적어 주세요」 / 「이름은 20자까지 쓸 수 있습니다」 / 「이름은 한 줄로 적어 주세요」 |
| `label-dup` | main 메뉴 **또는 같은 카테고리의 대기 중 메뉴 제안**에 같은 이름 | 「'{이름}'은(는) 이 메뉴에 이미 있거나, 같은 이름으로 바꾸자는 제안이 승인을 기다리고 있습니다. 다른 이름을 적어 주세요」 |
| `label-same` | 지금 이름과 같음 | 「지금 이름과 같아 올리지 않았습니다」 |
| `public-leak` | 공개 검사 차단 | 「위키는 누구나 볼 수 있는 곳이라 올릴 수 없는 표현이 있습니다」 + `hitLines` |
| `no-new-sub` | `allowNewSub:false` 카테고리 | 「이 메뉴에는 하위 메뉴를 만들 수 없습니다」 |
| `fixed` | 고정 메뉴 지우기 | 「이 메뉴는 챗봇 답변과 리포트가 쓰는 메뉴라 지울 수 없습니다. 이름은 바꿀 수 있습니다」 |
| `has-docs` | main 기준 문서 1건 이상 | 「문서가 {n}개 있어 지울 수 없습니다. 문서를 다른 메뉴로 옮긴 뒤 지워 주세요」 |
| `has-pending-docs` | 이 메뉴로 가는 대기 중 새 문서 제안 | 「이 메뉴에 승인을 기다리는 새 문서가 {n}건 있어 지울 수 없습니다」 |
| `edge` | 맨 위 [위로]·맨 아래 [아래로] | 「더 옮길 자리가 없습니다」 |
| `bad-op` | 그 밖 입력 오류(모르는 카테고리·동작) | 「요청 내용을 알아보지 못했습니다. 화면을 새로 고친 뒤 다시 해 주세요」 |

화면 버튼: 400 은 [고치기](입력 칸으로 돌아감, 입력한 이름 유지) · [닫기].

### 6-3. 그 밖 실패

`docs/sections/requests-chat-draft.md` 5-8 "제출 실패" 표의 401·429·503·502·네트워크 문구를 그대로 쓰되, 「제출」→「올리기」, 끝말 「초안은 그대로 있습니다.」→「적은 이름은 그대로 있습니다.」로 바꾼다. 「GitHub에 제안을 올리지 못했습니다」는 「제안을 올리지 못했습니다」로 바꾼다(실무자 화면에 GitHub 를 쓰지 않는다). 관리자에게만 끝에 「· HTTP {상태}」(기존 규칙).

## 7. 충돌과 반려

### 7-1. 같은 카테고리에 대기 중 메뉴 제안이 있을 때 — 알리고, 막지 않는다

판정: `/api/proposals` 의 `kind:'menu'`, `status:'pending'`, `menuCategory` 일치. **편집 입구를 여는 순간** 한 번 보인다. 목록을 못 읽었으면 알리지 않고 막지도 않는다.

| 상황 | 문구 | 다음 행동 |
| --- | --- | --- |
| 같은 하위 메뉴에 남의 제안 | 「'{메뉴 이름}'에 승인을 기다리는 제안이 있습니다 ({요청자} · {월/일} · {한 줄 요약}). 같은 메뉴를 바꾸면 나중에 승인되는 쪽은 다시 올려야 할 수 있습니다.」 | [그래도 바꾸기] · [그 제안 보기] |
| 같은 하위 메뉴에 내 제안 | 「'{메뉴 이름}'에 내가 올린 제안이 승인을 기다리고 있습니다 ({월/일} · {한 줄 요약}). 그 제안을 고치려는 것이면 먼저 관리자에게 알려 주세요.」 | [그래도 바꾸기] · [내 요청에서 보기] |
| 같은 카테고리의 다른 메뉴에 제안 | (사이드바 그 메뉴 줄 옆 「바꾸는 중」 표시만. 상자는 띄우지 않는다) | — |
| 같은 카테고리에 새 하위 메뉴 제안이 대기 중인데 또 새 메뉴를 만들 때 | 「이 메뉴에 새 하위 메뉴를 만들자는 제안이 이미 {n}건 승인을 기다리고 있습니다 ({이름들}). 함께 올려도 되지만, 하나가 승인되면 나머지는 다시 올려야 할 수 있습니다.」 | [그래도 만들기] · [취소] |

「바꾸는 중」 표시: 사이드바 하위 메뉴 줄 오른쪽 회색 글자. 마우스를 올리면 「승인을 기다리는 제안: {한 줄 요약}」. 대기 중 제안이 반영돼 사라질 때까지(태그가 `대기 중` 이거나, `머지됨`·반영 대기일 때) 보인다. 자리와 모양은 wiki-ux.

### 7-2. 먼저 승인된 제안 때문에 그대로 승인할 수 없게 될 때 — 「다시 올려야 함」

메뉴 파일은 카테고리마다 한 장이라, 같은 카테고리의 제안 두 건이 **같은 줄이나 바로 붙은 줄**을 고치면 한쪽이 머지된 뒤 다른 쪽은 GitHub 에서 충돌로 머지할 수 없다.

| 먼저 승인된 것 → 남은 것 | 저장소에서 | 처리 |
| --- | --- | --- |
| 이름 바꾸기 A → 같은 메뉴 이름 바꾸기 | 같은 줄 충돌 | 남은 쪽 「다시 올려야 함」 |
| 새 메뉴 → 새 메뉴 | 둘 다 목록 끝에 붙여 충돌 | 남은 쪽 「다시 올려야 함」. 서버가 id 와 코드 머리글을 **대기 중 메뉴 제안까지 피해서** 정하므로(S5), 다시 올려도 같은 이름이면 같은 결과다 |
| 지우기 → 같은 메뉴 이름 바꾸기·순서 | 대상이 main 에 없음 | 남은 쪽 「다시 올려야 함」이지만 다시 올리면 409(이미 지워짐). 문구는 아래 「대상이 지워짐」 |
| 순서 → 이웃 메뉴 순서 | 붙은 줄 충돌일 수 있음 | GitHub 판정을 따른다 |
| 떨어진 줄끼리 | 충돌 없이 둘 다 머지됨 | 그대로 |
| 이름 바꾸기 → 다른 메뉴 이름을 같은 이름으로 | **충돌 없이 둘 다 머지돼 이름이 겹친다 → 빌드가 실패한다** | 서버가 대기 중 제안의 새 이름까지 보고 막는다(`label-dup`, S5). 그래도 동시에 들어오면 승인자 점검표(9-2)의 「미리보기 실패면 머지하지 않기」가 마지막 방어선이다 |

판정(S4): `/api/proposals` 가 대기 중 메뉴 제안에 한해 (a) GitHub 의 `mergeable` 값이 `false` 이거나 (b) 대상 메뉴(`menuId`)가 main 메뉴에 없으면 `needsResubmit:true`, `resubmitReason:'conflict'|'gone'` 을 붙인다. 값을 아직 모르면(`mergeable:null`) 붙이지 않는다.

| 상황 | 내 요청 둘째 줄 | 버튼 |
| --- | --- | --- |
| `conflict` | 「같은 메뉴의 다른 제안이 먼저 승인돼, 이 제안은 그대로는 승인할 수 없습니다. [다시 올리기]를 누르면 같은 내용으로 새로 올리고 이 제안은 닫힙니다.」 | [다시 올리기] (1클릭) · [자세히 보기 ↗] |
| `gone` | 「'{메뉴 이름}'은(는) 지우기로 승인돼 다음 반영 때 없어집니다. 이 제안은 더 이상 쓸 수 없습니다. 관리자가 닫습니다.」 | [자세히 보기 ↗] |

[다시 올리기]: 화면이 PR 에서 읽은 같은 동작·이름·사유로 `/api/proposeMenu` 를 다시 부르고 `replaces: {옛 번호}` 를 붙인다. 서버는 새 PR 을 연 뒤 옛 PR 을 닫고 의견 「새 제안 #{새 번호}로 다시 올렸습니다」를 남긴다(S6). 다시 올릴 때 6-2·7-3 에 걸리면 그 문구를 그대로 보인다(예: 이름 바꾸기인데 먼저 승인된 쪽이 이미 같은 이름으로 바꿨으면 `label-same`).

### 7-3. 화면이 본 메뉴와 저장소 메뉴가 다를 때 — 409

머지됐지만 아직 반영 전이면 화면은 옛 메뉴를 보여 준다. 그 상태로 올린 제안이 엉뚱한 곳을 바꾸지 않도록 화면은 **자기가 본 것**을 `base` 로 함께 보낸다: 대상 메뉴의 이름(`label`), 순서 바꾸기면 바꿀 이웃의 id(`neighborId`). 서버는 main 과 다르면 PR 을 열지 않고 409 와 `{ code, mainLabel? }` 를 준다. 새 하위 메뉴는 기준 확인을 하지 않는다(이름 겹침만 본다).

| `code` | 조건 | 화면 문구 | 버튼 |
| --- | --- | --- | --- |
| `gone` | 대상 메뉴가 main 에 없음(지우기가 먼저 승인됨) | 「'{메뉴 이름}'은(는) 지우기로 승인돼 다음 반영 때 없어집니다. 올리지 않았습니다.」 | [닫기] |
| `renamed` | 대상 이름 ≠ main 이름 | 「이 메뉴 이름은 그사이 '{mainLabel}'(으)로 바뀌기로 승인됐습니다. 올리지 않았습니다. 바뀐 이름이 반영된 뒤 다시 해 주세요.」 | [닫기] |
| `moved` | 순서 이웃이 main 과 다름 | 「메뉴 순서가 그사이 바뀌기로 승인됐습니다. 올리지 않았습니다. 바뀐 순서가 반영된 뒤 다시 옮겨 주세요.」 | [닫기] |

- 문서 수정 409 와 달리 "최신본에 다시 얹기"를 하지 않는다. 메뉴 동작은 한 줄이고, 바뀐 메뉴를 사용자가 화면에서 볼 수 없는 상태(반영 전)에서 자동으로 얹으면 무엇을 바꾸는지 사용자가 확인할 수 없다.

### 7-4. 지워진 메뉴·반영 전 새 메뉴로 새 문서를 올릴 때 (새 문서 흐름과의 경계)

| 상황 | 지금 동작 | 바꾼 뒤 | 문구 (새 문서 화면) |
| --- | --- | --- | --- |
| 새 메뉴가 승인됐지만 반영 전 | 고르기 목록에 없음 | 그대로. 막힐 일이 없다 | (없음) |
| 지우기가 승인됐지만 반영 전에 그 메뉴로 새 문서 | `isKnownPlace` 는 배포본을 봐 통과 → 머지되면 문서가 「기타」로 떨어진다 | `createDocPR` 이 main 메뉴에 그 하위 메뉴가 있는지 확인해 409 `menu-gone`(S7) | 「'{메뉴 이름}'은(는) 지우기로 승인돼 다음 반영 때 없어집니다. 다른 하위 메뉴를 골라 주세요. 쓴 내용은 그대로 있습니다.」 |
| 지우기 제안이 대기 중인 메뉴로 새 문서 | 아무 표시 없음 | 하위 메뉴 고르기 아래 회색 경고, 제출은 막지 않음 | 「이 하위 메뉴를 지우자는 제안이 승인을 기다리고 있습니다. 문서가 올라가면 그 제안은 승인되지 않습니다.」 |

(마지막 줄의 "승인되지 않습니다"는 서버가 지우기를 다시 확인하지 않으므로 운영 규칙으로 지킨다: 승인자 점검표 9-2 ③.)

### 7-5. 반려

- 허브에는 반려 버튼이 없다. 관리자가 GitHub 에서 PR 을 **머지하지 않고 닫으면** `닫힘` 이 된다. 사유는 PR 의견으로 남긴다(운영 규칙 O3, `requests-doc-edit.md` 와 같음).
- 문구는 "사유가 전달된다"라고 쓰지 않는다. 허브가 사유를 읽어 오지 않기 때문이다.

| 자리 | 문구 | 버튼 |
| --- | --- | --- |
| 내 요청 둘째 줄 | 「반려됐습니다. 사유는 [사유 보기]에서 확인해 주세요. 사유가 없으면 관리자에게 물어 주세요.」 | [사유 보기 ↗] · [다시 제안하기](같은 메뉴의 편집 입구를 연다) |

## 9. 내 요청 · 승인 관리 표시

### 9-1. 한 줄 요약 (카드 제목 — 두 화면 같음)

`docTitle` 자리에 서버가 만든 한 줄 요약을 넣는다(S3). 화면은 그대로 보이기만 한다.

| 동작 | 한 줄 요약 | 예 |
| --- | --- | --- |
| 이름 바꾸기 | `{카테고리} › {전} → {후}` | 프로모션 › 운영 참고자료 → 운영 자료 |
| 새 하위 메뉴 | `{카테고리} › + {이름}` | 편성 › + 극장 개봉작 |
| 순서 | `{카테고리} › {이름} 한 칸 {위로/아래로}` | 편성 › TV 방송 한 칸 위로 |
| 지우기 | `{카테고리} › − {이름}` | 프로모션 › − 업무 프로세스 |

카테고리 이름은 1단 표시 이름(`편성`·`프로모션`)이다. 하위 메뉴 아래 단은 없다(R5).

### 9-2. 승인 관리 (`Approvals.tsx`)

| 자리 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 탭 | 「문서 수정 {n}」 | 「위키 제안 {n}」 — 새 문서·수정·메뉴를 함께 담는다(탭 이름은 wiki-ux 확인) |
| 목록 한 줄 | 제목 · 요청자 · 날짜 | 앞에 종류 태그 「메뉴」 + 9-1 요약. 「다시 올려야 함」이면 회색 표시 |
| 상세 머리 | `{요청자} · {날짜} · 새 문서/문서 수정 · PR #{n}` | 메뉴는 `{요청자} · {날짜} · 메뉴 {이름 바꾸기/새 하위 메뉴/순서 바꾸기/지우기} · 진입 메뉴 편집` |
| 상세 사유 | 「수정 사유 — …」 | 「변경 사유 — {사유}」, 비었으면 「변경 사유 — 근거 미기재」 |
| 상세 안내 (메뉴만) | — | 「이 제안은 하위 메뉴 목록 한 곳만 바꿉니다. 문서는 바뀌지 않습니다. 승인은 GitHub 화면의 [Merge] 버튼으로 합니다. 승인해도 다음 반영 전까지는 사이드바가 그대로입니다.」 |
| 같은 카테고리 다른 대기 제안 | — | 「같은 메뉴에 승인을 기다리는 제안 {n}건: {요약들}. 하나를 승인하면 나머지는 다시 올라올 수 있습니다.」 |
| 버튼 | [PR에서 열기 ↗] | [변경 내용 보기 ↗](GitHub, 같은 링크) |

**승인자 점검표 (메뉴 제안, 머지 전)** — `requests-rollout.md` 7-1 에 덧붙인다(ops)

1. 바뀐 파일이 `지식/<카테고리>/_menu.json` **한 장**이고, 바뀐 줄이 이름 바꾸기 1줄 / 새 메뉴 1항목 / 순서 2항목 자리 바꿈 / 지우기 1항목 뿐인가.
2. 이름에 회사 이름·금액·사람 이름이 없는가.
3. 지우기면: 그 메뉴로 가는 새 문서 제안이 대기 중이 아닌가(7-4).
4. 미리보기 빌드가 실패로 표시돼 있으면 머지하지 않는다(이름 겹침·형식 오류는 빌드 검사가 잡는다, 7-2 마지막 줄). — 이 저장소에서 PR 마다 미리보기 빌드가 도는지는 확인 필요(O4).
5. 닫을 때는 사유를 의견으로 남긴다(O3).

## 10. PR 본문 형식 (dev-server, `parseProposalPr` 가 다시 읽는다)

화면에는 나오지 않고 승인자(GitHub)와 서버만 읽는다. 그래서 여기에는 id 가 들어가도 된다. 공개 저장소이므로 이름·사유는 6-2 공개 검사를 통과한 값만 들어간다. 요청자 이름은 계정 이름(팀 이름) 그대로다.

브랜치 `docs/menu-{카테고리 id}-{시각}` · 커밋 `menu: {카테고리 id} {동작}` · 파일 `지식/{카테고리 id}/_menu.json` 하나.

PR 제목:

| 동작 | 제목 |
| --- | --- |
| 이름 바꾸기 | `메뉴 이름 바꾸기: {카테고리} › {전} → {후}` |
| 새 하위 메뉴 | `새 하위 메뉴: {카테고리} › {이름}` |
| 순서 | `메뉴 순서: {카테고리} › {이름} 한 칸 {위로/아래로}` |
| 지우기 | `메뉴 지우기: {카테고리} › {이름}` |

PR 본문:

```
{요청자}님이 위키 허브에서 하위 메뉴 {이름 바꾸기|만들기|순서 바꾸기|지우기}를 제안했습니다.

- 메뉴: {카테고리 표시 이름} › {대상 메뉴 이름(새 메뉴는 새 이름)}
- 변경: {9-1 요약에서 "{카테고리} › " 를 뺀 것}
- 동작: {rename|add|move|remove}
- 카테고리 id: {category}
- 메뉴 id: {subId}
- 이웃 id: {neighborId}            ← 순서만
- 코드 머리글: {codePrefix}         ← 새 메뉴만
- 다시 올림: #{옛 번호}              ← [다시 올리기]일 때만
- 진입: 메뉴 편집

## 변경 사유

{사유, 비었으면 "근거 미기재"}

내용을 확인하고 이상 없으면 머지해 주세요. 머지되면 다음 배포 때 사이드바에 반영됩니다. 문서 파일은 바뀌지 않습니다.
```

- 끝줄이 지금 `PR_FOOTER` 로 시작하므로 사유 자르기 규칙을 그대로 쓸 수 있다. 사유 절 이름 `## 변경 사유` 를 읽기 정규식에 더한다.
- 「- 메뉴:」·「- 변경:」 줄은 사람이 읽는 줄, 「- 동작:」~「- 이웃 id:」는 서버가 읽는 줄이다. 사람이 읽는 줄을 다시 파싱하지 않는다(이름에 `→`·`›` 가 들어가도 깨지지 않게).

## 11. 클릭 수와 기다리는 단계

| 동선 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 하위 메뉴 이름 바꾸기 요청 | 메신저로 관리자에게 양식 → 관리자가 PM 데스크에 → 개발 PR(코드 두 곳 + 챗봇 프롬프트) → 머지 → 배포. 허브 안 클릭 0, **사람 3단계 대기** | 사이드바 `⋯`(1) → [이름 바꾸기](2) → 이름 입력 → [제안 올리기](3) = **3클릭 + 이름 입력**. 대기는 관리자 승인 1단계 + 다음 반영 |
| 새 하위 메뉴 | 위와 같음 | `+ 새 하위 메뉴`(1) → 이름 입력 → [제안 올리기](2) = **2클릭** |
| 한 칸 옮기기 | 위와 같음 | `⋯`(1) → [위로](2) → 확인 없이 바로 올림 = **2클릭** |
| 빈 메뉴 지우기 | 위와 같음 | `⋯`(1) → [지우기](2) → 확인 상자 [지우자는 제안 올리기](3) = **3클릭** |
| 제출 후 상태 확인 | 해당 없음 | 성공 줄 [내 요청에서 보기] **1클릭**. 나중에는 메뉴 `내 요청`(배지) 1클릭 |
| 다시 올려야 할 때 | 해당 없음 | 내 요청 [다시 올리기] **1클릭**, 입력 없음 |
| 새 메뉴에 첫 문서 | 해당 없음 | 반영 뒤 내 요청 [이 메뉴에 문서 쓰기] 1클릭으로 새 문서 화면(메뉴 골라진 채) |

기다리는 단계: ① 제안 올리기 — 몇 초 ② 관리자 승인 — 사람, 정해진 시간 없음 ③ 다음 반영 — 승인 뒤 배포까지 걸리는 시간은 확인 필요(O2). 로컬 허브는 업데이트할 때.
