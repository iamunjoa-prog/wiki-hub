확정 전제(상위 지시자)
- 계정은 **팀 계정 4개(실무자) + 관리자 계정 1개**. 관리자 계정 담당자가 GitHub 승인자다(D5 ①).

- D2 ② 수정 제안도 비공개 이름·별표 2개는 **차단**, 금액은 **경고**. D7 ① 섹션 추가·삭제·이동은 상용화 전엔 요청으로. D8 ① 관리자 잠금 풀기 + 아이디 5→10회·IP 한도 상향. D8-2 질문 한도 계정당 분당 10→30회. 새 `api/` 파일 금지(D6).

이 문서는 문구와 규칙만 정한다. 코드는 dev-server·dev-front 가 옮긴다. 「」 안이나 코드 칸 안의 문자열은 **그대로** 옮긴다. `{ }` 는 채워 넣는 값이다. 상태 이름·검사 문구는 `requests-chat-draft.md`·`requests-report.md` 와 같은 말을 쓴다.

## 4. (a') 팀 계정에서 "내 요청"

### 4-1. 규칙

- 팀 계정은 **이름 칸 = 팀 이름** 으로 발급한다(예: 이름 `편성기획팀`, 팀 `편성기획팀`). PR 본문 첫 줄은 `편성기획팀님이 위키 허브에서 …`가 된다. 어색해도 이 형식을 **바꾸지 않는다** — `parseProposalPr` 가 `^(.+?)님이 ` 로 요청자를 읽기 때문이다.
- 관리자 계정 이름은 실명이 아닌 **`허브 관리자`** 로 둔다(첫 관리자 기본값 그대로).
- "내 요청"은 지금처럼 **이름 기준**으로 고른다. D4 를 하지 않으므로 아이디 기준으로 바꿀 필요가 없다. 팀 계정이면 팀원 누가 올렸든 팀 전체 제안이 보이고, 그것이 의도한 동작이다.
- 이름 기준의 약점: 관리자가 계정 이름을 바꾸면 **그전 제안이 내 요청에서 사라진다**(PR 본문 첫 줄은 옛 이름 그대로). 그래서 이름 수정 때 확인 문구를 띄운다(4-3).

### 4-2. 화면 문구 (전 → 후)

| 화면·자리 | 지금 | 바꾼 뒤 | 반영 |
| --- | --- | --- | --- |
| 내 요청 현황 · 문서 탭 위 안내 (`MyRequests.tsx` hint) | 「문서 제안은 GitHub PR 입니다. 머지돼도 **다음 배포 전까지는** 위키 화면에 반영되지 않습니다.」 | 첫 줄 그대로 두고 둘째 줄 추가: 「팀 계정이면 같은 팀원이 올린 제안도 여기에 함께 보여요. 누가 올렸는지는 팀 안에서 확인해 주세요.」 | dev-front |
| 내 요청 현황 · 편성표·시스템 탭 | 안내 없음 | 손대지 않음(브라우저 메모리 기록이라 팀원끼리 공유되지 않음. 따로 기획) | — |
| 사이드바 아래 계정 줄 (`AppShell.tsx` `{session.name} · {session.team}`) | `편성기획팀 · 편성기획팀` 처럼 두 번 보임 | 이름과 팀이 같으면 **한 번만**: `편성기획팀 · 팀 계정`. 팀이 비면 `{이름}`만 | dev-front |
| 계정 관리 목록 줄 (`Accounts.tsx`) | `{이름} · {팀 or 소속 미등록} · {아이디}` | 이름과 팀이 같으면 `{이름} · 팀 계정 · {아이디}` | dev-front |
| 계정 발급 폼 · 이름 칸 placeholder | `홍길동` | `팀 이름 (예: 편성기획팀)` | dev-front |
| 계정 발급 폼 · 이름 칸 아래 회색 줄 (새) | 없음 | 「이름은 제안을 올릴 때 공개 저장소에 그대로 남습니다. 직원 실명 대신 팀 이름을 넣어 주세요.」 | dev-front |
| 여러 명 발급 placeholder | 실명 예시 3줄 | `team.a\t편성기획팀\t편성기획팀` 꼴 예시로(실명 없이) | dev-front |

"팀 계정" 표시는 별도 칸을 만들지 않는다. **이름 = 팀** 이면 팀 계정으로 본다. 4-2 첫 줄 안내는 조건 없이 늘 보인다("내 대화 기록"의 「팀 계정의 대화가 함께 보여요.」와 같은 방식).

## 5. (b) 수정 제안 — 서버 공개 검사 차단

### 5-1. 기준 (새 문서와 맞춤)

| 걸리는 것 | 새 문서 직접 작성 (지금) | 수정 제안 (지금) | 수정 제안 (바꾼 뒤) |
| --- | --- | --- | --- |
| 비공개 이름 목록 일치 | 차단 | 경고 | **차단** |
| 별표 2개 가림 (`미디어**팀`) | 차단 | 경고 | **차단** |
| 금액 | 경고 | 경고 | 경고 (쿠폰 금액 허용 문장) |
| 회사 표기·URL·이메일·전화·(보완 필요) | 경고 | 경고 | 경고 |

**검사 범위 — 바뀐 줄만.** 수정 제안 본문에는 원래 문서 전체가 들어 있다. 예전부터 있던 줄까지 차단하면 고칠 수 없는 이유로 모든 수정이 막힌다. 그래서 화면(`usePublicWarnings` 의 `fresh`)과 서버가 **같은 규칙**을 쓴다.

- 본문: 앞뒤 공백을 걷어낸 줄 글자가 **지금 main 의 그 문서 본문**에 똑같이 있는 줄이면 건너뛴다. 새로 생기거나 바뀐 줄만 본다.
- 수정 사유: 늘 본다(PR 본문에 실린다).
- 제목: 수정 제안에서는 바꿀 수 없으므로 보지 않는다.
- 서버는 `createEditPR` 이 이미 읽는 main 본문과 비교한다. 화면은 배포된 본문과 비교하므로 재배포 전이면 다를 수 있으나, 그 경우는 버전이 달라 409 가 먼저 난다.

### 5-2. 응답 계약 (dev-server)

새 문서와 **같은 모양**을 쓴다. 화면이 같은 함수로 그린다.

```
POST /api/proposeEdit  (바뀐 줄에 이름·별표 2개가 있으면)
→ 400 { error: '공개 저장소에 올릴 수 없는 표현이 있습니다', code: 'public-leak', blocks: Hit[] }
  · GitHub 을 부르기 전에 돈다 — 브랜치·커밋·PR 아무것도 안 생긴다
  · Hit.line 은 사용자가 보낸 본문의 줄 번호(1부터), 사유면 where:'reason', line:null
  · 로그는 건수만: `[api/proposeEdit] 차단 · publicCheck block name=1`

POST /api/publicCheck { …, target: 'edit' }
→ 200 { blocks: [이름·별표 2개], warnings: [나머지], namesChecked }
  · 지금은 edit 이면 blocks 가 늘 빈 배열 — 이름·별표 2개를 blocks 로 옮긴다. 금액은 warnings 그대로
  · 바뀐 줄 거르기는 화면이 지금처럼 한다(서버 publicCheck 는 원문 본문이 없다)
```

로컬 중계(`server/cliBridge.ts` 의 수정 제안 경로)도 같은 검사를 거친다. 한쪽만 고치면 로컬과 배포가 갈라진다.

### 5-3. 화면 문구 (전 → 후, `ProposeEdit.tsx`)

| 자리 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 빨강 상자 제목 (새, 화면 검사에서 차단이 나왔을 때) | 없음(모두 노랑) | 「제출할 수 없습니다 — 공개 저장소에 올릴 수 없는 표현이 있습니다」 (새 문서 화면과 같은 문장) |

| 빨강 상자 끝줄 (새) | — | 「[편집으로]를 눌러 편집 칸에서 Ctrl+F 로 「 」 안의 글자를 찾아 고쳐 주세요.」 |
| 제출 버튼 | 가린 표기를 건드렸을 때(`maskLeaks`)만 꺼짐 | 빨강 상자가 있어도 꺼짐 |
| 노랑 상자 제목 | 「제출은 할 수 있지만 확인해 주세요 — 위키는 공개 저장소에 올라갑니다」 | 그대로 |
| 노랑 · 금액 항목 | 「{위치} 「{표기}」 — 금액으로 보입니다. 공개 저장소에는 금액 대신 "할인 폭이 큰 편"처럼 경향으로 쓰는 것이 좋습니다.」 | 수정 제안에서만 「{위치} 「{표기}」 — 금액으로 보입니다. 매출·거래액이면 "늘어나는 추세"처럼 경향으로 바꿔 주세요. 쿠폰 할인 금액이면 그대로 두셔도 됩니다.」 (`requests-chat-draft.md` 5-3 과 같은 문장. 챗봇 규약이 쿠폰 금액을 허용하므로) |
| 위치 표기 · 사유 | 「등록 사유」 (새 문서 기준 고정) | 수정 제안에서는 「수정 사유」 |
| 이름 목록을 못 읽었을 때 (`namesChecked:false`) | 안내 없음 | 상자 끝 회색 한 줄: 「이 허브에서는 제휴사 이름을 자동으로 확인하지 못했습니다. 제휴사 이름이 들어가 있지 않은지 직접 확인해 주세요.」 (새 문서와 같은 문장) |
| 서버가 막았을 때 (400 `public-leak`) | 「제출하지 못했습니다 — 공개 저장소에 올릴 수 없는 표현이 있습니다」 한 줄(원문 그대로) | 빨강 상자를 서버 `blocks` 로 다시 그리고, 상자 위에 「제출하지 않았습니다. 아래 줄을 고친 뒤 다시 제출해 주세요. 편집한 내용은 그대로 있습니다.」 |
| 화면 검사 자체가 실패 | 조용히 넘어감(콘솔만) | 그대로 둔다. 서버가 제출 때 다시 막는다 |

**걸린 줄 보여 주기 — 정한 것**
- 1차는 **문장으로만** 보인다: `{n}번째 줄 「{걸린 글자}」`. 걸린 글자는 사용자가 쓴 글자라 보여 줘도 된다. 목록의 다른 항목은 절대 보이지 않는다.
- 편집 칸에는 줄 번호가 없으므로 끝줄에서 **Ctrl+F 로 찾기**를 안내한다. 비교(diff) 화면의 줄 강조는 하지 않는다(작업이 크고, 같은 글자 찾기로 충분).
- 같은 글자가 여러 줄에 있으면 줄마다 한 항목씩 보인다(지금 `scanText` 동작 그대로).

## 6. (c) 로그인 잠금 · 잠금 풀기 · 한도 429

### 6-1. 바뀌는 수치 (확정, 반영은 dev-server)

| 항목 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 아이디 기준 잠금 | 5회 / 10분 | **10회** / 10분 |
| IP 기준 잠금 | 30회 / 10분 | 상향 (값은 dev-server 가 사무실 인원 기준으로 제안, 6-6 Q) |
| 질문 한도 | 계정당 분당 10회 | **분당 30회**, 환경변수로 조정 |
| 제안 하루 한도(계정) | 30건 | 유지 |
| 제안 하루 상한(허브 전체, 새) | 없음 | 새로 둔다. 값은 6-6 Q |

### 6-2. 로그인 화면 문구 (전 → 후)

서버가 아이디 잠금과 IP 잠금을 **다른 `code` 로** 구분해 준다(지금은 같은 문장). 화면은 `code` 로 문장을 고른다.

| 경우 | 지금 | 바꾼 뒤 | 계약 |
| --- | --- | --- | --- |
| 아이디 잠금 | 「로그인에 여러 번 실패했습니다. 10분 뒤에 다시 시도해 주세요」 | 「비밀번호가 여러 번 틀려 이 계정이 잠겼습니다. 10분 안에 저절로 풀립니다.<br>팀 계정은 팀원 누가 틀려도 횟수가 함께 쌓여, 팀 전체가 로그인하지 못할 수 있어요.<br>급하면 허브 관리자에게 **잠금 풀기**를 요청해 주세요.」 | 429 `code:'locked'` |
| IP 잠금 | 같은 문장 | 「이 사무실 인터넷에서 로그인 실패가 많아 잠시 막혔습니다. 10분 안에 저절로 풀립니다. 계속되면 허브 관리자에게 알려 주세요.」 | 429 `code:'locked-ip'` |
| 틀림 (남은 횟수 3회 이하일 때, 새) | 「아이디 또는 비밀번호가 맞지 않습니다」 | 「아이디 또는 비밀번호가 맞지 않습니다. {n}번 더 틀리면 이 계정이 10분 동안 잠겨 팀원 모두 로그인하지 못합니다.」 | 401 + `remaining:n` (없는 아이디에도 실패 횟수를 똑같이 세므로 계정 유무가 드러나지 않는다) |
| 틀림 (그 밖) | 「아이디 또는 비밀번호가 맞지 않습니다」 | 그대로 | — |

로그인 화면은 로그인 전이라 관리자 이름·연락처를 띄우지 않는다. "허브 관리자"가 누구인지는 팀별 비밀번호를 전달할 때 함께 알린다(ops, `docs/accounts.md`).

### 6-3. 계정 관리 "잠금 풀기" (관리자)

**서버 계약 (dev-server, 새 `api/` 파일 없음)**

```
GET /api/users → users[i] 에 locked: boolean 추가
  · 아이디 기준 실패 횟수가 한도 이상이면 true. IP 잠금은 계정에 붙지 않으므로 넣지 않는다
PATCH /api/users { loginId, unlock: true } → 200 { user, unlocked: true }
  · 아이디 기준 실패 기록만 지운다. 비밀번호·세션은 그대로
  · 잠겨 있지 않아도 200 (두 번 눌러도 문제없게)
PATCH /api/users { loginId, resetPassword: true } → 실패 기록도 함께 지운다 (새)
  · 지금은 초기화한 임시 비밀번호가 잠금 때문에 10분간 안 먹는다
```

**화면 (dev-front, `Accounts.tsx` 각 계정 줄)**

| 자리 | 문구 |
| --- | --- |
| 상태 태그 | 잠겼으면 기존 태그 앞에 빨강 `잠김` |
| 버튼 | `잠금 풀기` — `locked` 일 때만 보인다. 자기 줄에는 없다 |
| 확인창 | 「{이름} 계정의 로그인 잠금을 풀까요? 비밀번호는 바뀌지 않고, 바로 다시 로그인할 수 있어요.」 |
| 성공 (목록 위 초록 상자, 기존 임시 비밀번호 상자 자리) | 「{이름} 계정의 잠금을 풀었습니다. 팀원에게 다시 로그인해 보라고 알려 주세요. 비밀번호를 잊어서 잠긴 거라면 [비밀번호 초기화]를 눌러 새 임시 비밀번호를 전달해 주세요.」 · [닫기] |
| 실패 | 기존 `account-error` 자리에 「잠금을 풀지 못했습니다 — {서버 문장}」 |
| 목록 머리 | 오른쪽 `{n}명` 옆에 `새로고침` 버튼(새). 잠김 표시는 화면을 연 때 기준이라, 요청을 받으면 눌러 확인한다 |

비밀번호 초기화 확인창도 팀 계정에 맞춘다.

| 자리 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 비밀번호 초기화 확인창 | 「{이름}님의 비밀번호를 초기화할까요?」 | 「{이름} 계정의 비밀번호를 초기화할까요? 이 계정을 쓰는 팀원 모두 로그아웃되고, 새 임시 비밀번호로 다시 로그인해야 합니다.」 |
| 사용 중지 확인창 | 「{이름}님 계정의 사용을 중지할까요? 바로 로그아웃됩니다.」 | 「{이름} 계정의 사용을 중지할까요? 이 계정을 쓰는 팀원 모두 바로 로그아웃됩니다.」 |

### 6-4. 한도 429 문구

서버는 지금처럼 `code:'rate'`, `rule`, `windowSeconds` 를 준다. 화면은 `rule` 로 문장을 고른다(서버 `error` 원문을 그대로 붙이지 않는다).

| `rule` | 언제 | 지금 문구 | 바꾼 뒤 문구 | 보이는 곳 |
| --- | --- | --- | --- | --- |
| `pr` (계정 하루) | 이 계정이 하루 30건 넘음 | 「제출하지 못했습니다 — 오늘 올릴 수 있는 제안 수(하루 30건)를 넘었습니다. 내일 다시 제출해 주세요」 | 「이 계정이 오늘 올릴 수 있는 제안 수(하루 {limit}건)를 다 썼습니다. 팀 계정은 팀원이 올린 제안도 함께 셉니다. 내일 다시 제출해 주세요. 편집한 내용은 그대로 있습니다.」 | 수정 제안·새 문서·챗봇 카드 |
| `pr-total` (새, 허브 전체 하루) | 모든 계정 합계가 상한 넘음 | 없음 | 「오늘 허브 전체에서 올릴 수 있는 제안 수를 다 썼습니다. 내일 다시 제출해 주세요. 편집한 내용은 그대로 있습니다.」 | 같음 |
| `ask` (질문 분당) | 이 계정이 1분에 30번 넘게 물음 | 「요청이 잠깐 많아 문서 기준 규칙 기반으로 답했습니다. 잠시 후 다시 물어보세요.」 | 「질문이 잠깐 몰려 문서 기준 규칙 기반으로 답했습니다. 팀 계정은 팀원 모두 합쳐 1분에 {limit}번까지 물을 수 있어요. 1분쯤 뒤에 다시 물어보세요.」 | 챗봇 답 위 한 줄 |

- `pr-total` 은 숫자를 보이지 않는다(실무자가 할 수 있는 일이 "내일"뿐이라).
- 새 문서 화면은 끝말을 「입력한 내용은 그대로 있습니다.」, 챗봇 카드는 「초안은 그대로 있습니다.」로 바꾼다(`requests-chat-draft.md` 5-8 규칙).
- **"내일"이 참이 되게** 하루 한도를 한국 시간 자정에 풀리도록 바꿀 것을 dev-server 에 요청한다(키에 KST 날짜를 넣는 방식 등). 못 바꾸면 문장의 「내일 다시」를 「24시간 안에 다시 열립니다. 그때」로 바꾼다.
- 관리자에게만 끝에 `· HTTP 429 · {rule}` 를 붙인다(기존 규칙).

### 6-5. 질문 한도 문구를 바꾸는 범위

`FAILURE_CAUSE.rate` 는 AI 수정(`/api/edit`, 분당 10회 유지)과 함께 쓴다. `ask` 일 때만 위 문장을 쓰고, `edit` 은 지금 문장 「요청이 잠깐 많아 수정하지 못했습니다. 잠시 후 다시 시도해 주세요.」를 둔다.

### 6-6. 이 절의 열린 값

| Q | 내용 | 제안 |
| --- | --- | --- |
| Q1 | IP 잠금 한도 | 사무실 인원 × 3 정도. dev-server 가 값과 근거를 PR 에 적는다 |
| Q2 | 허브 전체 하루 PR 상한 | 시범(한 팀) 동안 60건(계정 한도 30 × 2). 4팀 전체 공개 때 다시 정한다 |

## 7. (d) 승인자 점검표 — 관리자 계정 담당자 = GitHub 승인자

승인 관리 화면 상세(`Approvals.tsx`) 아래에 접힌 상자로 두고, 같은 내용을 운영 메모(ops)에 둔다. **PR 이 열린 순간 이미 공개**이므로, 문제를 찾으면 머지하지 않는 것만으로는 부족하다 — 아래 "찾았을 때"를 따른다.

### 7-1. 머지 전 점검 (PR 의 Files changed 에서, 위에서 아래로)

| # | 볼 것 | 어디서 | 통과 기준 |
| --- | --- | --- | --- |
| 1 | **금액** | 본문 바뀐 줄, PR 본문의 사유 | 매출·거래액·정산 금액이 없다. 쿠폰 할인 금액·할인율은 둬도 된다(챗봇 규약). 수정 제안의 금액은 서버가 **경고만** 하므로 여기서 사람이 거른다 |
| 2 | **제휴사 이름** | 본문·사유·PR 제목 | 회사 이름 대신 "제휴사"로 쓰였다. 서버가 막는 것은 비공개 이름 목록에 있는 이름뿐이다. 목록에 없는 새 회사 이름은 통과한다 → 보이면 ops 에 목록 추가를 요청 |
| 3 | **직원 실명** | 본문·사유·PR 본문 첫 줄·`updatedBy` | 첫 줄이 팀 이름(`{팀}님이 …`)이다. 본문에 담당자 실명이 없다(가릴 땐 별표 하나, 예: `구*화`) |
| 4 | **내부 주소** | 본문·사유 | 사내 시스템 주소·IP·내부 도메인·메일 주소·전화번호가 없다. 사내 주소는 "(URL 생략)" |
| 5 | 문서 코드 중복 (새 문서) | PR 제목 `(코드)` | 열린 다른 새 문서 PR 과 코드가 겹치지 않는다(서버가 열린 PR 은 보지 않음) |
| 6 | 의도한 곳만 바뀜 (수정) | diff | 사유와 관계없는 줄이 지워지거나 바뀌지 않았다 |
| 7 | 같은 문서의 다른 대기 PR | 승인 관리 목록 | 둘 다 머지하면 충돌할 수 있다. 먼저 하나를 머지하고 나머지는 요청 팀에 다시 제안을 부탁 |

### 7-2. 찾았을 때

| 상황 | 할 일 |
| --- | --- |
| 1~4 에 걸림 | 머지하지 않고 PR 을 **닫는다**(반려). 닫기 댓글에 걸린 내용을 **다시 적지 않는다**(댓글도 공개). 「공개 규칙(금액·회사 이름·실명·사내 주소)에 걸리는 표현이 있어 닫습니다. 경향으로 바꿔 다시 제안해 주세요.」 |
| 이미 공개된 내용이 민감함 | 닫은 뒤 브랜치 삭제. PR diff 는 남으므로 PM 데스크에 알려 기록 정리 여부를 정한다 |
| 목록에 없는 제휴사 이름이 보임 | ops 에 비공개 이름 목록 추가 요청(공유 드라이브 파일 + Vercel 환경변수 둘 다) |
| 5~7 | 반려 댓글로 이유를 짧게. 실명·금액 없이 |

### 7-3. 화면 문구 (전 → 후, `Approvals.tsx` 상세 아래)

| 자리 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 상세 아래 안내 | 「머지는 GitHub PR 화면에서 합니다. 변경 내용(diff)도 거기서 봅니다. 머지해도 다음 배포 전까지는 위키 …」 | 그대로 + 아래 접힌 상자 |
| 접힌 상자 제목 (새) | 없음 | `머지 전 점검 4가지 — 금액 · 제휴사 이름 · 직원 실명 · 사내 주소` |
| 접힌 상자 본문 (새) | 없음 | 7-1 의 1~4 를 한 줄씩. 끝줄 「걸리면 머지하지 말고 PR 을 닫아 주세요. 닫는 댓글에 걸린 내용을 다시 적지 마세요(댓글도 공개됩니다).」 |

| --- | --- |
| 누가 | 팀 계정을 쓰는 실무자 누구나 |
| 어디로 | **허브 관리자(관리자 계정 담당자)** 에게 사내 메신저로. 허브 안에 요청 화면은 만들지 않는다(시스템 등록 요청처럼 브라우저 메모리에만 남는 문제를 되풀이하지 않기 위해). 채널은 Q3 |
| 어떤 정보로 | 아래 요청 양식을 복사해 채운다 |
| 누가 처리 | 관리자가 받아 PM 데스크에 넘긴다 → 문서 삭제·이동은 개발 PR(문서 파일 이동·링크 정리), **섹션(서브메뉴) 추가**는 메뉴 정의가 코드 여러 곳에 있어 dev-front·dev-server PR. 머지·배포 후 관리자가 요청자에게 알린다 |
| 얼마나 걸리나 | 안내에 날짜를 약속하지 않는다. 「다음 배포 때 반영됩니다」까지만 쓴다 |
| 안 되는 것 | 제목·본문을 고치는 것은 요청이 아니라 **수정 제안**으로 한다. 새 문서 하나 추가는 **+ 새 문서** 로 한다(섹션이 이미 있으면) |

**요청 양식** (안내 문서에 그대로 싣는다)

```
[허브 섹션 요청]
1. 종류: 섹션 추가 / 문서 삭제 / 문서 이동 / 섹션 이름 바꾸기 중 하나
2. 대상: 문서 코드와 제목 (예: PPC-R-06 ○○ 안내) — 섹션 추가면 "없음"
3. 지금 위치: 카테고리 › 서브메뉴
4. 바꿀 위치·새 이름: (이동·추가·이름 바꾸기일 때)
5. 이유: 한두 줄
6. 요청 팀:
※ 금액·제휴사 이름·직원 실명은 쓰지 않습니다.
```

**문구** (자리는 wiki-ux 설계안을 따른다)

| 자리 | 문구 | 반영 |
| --- | --- | --- |
| 이용 안내 문서 (새, `지식/guide/`) | 제목 「새 분류 추가·문서 삭제·이동은 이렇게 요청하세요」, 본문은 위 표와 양식 | ops |
| 수정 제안 화면 1단계 아래 회색 한 줄 (새) | 「문서를 지우거나 다른 분류로 옮기려면 수정 제안 대신 [요청 방법]을 봐 주세요.」 ([요청 방법] = 위 안내 문서) | dev-front (자리는 wiki-ux) |
| 챗봇 — 삭제·이동을 부탁받았을 때 | 「문서 삭제·이동은 아직 챗봇이나 화면에서 할 수 없어요. 허브 관리자에게 요청해 주세요. [요청 방법]」 | chatbot-planner 와 맞춤(규약 `none` 유지) |

### 8-2. 상용화 후 — 삭제·이동 제안 (초안)

기획서 5단계 1번. 지금은 만들지 않는다. 만들 때 이 초안에서 시작한다.

**무엇을 만드는가**

| 종류 | 하는 일 | 브랜치 | PR 제목 |
| --- | --- | --- | --- |
| 삭제 | 문서 파일 1개 삭제 | `docs/delete-{코드}-…` | `문서 삭제: {제목} ({코드})` |
| 이동 | 같은 파일의 카테고리·서브메뉴(필요하면 적용 상품) 변경. **문서 코드는 그대로**(링크·챗봇 인용이 코드로 걸려 있음) | `docs/move-{코드}-…` | `문서 이동: {제목} ({코드})` |

- 서버는 이 둘을 추가하기 **전에** `parseProposalPr` 가 `docs/delete-`·`docs/move-` 를 구분하게 해야 한다. 지금은 `docs/edit-` 가 아니면 모두 "새 문서"로 읽는다.
- PR 본문 첫 줄은 지금과 같은 형식: `{팀 이름}님이 위키 허브에서 문서 삭제를 제안했습니다.` / `… 문서 이동을 제안했습니다.` 사유 절은 `## 삭제 사유` / `## 이동 사유`.

**상태** — 2절 네 단계 그대로. 태그 종류만 늘어난다.

| 내 요청·승인 관리 종류 태그 | 지금 | 상용화 후 |
| --- | --- | --- |
| 새 문서 | `새 문서` | 그대로 |
| 수정 | `수정` | 그대로 |
| 삭제 | — | `삭제` (빨강 테두리) |
| 이동 | — | `이동` |

**권한**

| 동작 | 팀 계정 | 관리자 | 막는 곳 |
| --- | --- | --- | --- |
| 삭제·이동 제안 | 된다 | 된다 | 서버: 로그인·하루 한도(`pr` 함께 셈)·사유 필수 |
| 삭제 머지 | 못 함 | GitHub 에서 | GitHub 권한 |
| 다른 문서가 링크하는 문서 삭제 | 제출은 되고 경고 | 점검표에서 확인 | 서버가 링크 수를 PR 본문에 적는다 |

**문구 초안**

| 자리 | 문구 |
| --- | --- |
| 문서 화면 메뉴 | `⋯` 안에 `삭제 제안` · `이동 제안` (진입점은 wiki-ux) |
| 삭제 확인 1단계 | 「이 문서를 지우자고 제안합니다. 관리자가 승인(머지)하면 다음 배포 때 위키에서 사라집니다. 지금 바로 지워지지는 않습니다.」 |
| 삭제 · 링크 경고 | 「다른 문서 {n}개가 이 문서를 가리키고 있습니다. 지워지면 그 링크가 끊깁니다.」 + 문서 목록 |
| 사유 칸 | 라벨 `삭제 사유 *` / `이동 사유 *`, placeholder 「왜 지우는지(옮기는지) 적어 주세요 — 승인자가 판단하는 근거가 됩니다」 |
| 제출 버튼 | `삭제 제안 제출` / `이동 제안 제출` (진행 중 `PR 만드는 중…`) |
| 완료 | 「{제목} ({코드}) 삭제 제안을 올렸습니다(PR #{n}). 관리자가 승인(머지)하면 다음 배포 때 위키에서 사라집니다. 지금 바뀐 것은 없습니다.」 / 이동은 「… 다음 배포 때 {새 위치}로 옮겨집니다.」 |
| 승인 관리 상세 (삭제) | 「삭제 제안입니다. 머지하면 다음 배포 때 이 문서가 위키에서 사라집니다. 링크가 끊기는 문서가 있는지 PR 본문에서 확인해 주세요.」 |
| 승인자 점검표 추가 | 삭제: 링크 끊김 수, 같은 문서의 대기 중 수정 제안(머지하면 지운 문서가 되살아남). 이동: 새 위치 서브메뉴가 실제로 있는지 |
