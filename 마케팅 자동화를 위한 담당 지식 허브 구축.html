01 과제 배경

기준을 찾는 일이
결국 사람에게 묻는 일이 된다

담당 4개 팀이 각자의 편성·마케팅 판단 근거를 따로 관리하고 있어,
담당 전체가 함께 볼 하나의 기준이 없는 상태.

현황

편성 인사이트·마케팅/편성 정책이 개인 PC·메신저·사내 사이트에 분산.
시트 양식도 구글시트·PPT·컨플루언스로 제각각.

문제

정보를 찾으려면 아는 사람에게 묻거나 폴더를 뒤져야 한다.
수정 이력·승인 절차가 없어 구버전 기준이 적용될 위험도 남는다.

왜 중요한가

담당 내 마케팅 자동화 프로젝트가 상용화 전 단계.
자동화가 참조할 정제된 기준 문서를 지금 만들어 두어야 한다.

담당 4개 팀은 각자 편성·마케팅 기준을 따로 관리하고 있습니다.
개인 PC, 메신저, 사내 사이트에 흩어져 있고 양식도 구글시트·PPT·컨플루언스로 제각각입니다.
그러다 보니 기준이 필요할 때마다 결국 아는 사람에게 물어봐야 하고, 수정 이력이 남지 않아 구버전 기준이 적용될 위험도 있습니다.
마침 담당 내 마케팅 자동화 프로젝트가 상용화 전 단계라, 자동화가 참조할 정제된 기준 문서를 지금 만들어 둬야 한다고 판단했습니다.
02 솔루션 내용 · 진행 과정

무엇을 만들었나

지식 위키 + 시트 허브 + 챗봇을 하나로 묶은 담당용 웹앱.
핵심은 대화에서 프로모션 실행까지 끊기지 않는 흐름.

1

지식 위키 — 흩어진 문서를 한 저장소로

프로모션 정책·마케팅 인사이트·시스템 매뉴얼·이용 안내 38건을 마크다운 트리로 이관.
트리 열람·검색·버전 확인

2

문서 근거 챗봇 — 출처를 함께 보여준다

위키 문서만 근거로 답하고 근거 문서를 함께 표시.
문서에 없으면 없다고 답한다

3

수정 제안 → 승인 — 문서가 낡지 않게

실무자 수정 제안(diff 비교) → 관리자 승인 → 위키 반영.
변경 이력이 남는다

4

시트 허브 · 편성 스케줄 — 담당 전체가 같은 화면을

B tv · 모바일 B tv 플랫폼 기준 편성 모니터링, 빅배너 스케줄, 캠페인 신청 캘린더

5

프로모션 핸드오프 — 대화에서 실행 화면까지

대화로 정리된 조건(기간·채널·구분·타겟·스킴)을 요약 카드로 확인받아 실행 화면으로 전달

만든 건 지식 위키 + 시트 허브 + 챗봇을 하나로 묶은 담당용 웹앱입니다.
1) 흩어진 문서 38건을 마크다운 트리로 이관한 지식 위키, 2) 그 위키만 근거로 답하고 출처를 함께 보여주는 챗봇, 3) 실무자 수정 제안을 diff로 비교해 관리자가 승인하는 흐름, 4) 편성 모니터링·빅배너 스케줄 같은 시트 허브, 5) 대화로 정리된 프로모션 조건을 요약 카드로 넘기는 핸드오프까지 다섯 가지입니다.
핵심은 대화에서 실행까지 끊기지 않는 흐름이라는 점을 강조해주세요.

02 솔루션 내용 · 진행 과정

AI와 어떻게 만들었나

1

기획서로 범위를 먼저 좁혔다

중간과제 기획서에서 "챗봇 → 프로모션 핸드오프 하나만은 끝까지 돌아가게"로 핵심 범위를 박고 시작

2

문서 이관과 앱 구현을 Claude Code로

기존 PPT·매뉴얼을 마크다운 위키트리로 일괄 이관하고, 화면 14개·약 7,800줄을 대화로 구현 (PR 28건)

3

챗봇 품질은 코드가 아니라 규약 문서로 잡았다

답변 규칙을 프롬프트 문서로 분리 — 결론부터 5줄 이내, 문서에 없으면 없다고 말하기, 상품 유형(PPM·PPV) 교차 인용 금지

4

승인 절차는 만들지 않고 Git을 그대로 썼다

수정 제안=브랜치, diff 뷰=PR, 승인=리뷰, 반영=머지.
main 보호로 AI가 직접 반영하지 못하게 하고 최종 승인은 사람이 한다

Claude Code React · TypeScript · Vite Git 기반 문서 관리 프롬프트 규약 문서화 더미 데이터 검증
AI와는 이렇게 협업했습니다.
먼저 중간과제 기획서에서 "챗봇 → 프로모션 핸드오프 하나만은 끝까지 돌아가게"로 범위를 좁혔고, 문서 이관과 화면 구현(14개 화면·약 7,800줄)을 Claude Code와 대화하며 PR 28건으로 진행했습니다.
챗봇 품질은 기능을 고치는 대신 답변 규칙을 프롬프트 문서로 분리해서 잡았고, 승인 절차도 새로 만들지 않고 Git 워크플로우(브랜치=제안, PR=diff, 리뷰=승인, 머지=반영)에 그대로 대응시켰습니다.

더 중요한 건 담당자가 자리를 비워도 업무가 멈추지 않는다는 점, 그리고 문서가 수정 제안·승인 루트로 계속 살아있게 유지된다는 점입니다.

04 최종 코멘트

Lesson Learned & 향후 계획

지식은 체계가 절반이다

컨플루언스에 산재해 있던 문서를 한 번에 마크다운으로 모아 분류하고 나니, 그제서야 컴퓨터가 읽을 수 있는 문서가 됐다.
같은 내용인데도 흩어져 있을 때는 챗봇이 근거로 쓰지 못했다.
정리 자체가 기능이었다.

품질은 코드가 아니라 규약 문서로

챗봇이 서로 다른 상품·조건의 기준을 섞어 답하던 문제는 기능을 고쳐서가 아니라 지켜야 할 규칙 한 줄을 문서에 추가해서 해결됐다.
승인 절차도 새로 만들지 않고 Git 워크플로우에 대응시키자 개발량이 크게 줄었다.

상용화는 사람의 분류에서 시작

지금 분류는 만드는 사람 기준이다.
교육 종료 후에는 실무자가 실제로 쓰는 방식과 용어로 카테고리를 다시 짜고, 그 기준에 문서를 담아 실무자에게 배포해 최종 검수·수정을 받는다.

  • → 향후 계획 ① 실무자 기준 카테고리 재설계 → 문서 재배치 → 담당 4개 팀 배포 후 최종 검수·수정
  • → 향후 계획 ② NCMS·EUXP 등 담당이 쓰는 시스템을 순차 연결 — 지금은 일부만 연결한 베타 수준
  • → 향후 계획 ③ 핸드오프 필드 매핑을 프로모션 자동화 담당과 확정해 실행 화면까지 연결, 챗봇 답변 품질 점검 루틴 운영
배운 점 세 가지입니다.
첫째, 지식은 체계가 절반이었습니다 — 컨플루언스에 흩어져 있던 문서를 한 번에 마크다운으로 모아 분류하고 나서야 컴퓨터가 읽는 문서가 됐습니다.
둘째, 챗봇 품질은 코드가 아니라 규약 문서로 잡혔습니다.
(질문 나오면 풀어서 설명: 프로모션 상품은 PPM·PPV 두 종류로 나뉘고 적용 정책이 서로 다른데, 초기 챗봇은 PPV를 물어도 PPM 전용 정책까지 끌어와 섞어서 답하는 문제가 있었습니다. 이걸 검색 로직 같은 코드를 고쳐서 잡은 게 아니라, 챗봇이 참고하는 답변 규약 문서에 "사용자가 말한 상품 유형의 문서만 쓰고 섞지 마라"는 규칙 한 줄을 추가해서 해결했습니다. 코드는 그대로 두고 지시문만 고쳐 품질을 잡은 겁니다.)
승인 절차도 새로 개발하지 않고 이미 있는 Git 워크플로우(브랜치=제안, PR=검토, 머지=반영)에 그대로 대응시켜 개발량을 줄였습니다.
셋째, 지금 분류는 만드는 사람 기준입니다 — 교육이 끝나면 실무자가 실제로 쓰는 방식과 용어로 카테고리를 다시 짜고, 그 기준에 문서를 담아 실무자에게 배포해 최종 검수·수정을 받을 계획입니다.
마지막으로 NCMS·EUXP 같은 담당 시스템 연결은 지금은 일부만 연결한 베타 수준이라는 점, 그리고 핸드오프 실행 연결과 챗봇 품질 점검 루틴이 다음 단계라는 점으로 마무리하겠습니다. 감사합니다.
